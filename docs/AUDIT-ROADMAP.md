**Три находки изменили форму при столкновении с фактами.**

*B13.* Аудит предлагал убрать `/nv` у `MakeAppx`. Проверка показала, что `/nv`
здесь вынужден: пакет объявляет внешний `AsteriaScale.exe`

манифест, block map, размеры объявленных логотипов и подпись MSIX; регистрация
сначала выполняет транзакционное обновление и удаляет прежнюю версию только при
точном конфликте той же версии и наличии проверенного rollback-пакета.
`run.ps1` дополнительно сверяет корень зарегистрированного sparse package с
текущим publish, иначе Windows OCR мог молча работать с чужой сборкой.

*B3.* Правка кода не отменяет следствия: состав трёх holdout-ов уже повлиял на
отбор обучающих данных, поэтому для по-настоящему слепого финального
подтверждения обученной модели понадобится новый набор. Запись — в
[RESEARCH.md](RESEARCH.md), журнал открытий frozen holdout.

*B6.* Поведенческую часть (не отправлять toggle, когда запрошенное уже
выполняется) нельзя воспроизвести без живого Magpie, поэтому решение вынесено в
чистую `PlanScalingCommand` и покрыто тестом на ней; сам `ScaleAsync` проверен
существующим smoke-тестом реального жизненного цикла движка.

**Долг, закрытый попутно:** fingerprint сборки снимается до publish и

## Проход 4 — корректность захвата текста (16 августа 2026)

Проход целился в один вопрос: **доходит ли до перевода ровно тот текст, на
который навёл пользователь**. Путь прослежен от `GetCursorPos` до payload
TranslateGemma: `VisibleCursorService` → `WindowsAiOcrService` →
`TextHookService` → `SmartPhraseContextBuilder`. Дополнительно — общая культура
кода и обязательный smoke-гейт.

```
dotnet build AsteriaScale.slnx -c Release   → OK, 0 предупреждений
tests/AsteriaScale.Tests                    → PASS: 54 smoke tests (6 из 7 прогонов, см. D4)
```

| # | Задача | Тип | Статус |
|---|---|---|---|
| D1 | Порядковый номер вхождения токена считается в одном тексте, а применяется к другому | баг P1 | **выполнено** |
| D2 | Попадание в кэш распознавания обходит гейт стабильности предложения и гейт подписи | инвариант P2 | **выполнено** |
| D3 | Ветка `colon` в `TryFindLeadingSpeaker` принимает нарративный зачин за имя говорящего | баг P2 | **выполнено, severity уточнена** |
| D4 | Ассерт бюджета памяти sense-индекса недетерминирован (1 отказ из 7) | тесты P3 | **выполнено, механизм не найден** |
| D5 | В OCR используется приватный резолвер вхождений вместо общего `RankerTargetAnchor` | согласованность P3 → баг | **выполнено, severity повышена** |

*D1* — главная находка прохода, и единственная, где ломается уже записанное
намерение. `FindTokenOccurrenceOrdinal` (`TextHookService.cs:1037`) считает
вхождения по **предложению из OCR**, а `TryFindToken` (`:1010`) применяет
полученный номер к **целой строке Textractor**. Домены разные по построению:
`ExtractSentence` сужает OCR ровно до одного предложения, тогда как одна hook-строка
их обычно содержит несколько. Воспроизведено на изолированном probe против
собранных сборок проекта:

```
hook   : "I went to the bank. The bank was closed."
OCR    : "The bank was closed."   (курсор на index 4)
=> hook index 14 → в TranslateGemma уходит "I went to the bank."
```

Пострадали одновременно якорь WSD и `SmartPhraseContextBuilder`: переводится
чужое предложение, а карточка при этом честно рапортует `HOOK`. Комментарий на
`TextHookService.cs:1060` описывает ровно тот исход, который должен был быть
исключён («assigning a repeated hook token to the wrong sense»). Существующий
тест (`TextHookSafetyTests.cs:68`) проходит лишь потому, что лишний префикс в
фикстуре — имя `LongSpeaker`, а не повтор самого `bank`.

**Выполнено (16 августа 2026).** Порядковый номер как таковой не чинился — он
непереносим между текстами, которые делятся на предложения по-разному.
Согласованы домены: обе стороны теперь считают вхождение **внутри предложения**.
`ResolveOcrTargetAnchor` сужает OCR-вход до предложения вокруг курсора через
`SentenceBoundaryRules.FindContainingSpan` (в dictionary-режиме туда приходит
целая строка OCR, а не предложение — раньше и эта сторона была неверна) и отдаёт
типизированный `OcrTargetAnchor`: токены предложения плюс номер вхождения в нём.
`TryFindToken` группирует вхождения по их предложению в hook-строке и требует
совпадения номера **и** того, что OCR-предложение является упорядоченной
подпоследовательностью hook-предложения.

Два намеренных решения по краям:

- **Единственное вхождение переносится без номера.** Иначе одна ошибка OCR в
  соседнем слове отменяла бы hook-апгрейд для строк, где никакой
  неоднозначности нет.
- **Повтор без сопоставимого предложения возвращает `null`.** Это строже
  прежнего поведения: раньше номер применялся вслепую. Выбор совпадает с уже
  записанным в модуле предпочтением — «retaining OCR context is safer than
  assigning a repeated hook token to the wrong sense».

Направление подпоследовательности выбрано односторонним (OCR ⊆ hook), а не
симметричным, как в `StabilizeSentenceContext`: там оба наблюдения равноправны,
здесь hook-строка авторитетна, а OCR может быть обрезан краем рамки захвата.
Симметрия допускала бы больше кандидатов и тем самым возвращала бы часть риска,
ради снятия которого карточка и заведена.

**Порождённый рефактор.** `SentenceComparisonTokens` и `IsOrderedSubsequence`
были приватны в `WindowsAiOcrService`, а нужны обоим потребителям, поэтому
вынесены в `SentenceComparison` — сравнение двух наблюдений одной реплики.
Скопировать их означало бы закрыть D1 и завести второй экземпляр D5.

Тесты в `TextHookSafetyTests`: перенос якоря во второе предложение hook-строки
(до правки давал индекс 14 вместо 24 и отправлял в TranslateGemma «I went to the
bank.») и отказ переносить повтор через предложение, которого OCR не видел.

*D2* — при попадании в `_hoverCache` результат возвращается напрямую из
`SelectRecognitionNearCursor` (`WindowsAiOcrService.cs:148-163`), а
`SelectNearPoint` не выставляет `IsSentenceContextStable` — у record'а дефолт
`true` (`:33`). Поэтому не выполняются ни `LooksLikeCompleteOcrSentence` (`:312`),
ни `StableObservedSpeaker` (`:317`). Это не край: кэш живёт 30 с и требует лишь
совпадения bounds и fingerprint, а зона переиспользования для кадра 2400×720 —
2160×560. В VN кадр статичен, поэтому оба гейта работают только на **первом**
наведении на кадр, а все последующие выбирают уже другую строку без проверок.
Предложение, обрезанное краем рамки захвата, получает
`IsSentenceContextStable = true` и проходит `HasReliablePhraseContext`
(`SmartHoverPipeline.cs:817`) — ровно тот случай, против которого написан
комментарий «made the model invent continuations for the missing half».
Нарушается и прямой текст `ARCHITECTURE.md`: «OCR принимает отдельную подпись
только при двух совпавших наблюдениях». Найдено чтением кода: путь требует
живого NPU OCR и на probe не воспроизводится.

**Выполнено (16 августа 2026).** Разделены два разных утверждения, которые
`IsSentenceContextStable` смешивал в одном флаге:

- **согласие кадра** — свойство кадра, устанавливается один раз двумя
  захватами и корректно переиспользуется по fingerprint;
- **полнота предложения и подтверждённость подписи** — свойства *выбора*,
  которые обязаны пересчитываться на каждом наведении.

`ApplyConfirmedFrameGates` применяет вторую группу к результату, поднятому из
кэша. Флаг больше не наследуется от дефолта record'а.

**Вторая половина дефекта, которой не было в карточке.** Изначально
формулировалось только про `LooksLikeCompleteOcrSentence`. При разборе
выяснилось, что подпись протекала строже: `StableObservedSpeaker` мог
**отклонить** имя (наблюдения разошлись), результат при этом кэшировался, а
следующее попадание заново выводило подпись из геометрии — без всякой сверки.
То есть кэш умел *воскрешать* именно ту нашлёпку, которую гейт только что
забраковал. Поэтому в `HoverRecognitionCacheEntry` добавлено
`ConfirmedSpeakerName`: подтверждение путешествует вместе с распознаванием,
потому что два захвата, между которыми оно устанавливалось, ни одно последующее
наведение переиспользовать не может. Подпись принимается только при совпадении
имени с подтверждённым.

**Принятый размен.** Если в одном кадре несколько блоков с разными нашлёпками,
то на попаданиях в кэш подпись чужого блока будет отклонена — она в этом кадре
никогда не подтверждалась дважды. Отказ в сторону `null` безопасен (род просто
не применяется), а для типичной VN-сцены с одним диалоговым окном случай не
возникает.

Тест — на чистом seam `ApplyConfirmedFrameGates`, как `CanReuseCachedRecognition`
рядом и `PlanScalingCommand` в B6: путь целиком требует живого NPU OCR. Красноту
проверял обратным порядком — временно вернул pass-through и получил
`A cached frame reported a clipped sentence as stable phrase context`, после чего
восстановил правку.

*D3* — ветка `colon` (`SpeakerMetadataParser.cs:95`) зовёт
`TryParseName(standalone: false)`, поэтому фильтр `StandaloneUiOrUtteranceWords`
не применяется, а любые до четырёх слов подряд проходят как имя. Воспроизведено:

```
'Warning: Do not open the gate.'       -> speaker='Warning'
'Note: the bank is closed today.'      -> speaker='Note'
'Mom always said: never trust a…'      -> speaker='Mom always said'
'The doctor said: your arm is broken.' -> speaker='The doctor said'
```

Это **не** повтор наблюдения C7: там разбиралась ветка по `\r\n`, недостижимая
на OCR-пути, и воспроизвести её не удалось. Эта ветка воспроизводится
детерминированно и без живого прогона, то есть C7 следует считать закрытым
наблюдением, а D3 — отдельным подтверждённым дефектом.

**Формулировка вреда исправлена при проверке.** Исходная карточка утверждала, что
во всех четырёх случаях «голова предложения теряется до отправки в
TranslateGemma». Прогон по таблице случаев показал, что это верно только для
половины, и половины разной по тяжести:

- **Reporting clause** (`Mom always said:`, `The doctor said:`, `My friend told
  me:`, `A voice whispered:`) — настоящий дефект перевода. Отрезается не метка,
  а часть самой реплики: `never trust a stranger.` теряет и атрибуцию, и
  прошедшее обрамление, а «говорящим» становится целое придаточное.
- **Annotation label** (`Warning:`, `Note:`, `Tip:`) — в CURRENT уходит ровно
  содержимое (`Do not open the gate.`), то есть перевод не страдает. Вред здесь
  только в засорении: в per-game хранилище появляется говорящий `Warning`, имя
  видно на карточке, и редактор рода предлагает назначить ему род.

То есть P2 заслуживает первая группа, вторая — гигиена. Обе закрыты одной
правкой, но severity в карточке была завышена для трёх случаев из семи.

**Выполнено (16 августа 2026).** Корень — не сама ветка `colon`, а параметр
`standalone` у `TryParseName`: он делал фильтр UI-слов свойством *способа
разметки*, хотя это свойство *слова*. Двоеточие не является доказательством
нашлёпки с именем. Параметр удалён целиком (других применений у него не было),
`StandaloneUiOrUtteranceWords` переименован в `UiOrUtteranceWords`, применяется
во всех трёх ветках и дополнен аннотационными метками.

Против reporting clause добавлен `LooksLikeReportingClause`: ведущий детерминатив
или притяжательное из `EnglishContextLexicon.Determiners`/`Possessives`, либо
любой токен из закрытого набора `AttributionVerbs`. Прежний код уже отклонял
`I said:` через `NonSpeakerLeadingWords` — то же намерение, но покрытое только
для местоимённого подлежащего; правка обобщает его на полную именную группу.

`AttributionVerbs` намеренно **уже**, чем `EnglishContextLexicon.ComplementTakingVerbs`:
там лежат базовые формы `hope`, `feel`, `guess`, а `Hope` — человеческое имя.
В набор входят только финитные формы, которые не могут возглавлять английское
имя. Тест закрепляет это отдельно: `Hope:`, `Will:`, `May:`, `Grace:` обязаны
остаться говорящими, хотя `will` и `may` лежат в `Modals`, а `hope` — в
`ComplementTakingVerbs`. По той же причине набор не строится по суффиксу.

Тесты в `SmartPhraseTranslationFoundationTests`: четыре reporting clause, три
аннотационные метки, standalone-нашлёпка `Warning` и четыре имени, совпадающих
со служебными словами.

*D4* — `Program.cs:656`, `managedSenseBytes < 128 МБ`. Из семи прогонов подряд
шесть дали **71,9 МБ** (повторяемо до десятой доли), один — **146,8 МБ** и
`FAIL`. Состав индекса при этом каждый раз идентичен (147 841 ключ /
446 863 кандидата), то есть ассерт меряет поведение GC, а не контракт кода.
`AGENTS.md` предписывает гонять набор после каждого изменения — гейт с ~15 %
ложных отказов это правило подрывает. Exit code корректен (`return 1`), ложного
зелёного нет: это ровно обратная C1 ошибка — не молчаливый `PASS`, а шумный
`FAIL`.

**Гипотеза о механизме не подтвердилась.** Предполагалось, что виноват
best-effort характер `GC.GetTotalMemory(true)`: документация обещает лишь
«подождать короткий интервал», поэтому под нагрузкой вызов мог вернуться до
завершения gen2 и посчитать мусор живым. Проверка это опровергла. Probe мерил
одно и то же двумя способами — обычным вызовом и серией блокирующих
compacting-сборок до стабилизации — в двух сценариях: (а) сразу после
намеренного создания сотен мегабайт короткоживущего мусора, (б) на реальной
загрузке словарей и sense-индекса. Во всех трёх прогонах оба способа дали
**побайтово одинаковые** числа: 176,0 МБ и 71,9 МБ, расхождение 0,0 МБ.
То есть в чистом процессе `GetTotalMemory(true)` мусор не недосчитывает, и
настоящий механизм выброса остался неизвестен.

**Выполнено (16 августа 2026).** Раз механизм неизвестен, правка сознательно
построена так, чтобы от знания механизма не зависеть. Два изменения:

- `SettledManagedBytes` заменяет одиночную выборку серией блокирующих
  compacting-сборок до тех пор, пока число перестаёт падать. Это не
  подтверждённое лекарство, а приведение замера к детерминированной форме:
  меряется удержанный размер, а не мгновение.
- `AssertManagedBudget` **перемеряет** превышение перед тем, как уронить
  прогон. Это и есть та часть, которая работает независимо от причины: бюджет
  описывает то, что индекс удерживает, поэтому настоящая регрессия остаётся
  над порогом и на втором замере, а единичный аномальный сэмпл — нет.

Порог не поднимался: маскировать нечего. После правки числа те же (176,2 МБ и
71,9 МБ в пяти прогонах подряд), состав индекса тот же. Сообщение об отказе
теперь содержит измеренное значение, иначе будущий отказ пришлось бы
диагностировать по соседней печатной строке. Общее время набора ~31 с —
регламент «~1 минута» из `AGENTS.md` соблюдается.

Ограничение честно фиксируется: отсутствие редкого события пятью прогонами не
доказывается. Утверждать можно лишь то, что одиночный выброс больше не
приводит к отказу, а детерминированная регрессия — приводит.

*D5* — `WindowsAiOcrService.cs:1072`, приватный `FindClosestOccurrence` на голом
`IndexOf`, без проверки границ токена. Остальные семь вызовов в решении идут в
общий `RankerTargetAnchor.FindClosestOccurrence`, который вхождения внутри слов
отбрасывает. Слабый вариант стоит именно там, где `characterIndex` **рождается**:
`closestWord = "in"` может привязаться внутрь `waiting`, после чего
`LocalDictionaryService.FindClosestToken` (`:1740`) по containment вернёт
`waiting`. Дублирование здесь не отмечено как намеренное — в отличие от
правила 7 AGENTS.md про POS-инференс.

**Severity повышена при проверке — в обратную сторону от D3.** Карточка
утверждала, что «геометрическая оценка обычно перевешивает, поэтому это
латентный риск, а не наблюдаемый отказ». Это оказалось неверно, причём именно
из-за того, что оценка **неточна**: она предполагает равную ширину символов, а
на пропорциональном шрифте промахивается на несколько позиций — и промахивается
в сторону соседнего слова. Для `I am waiting in line` с курсором над настоящим
`in` оценка даёт 10, а прежний резолвер выбирал вхождение с ближайшей серединой
и возвращал **9** — внутрь `waiting`. То есть неточность оценки не защищала от
дефекта, а подводила прямо к нему. Это баг, а не гигиена.

**Выполнено (16 августа 2026).** Приватная копия удалена; расчёт вынесен в
`ResolveLineCharacterIndex` и зовёт общий `RankerTargetAnchor.FindClosestOccurrence`.
Поведение при отсутствии standalone-вхождения не менялось: остаётся прежняя
геометрическая оценка (например, `bank` внутри `embankment` анкером не
становится).

Порядок был обратный обычному и специально: сначала чистое вынесение seam с
**прежним телом**, затем тест — он дал красное `index 9 in 'I am waiting in
line'` — и только потом подмена резолвера. Так «падает до правки» проверено на
самом дефекте, а не на новом методе. Отдельно прогнан набор обычных наведений
(одиночное вхождение, начало и конец строки, повтор, длинное слово): индексы
не изменились.

**Проверено и подтверждено здоровым:** правило 6 (IPC) — `ExecuteTransactionAsync`
намеренно не отменяем после записи, ровно один `ReadLine`, stderr дренируется
отдельным `DrainErrorsAsync`, любая ошибка ведёт в `StopWorkerLocked`;
`SentenceBoundaryRules` (аббревиатуры, многоточия, пропуск целого пунктуационного
прогона в обе стороны); `MapAxis` в `VisibleCursorService` с защитой от деления
на ноль; согласованность DPI — манифест `PerMonitorV2` плюс `GetDpiForWindow` в
`ShowNear`, так что курсор, захват и оверлей живут в одних физических пикселях;
оверлей с `WS_EX_TRANSPARENT` не попадает в кадр, потому что смена якоря вызывает
`HideOverlay` минимум за 350 мс до `CopyFromScreen`; `Normalize` сохраняет длину
строки (репейр `I'll` — 3 символа в 3), поэтому посчитанные до него индексы
остаются валидными. Числа `ARCHITECTURE.md` сходятся с кодом до константы
(90 мс, радиус 15 px → `RadiusSquared = 225`, порог `0.25`, 2400×720). Дисциплина
сравнения строк соблюдена сплошь: в `src/` нет ни одного `ToLower()`/`ToUpper()`
без культуры, ни одного `string.Equals` без `StringComparison`, ни одного
`Dictionary<string,…>`/`HashSet<string>` без компаратора. В `src/` нет ни одного
`TODO`/`FIXME`; в индексе нет build-выхода и файлов свыше 12 МБ.

**Итог.** Все пять карточек закрыты. Как и в проходах 1–3, главный результат —
не скорость правок, а то, что **три находки из пяти изменили форму при
столкновении с данными, причём в разные стороны**:

- D3 — severity **завышена**: из семи воспроизведённых случаев текст теряют
  только четыре (reporting clause); у `Warning:`/`Note:` в модель уходило ровно
  содержимое, там вред только в засорении хранилища говорящих.
- D5 — severity **занижена**: карточка называла это гигиеной, полагаясь на то,
  что «геометрическая оценка обычно перевешивает». Оценка как раз промахивается
  на пропорциональном шрифте — и промахивается в сторону соседнего слова, то
  есть подводит к дефекту, а не защищает от него. Это баг.
- D4 — гипотеза о механизме **опровергнута** замером и остаётся неизвестной;
  правка построена так, чтобы от знания механизма не зависеть.

Две карточки вскрыли вторую половину дефекта, не описанную в самой карточке:
у D1 неверен был и OCR-берег (в dictionary-режиме туда приходит целая строка, а
не предложение), у D2 кэш умел воскрешать подпись, которую гейт забраковал.
Обе нашлись только при реализации, а не при чтении.

Порождённое: `SentenceComparison` (D1) — общий примитив сравнения двух
наблюдений одной реплики, вынесенный вместо копирования.

**Пройденный порядок:** D1 → D3 → D2 → D5 → D4.

## A1. User-запись и scaffold-строка взаимно уничтожаются

**Мотивация.** При совпадении нормализованной поверхности оба кандидата
выбрасываются, и обязательного термина не остаётся вообще — прямо
противоположно намерению, записанному в комментарии
`TranslationScaffold.cs:322-326` («A user entry owns its source span even when
its multiple meanings cannot be reduced to one mandatory translation»).

Механика в `TranslationScaffoldBuilder.BuildAsync`:

1. Строка 410 — кандидат от пользовательской записи отбрасывается, потому что
   `explicitScaffoldSources` уже содержит его `sourceKey`.
2. Строки 444–448 — scaffold-кандидат отбрасывается, потому что его span
   пересекает `userEntrySpans`.

Защита на строках 251–258 (`IsUserEnglishKey(sourceKey) ||
IsUserEnglishKey(match.MatchedEnglishKey)`) закрывает только точное совпадение
ключей. Случай «лемма против словоформы» протекает: user-словарь содержит
`run`, scaffold-слой — `running`, в тексте `running`. Lookup через
`preferredLemmaCandidates` вернёт `MatchedEnglishKey = "run"`, но
`lookup.Source = "running"` → `sourceKey = "running"` → коллизия.

Сегодня узко (scaffold-слой — 21 строка), но растёт вместе с №14.1 «VN Layer
2.0 — безопасное расширение». Тестов на это взаимодействие нет: в `tests/` нет
ни одного упоминания `explicitScaffold` / `userEntrySpans`.

**Архитектура.** Не применять фильтр `explicitScaffoldSources` к кандидату,
который сам происходит из пользовательской записи
(`matchedUserEntry || explicitUserToken`). Пользовательский слой авторитетен по
контракту приоритета слоёв; scaffold-якорь его перекрывать не может ни прямо,
ни через побочный эффект дедупликации.

**Инварианты.** Приоритет слоёв (правило 10 AGENTS.md) — пользовательский слой
остаётся выше scaffold-only. Fail-open построения каркаса не меняется.

**Definition of Done.** Тест в `tests/AsteriaScale.Tests`, падающий до фикса:
временный bundled scaffold-слой со словоформой + пользовательская запись с
леммой → каркас содержит обязательный термин из пользовательского слоя. Полный
smoke-набор зелёный.

## A2. `ScaffoldSenseHint` собираются без лимита

**Мотивация.** `MaximumTermCount = 12` и `MaximumNeuralRequestCount = 12`
ограничивают термины и запросы, но `SenseHints` берутся целиком
(`TranslationScaffold.cs:505`). При 12 нейро-запросах × `.Take(2)` гипотез это
до 24 строк по ≤320 символов — около 7.7 КБ, которые целиком уходят в
`BuildSenseReviewPrompt` и в ключ финального кэша `CreateTranslationCacheKey`.

Для 2B-модели блок гипотез такого размера начинает доминировать над самой
задачей review; кроме того, каждая лишняя гипотеза дробит ключ кэша и снижает
его попадаемость.

**Архитектура.** Ввести `MaximumSenseHintCount`, симметричный
`MaximumTermCount`. Отбор обязан быть детерминированным и стабильным —
по порядку появления в реплике (тот же принцип, что у `TermPriority` →
`CharacterIndex`), а не по margin: margin приходит из модели, и сортировка по
нему сделала бы состав каркаса зависимым от провайдера.

**Инварианты.** Правило 2 (GroupId == индекс) не затрагивается: hint не несёт
GroupId. Воздержание по-прежнему не создаёт hint.

**Definition of Done.** Тест: реплика, дающая больше лимита hint-ов, отдаёт
ровно `MaximumSenseHintCount` в стабильном порядке. Smoke-набор зелёный.

## A3. Сужение контекста в ключе hover-кэша не описано

**Мотивация.** `SmartDictionaryResultCache.CreateLocalContextWindow` режет
контекст до ±5 слов / 384 символов, а в GlossBERT уходит **полный**
`recognized.Text`. Две разные реплики с одинаковым ближайшим окружением
целевого слова получат один кэшированный смысл, хотя модель на них ответила бы
по-разному.

Для WSD ±5 слов — обычно доминирующий сигнал, так что как компромисс это
защитимо. Но это единственное недокументированное приближение в компоненте, где
всё остальное описано до последнего инварианта: `ARCHITECTURE.md` говорит про
кэш только «persistent LRU; ключи SHA-256, исходный текст на диск не пишется».

**Архитектура.** Абзац в `ARCHITECTURE.md` (раздел «Конвейер hover-перевода»,
пункт про `SmartDictionaryResultCache`): ключ намеренно уже входа модели, radius
зафиксирован, следствие — возможное переиспользование решения между репликами
с общим окружением.

**Definition of Done.** Абзац в `ARCHITECTURE.md`. Кода не касается.

### Снято приближение, а не только описано (25 июля 2026)

Абзац был написан, а затем **устарел**: продуктовая карточка №14.2B закрыла сам
размен. `TargetCenteredContextBuilder` строит одно окно и для ключа, и для
входа воркера, поэтому ключ больше не уже того, что видит модель, и две реплики
с общим ближайшим окружением не переиспользуют решение друг друга. «Далёкий»
контекст теперь определяется token budget, а не радиусом ±5 слов. Описание в
`ARCHITECTURE.md` заменено на актуальное — документировать снятое ограничение
как действующее было бы хуже, чем не документировать вовсе.

## A4. Два независимых кэша над одним решением GlossBERT

**Мотивация.** Оба пути вызывают один и тот же метод с одинаковой семантикой:

| | hover Smart | full-text scaffold |
|---|---|---|
| вызов | `SmartHoverPipeline.cs:347` | `TranslationScaffoldGlossBertRanker.cs:87` |
| аргументы | `(text, source, charIndex, plan.CandidateGlosses, plan.CandidateGroupIds, "English", provider)` | те же |
| план | `GroupCandidates` → `CreateRankerPlan` | те же функции, те же аргументы |
| кэш | `SmartDictionaryResultCache` — **диск**, 4096 записей | `_cache` — **память**, 512 записей |
| ключ | окно ±5 слов + видимые русские переводы | предложение + glosses + GroupId + SourceIndex |

Следствия:

- Наведение на слово и последующий полный перевод той же реплики гоняют
  воркер дважды. Инференс — самая дорогая часть конвейера.
- Кэш каркаса не переживает перезапуск: повторный проход по сцене в
  `Screen`-режиме каждый раз считает заново.
- Ключи разной точности. Каркасный соответствует фактическому входу воркера;
  hover-ключ — lossy-прокси (см. A3).

**Архитектура.** Новый `GlossBertDecisionCache`, ключуемый по тому, что
действительно уходит в воркер: provider + model identity + версия протокола +
`LocalDictionaryService.VersionToken` + предложение + target + characterIndex +
glosses + GroupIds. Персистентный, по образцу `SmartDictionaryResultCache`
(SHA-256 ключи, атомарная запись, debounce, LRU). Подключить обе точки вызова.
`SmartDictionaryResultCache` остаётся сверху как дешёвый слой попаданий по окну
контекста — его не удалять, чтобы не терять уже накопленные кэши пользователей.

**Инварианты.** Правило 3 (никакого тихого fallback провайдера): попадание в
кэш пропускает инференс, но **не** валидацию провайдера/модели — warm-up и
`ValidateResponse` остаются до чтения кэша, как уже сделано в
`TranslationScaffoldGlossBertRanker.RankAsync:61-72`. Правило 2 (GroupId ==
индекс): в ключ входят и outcomes, и `CandidateGroupIds`. Кэшируются принятые
решения и воздержания; ошибки — никогда.

**Definition of Done.** Тесты: попадание после hover переиспользуется каркасом
и наоборот; смена `VersionToken` инвалидирует; смена провайдера инвалидирует;
воздержание кэшируется, ошибка — нет. Smoke-набор зелёный. Замер: второй проход
по той же сцене не вызывает воркер.

### Выполнено

- `GlossBertDecisionCache` — персистентный LRU (4096 записей, бюджет 4 МБ,
  атомарная запись, debounce 650 мс, SHA-256 ключи). Подключён к обоим
  потребителям; `TranslationScaffoldGlossBertRanker` лишился приватного
  in-memory словаря.
- **Канонизация `characterIndex`.** Без неё обмен не заработал бы вообще: hover
  передаёт позицию курсора, каркас — начало токена, и ключи никогда не
  совпали бы. Индекс приводится к началу вхождения цели **той же функцией, что
  использует воркер**: `FindClosestTargetOccurrence` вынесена из
  `AsteriaScale.RankerWorker` в общую `AsteriaScale.RankerProtocol` как
  `RankerTargetAnchor`. Копия на стороне хоста была бы хуже дублирования: она
  могла бы разойтись с воркером на одно вхождение и отдать решение для якоря,
  который воркер не оценивал. `RankerSelectionLogic` теперь делегирует туда же,
  тесты воркера не менялись.
- **Найден и устранён дефект в самой правке.** Первая версия передавала в ключ
  разные строки версии словаря: hover — `VersionToken + SmartRankingPipelineVersion`,
  каркас — только `VersionToken`. Оба пути работали бы, но молча перестали бы
  делиться решениями — регрессия без единого видимого симптома, кроме удвоенного
  инференса. Эпоха `SenseRankingEpoch` определена **один раз** в
  `GlossBertDecisionCache` и вкладывается в отпечаток самой функцией, так что
  вызывающая сторона не может её забыть. Тест
  `VerifyScaffoldAndHoverAgree` сравнивает ключи обоих путей напрямую.
- Бенчмарк перевода получает изолированный кэш во временном каталоге: тёплый
  кэш подменял бы измеряемый ранжировщик.
- Новый smoke-блок «Shared GlossBERT decision cache» (39 тестов в наборе).

- **Второй дефект, найденный уже после коммита A4 (A10).** Порог воздержания
  жил как `private const` в воркере и не входил ни в один ключ кэша. Смена
  модели безопасна (идентичность модели в ключе есть), а вот перекалибровка
  порога без смены модели — нет. До A4 урон был ограничен: hover-кэш хранил
  только принятые решения, а кэш каркаса жил в памяти. A4 сделал **воздержания
  персистентными на обоих путях**, то есть снижение порога продолжало бы
  отдавать старые воздержания с диска — ровно ту метрику, ради которой
  затевается №8 продуктового роадмапа («уменьшить долю воздержаний минимум на
  20 %»). Исправлено: `RankerAbstention.MarginThreshold` вынесен в общую
  protocol-сборку, воркер берёт константу оттуда, `CacheTag` входит в ключи
  обоих кэшей. Тест `VerifyAbstentionThresholdIsKeyed` падает без этого.

**Порождённая задача:** A9.

## A9. Выделить общий примитив персистентного LRU

**Мотивация.** Порождена A4. `SmartDictionaryResultCache` и
`GlossBertDecisionCache` содержат почти одинаковую машинерию хранения:
`EnsureLoadedLockedAsync`, debounce-планировщик, атомарная запись через
временный файл с `_lastCommittedVersion`, бюджет размера, LRU-вытеснение,
`DisposeAsync`, который намеренно не освобождает семафор. Это ~250 строк,
скопированных осознанно: извлекать общий базовый класс одновременно с
подключением нового кэша означало бы менять протестированный компонент
hover-критического пути в том же изменении.

Долг зафиксирован здесь, чтобы не выглядеть недосмотром: аудит, чья главная
находка — дублирование, не должен молча добавлять ещё одно.

**Архитектура.** Внутренний `PersistentLruStore<TEntry>` с контрактом
«запись знает свой ключ и `LastAccess`», параметрами ёмкости/бюджета/пути и
делегатом структурной валидации. Специфика остаётся у потребителей:
ревалидация кандидатов у `SmartDictionaryResultCache`, проверка адресуемости
`GroupId` у `GlossBertDecisionCache`.

**Инварианты.** Формат файлов и имена ключей не меняются: уже накопленные
пользовательские кэши обязаны читаться после обновления.

**Definition of Done.** Оба кэша используют общий примитив;
`SmartDictionaryResultCacheTests` и `GlossBertDecisionCacheTests` зелёные без
правок ожиданий; ручная проверка, что существующий
`smart-dictionary-cache.v2.json` читается.

### Выполнено (26 июля 2026)

`PersistentLruStore<TEntry>` держит загрузку, debounce, атомарную замену через
временный файл, бюджет размера, вытеснение и disposal. Доступ к записям выдаётся
через `UseAsync(access => …)` — колбэк выполняется под уже взятым gate, поэтому
потребителю не приходится повторять блокировки, а вытеснение и планирование
записи происходят автоматически, если колбэк вызвал `MarkDirty()`.

Специфика осталась у потребителей, как и планировалось: ревалидация кандидатов
и сдвиг индексов у `SmartDictionaryResultCache`, проверка адресуемости
`GroupId` у `GlossBertDecisionCache`.

**Формат на диске не менялся.** Документ по-прежнему сериализуется как
`{"version": N, "entries": [...]}` с собственным типом записи владельца, а
`JsonSerializerDefaults.Web` даёт те же camelCase-имена полей. Проверено на
**реальном накопленном кэше пользователя**: 27 931 байт, 131 запись — все
прочитаны через новый примитив. Проверка выполнялась на копии, оригинал не
трогался (чтение помечает LRU и запланировало бы запись).

Итог по объёму: `SmartDictionaryResultCache` 822 → 378 строк,
`GlossBertDecisionCache` 704 → 321, общий примитив 500. Дублирование ~250 строк
устранено.

## A6. Четыре несогласованных лимита на одном значении

**Мотивация.** `MaximumMergedMeaningCount = 32` → `MaximumMergedValueLength =
4096` → `Limit()` = 380 символов → `SplitMeanings().Take(8)`.

Комментарий у констант (`LocalDictionaryService.cs:44`) утверждает: «The merged
value only feeds a 380-character tooltip and an eight-candidate SplitMeanings
ranking, so a deeper tail is dead weight» — и тут же ставит 32 и 4096, оба
заметно выше того, что может всплыть.

Измерено по реальным `eng-rus*.tsv.gz`: 2692 ключа (1.5 %) имеют слитое
значение > 380 символов; экономия памяти от выравнивания — ~1 МБ. **Это не про
память.** Это про то, что у 1.5 % самых многозначных слов — ровно тех, где
выбор смысла важнее всего — хвост значений молча обрезается и не доходит до
`SplitMeanings`. Пересекается с №1 «Покрытие sense-sidecar»: где sidecar
покрывает ключ, потери нет; где не покрывает — есть.

**Архитектура.** Свести merge-лимит к тому, что реально всплывает, и записать в
`ARCHITECTURE.md`, что при переполнении теряются значения **низкоприоритетных**
слоёв (сейчас это верно по построению порядка слияния, но нигде не
зафиксировано). Порядок слияния (правило 10) не менять.

**Definition of Done.** Константы и комментарий согласованы; тест на то, что
при переполнении первым выживает значение более приоритетного слоя;
`ARCHITECTURE.md` дополнен. Smoke-набор зелёный.

### Выполнено — с поправкой к исходному выводу

Первоначальное предложение «свести merge-лимит к тому, что реально всплывает»
оказалось **неверным**. Если бюджет слияния равен потолку показа, `Limit`
никогда не обрезает значение и никогда не дописывает «…», и урезанный список
выглядит для пользователя полным. Запас над потолком — это не забытая память,
а то, что делает сигнал «есть ещё» честным.

Поэтому:

- значения констант оставлены как есть; переписан **комментарий**, который им
  противоречил и утверждал, будто хвост — мёртвый груз;
- магическое `380`/`377` заменено на `MaximumDisplayedValueLength` и явное
  резервирование трёх символов под «; …»;
- добавлен тест, закрепляющий сам инвариант («бюджет слияния строго больше
  потолка показа»), чтобы расхождение не вернулось;
- в `ARCHITECTURE.md` записано, что при переполнении теряется хвост —
  значения самых низкоприоритетных слоёв — и что для ~1.5 % ключей это
  компенсирует sense-sidecar (роадмап №1).

Экономия памяти не преследовалась: замер дал ~1 МБ.

## A7. Лестница разрешения смысла продублирована

**Мотивация.** Последовательность `GroupCandidates` → `CreateRankerPlan` →
`TrySelectFromContextTranslation` → `TrySelect` → GlossBERT реализована
независимо в `SmartHoverPipeline.ResolveSmartHoverAsync` и в
`TranslationScaffoldBuilder.SelectTranslation`, с разными порогами приёма
(hover — любая уверенность, каркас — ≥ 0.95).

Правило 7 AGENTS.md («POS-инференс раздельный намеренно») сюда **не
относится**: оно про `SmartDictionaryHeuristicRanker` против
`SmartDictionarySenseResolver`. Здесь дублируется не лингвистика, а порядок
шагов. Риск: изменение лестницы в одном месте молча не применяется во втором.

**Архитектура.** Общий модуль построения плана и детерминированных шагов с
параметром «порог приёма»; различие между потребителями сводится к нему и к
тому, что делать с отказом (hover показывает карточку вариантов, каркас
запрашивает нейро-подсказку).

**Инварианты.** Правило 2 (три согласованные нормализации) — унификация обязана
их сохранить, а не добавить четвёртую. Правило 7 — не сливать `TrySelect` и
`GroupCandidates`.

**Definition of Done.** Оба потребителя используют один модуль; существующие
тесты hover и каркаса зелёные без правок ожиданий; `--ranker-benchmark` без
деградации.

### Выполнено — в пересмотренном объёме

Разбор показал, что исходное предложение («общий модуль с параметром порога
приёма») сделало бы код **хуже**. Совпадает только порядок трёх вызовов;
всё остальное — действительно разная политика:

| | hover | каркас |
|---|---|---|
| нормализация исходов | нет | `NormalizeRussianTerm` (режет латиницу, > 160 символов) |
| порог приёма эвристики | любая уверенность | ≥ 0.95 |
| единственный исход | уверенность 1 | 1 или 0.85 по авторитетности слоя |
| отказ означает | показать карточку вариантов | запросить нейро-подсказку |

Абстракция с четырьмя политическими рычагами на двух потребителей сложнее
дублирования, которое она убирает. Параметризованная лестница отвергнута.

Реализована та часть, где риск расхождения настоящий: **пара построения плана**.
Оба продакшн-пути всегда вызывали `GroupCandidates` и `CreateRankerPlan` подряд
с одними и теми же тремя аргументами и использовали из инвентаря только
`Groups` — `InferredPartOfSpeech` и `PartOfSpeechFilterApplied` читают
исключительно тесты. Половина пары, применённая с другими аргументами, даёт
план, чьи GroupId больше не описывают ранжируемые смыслы (инвариант 2), — это
не то, что вызывающая сторона должна иметь возможность сделать наполовину.
Добавлена перегрузка `CreateRankerPlan(context, target, characterIndex,
candidates)`, выполняющая обе стадии; двухстадийная форма осталась публичной
для тестов POS-инференса.

Правило 7 AGENTS.md не затронуто: `SmartDictionaryHeuristicRanker` и
`SmartDictionarySenseResolver` не сближались.

**Подтверждение.** `--ranker-benchmark` на dev-наборе (65 случаев, CPU) дал
результат, тождественный зафиксированному в RESEARCH.md baseline по всем
решениям: `ranked=45`, `phrase-bypass=16`, `auto-resolved=3`, `no-inventory=1`,
покрытие `37/45`, `decided=21 correct=21`, `abstained=16`,
`medianMargin=0,305`, end-to-end `33/65`. Frozen holdout не открывался.

## A8. Квадратичность `TranslationScaffoldBuilder`

**Мотивация.** Замерено: полный `BuildAsync` — 4.0–6.5 мс, из которых ~80 % —
N повторов `LookupWithSenseMetadataAsync` (0.2 мс × 16 токенов ≈ 3.2 мс).
Каждый вызов заново токенизирует **всё** предложение регэкспом, заново считает
`NormalizeEnglishSentenceKey` и заново прогоняет фразовый поиск окном до 10
токенов (~100 конструирований ключа с `NormalizeEnglish` на каждый).

На дату аудита это **не** было узким местом: тогдашний Qwen был дороже на порядки. Но это ровно тот
множитель, в который упрётся №17 «Экранный конвейер 2.0», и он же стоит за
мотивацией №7 («сделать каркас дешёвым для пакетных сценариев»).

**Архитектура.**

1. `LookupContext` (токены + sentence key), вычисляемый один раз на предложение
   и прокидываемый в `LookupEnglish`; публичный API `LookupAsync` /
   `LookupWithSenseMetadataAsync` сохраняется как обёртка, создающая контекст
   на один вызов.
2. `FoldEnglishCase` заканчивается `new string(expanded.Select(
   char.ToLowerInvariant).ToArray())` (`LocalDictionaryService.cs:1676`) — LINQ
   по `char` на самом горячем пути в проекте, вызывается десятки тысяч раз на
   реплику. `string.Create` или цикл по `Span<char>` убирают промежуточный
   массив и энумератор без изменения семантики.

**Инварианты.** Правило 1 (каноническая форма ключей) — самое опасное место:
нормализация обязана остаться **побайтно** тождественной, иначе рассинхрон с
`build-dictionaries.py`. Любая правка `FoldEnglishCase` / `NormalizeEnglish`
проверяется `scripts/dictionary-normalization-contract.tsv` и
`LocalDictionaryNormalizationTests`.

**Definition of Done.** `BuildAsync` на 16-токенной реплике ≥ 2× быстрее при
идентичном составе каркаса; `LocalDictionaryNormalizationTests` и контракт
нормализации зелёные без правок ожиданий; smoke-набор зелёный.

### Выполнено — с исправлением диагноза (26 июля 2026)

**Атрибуция в мотивации была неверной.** Карточка утверждала, что ~80 %
времени — повторная токенизация и пересчёт sentence key. Реализация ровно
этого дала **7 %** (`3,94 → 3,66 мс`). Верна была лишь половина: lookup-и
действительно составляют ~80 % `BuildAsync`, но внутри lookup-а доминирует
**фразовый поиск** — цикл по длинам 10…2, где на каждую пару `(start, length)`
заново нормализуются те же токены и заново строятся те же леммы.

| Правка | Накопленный результат |
|---|---|
| `EnglishLookupContext` (токены + sentence key) | `3,94 → 3,66` (1,08×) |
| Кэш нормализованных токенов в контексте | `3,66 → 2,54` (1,55×) |
| Кэш лемм на реплику (`LemmasFor`) | `3,66 → 2,05` (**1,92×**) |

`FoldEnglishCase` дополнительно получил ASCII-fast-path (все расширяющие
свёртки не-ASCII, поэтому обычный текст не нуждается ни в одном из
двенадцати `Replace`) и `string.Create` вместо LINQ по `char`.

**DoD выполнен по букве, но не равномерно.** На 16-токенных репликах
`4,21 → 2,07` (2,03×) и `5,17 → 2,58` (2,00×). На 14-токенной — 1,50×, на
7-токенной — 4,4×. Разброс закономерен: ширина фразового окна зависит от
позиции цели.

**Методика замера пересмотрена.** Первые два прогона показали «ухудшение»
(`5,41` и `6,28 мс`), потому что среднее по одному батчу гуляло на 20 % между
идентичными сборками — больше измеряемого эффекта. Стенд переведён на
**минимум из 15 батчей**, база пересобрана тем же методом через `git stash`.
Без этого напрашивался вывод «правка не работает».

**Проверка неизменности.** `--register-benchmark` на 135 случаях дал побитово
те же числа: `decided=65`, `abstained=70`, `unresolved=0`, `92,3 % / 98,5 % /
86,2 %` и совпадение по всем четырём корзинам. Контракт нормализации и 16
тестов генератора зелёные без правок ожиданий.
