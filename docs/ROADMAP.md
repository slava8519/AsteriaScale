## 0. Новый замороженный holdout-v3

**Мотивация.** `ranker-holdout.json` и `ranker-holdout-v2.json` уже открывались
(v2 — дважды: релиз 0.9.3 и подтверждение снятия batch-лимита). Любая работа над
моделью (№1, 7, 8, 9) требует свежего слепого набора, созданного **до** начала
экспериментов.

**Архитектура.** Новый файл `assets/Ranker/ranker-holdout-v3.json` по схеме v2
(`context`, `target`, `characterIndex`, `candidates`, `expectedTranslation`,
`partOfSpeech`, `senseClass`): 40–60 оригинальных CC0-случаев. Обязательные
классы: междометия, переносные значения, разговорные формы (самые частые
промахи покрытия v2), плюс случаи с инвентарём > 20 глоссов. Автор набора не
должен видеть текущие ошибки модели — генерировать случаи из описаний классов,
а не из логов.

**Валидация.** Схема-валидация (`context.Substring(characterIndex,
target.Length) == target`), проверка «каждый target есть в словаре» через
smoke-тест. Файл после создания не открывается до финального подтверждения
очередной модели; каждое открытие фиксируется в RESEARCH.md.

## 1. Покрытие sense-sidecar

**Мотивация.** На holdout-v2 12 случаев из 30 имели метку, не покрытую
sense-инвентарём (`expected-not-covered` в `--ranker-benchmark`) — модель не
могла ответить правильно в принципе. Потолок качества сейчас в данных.

**Архитектура.** Правки только в `scripts/build-dictionaries.py` (секция
`eng-rus-enwiktionary-senses`) + регенерация:

1. **Больше поверхностей на смысл**: сейчас смысл получает только переводы из
   своего translation-box. Добавить выравнивание переводов ru-Wiktionary
   (kaikki-русский слой) к смыслам en-Wiktionary по схожести определений
   (нормализованный token-overlap ≥ 0.5 — консервативно, при сомнении не
   добавлять). Помечать источник поверхности пятым полем не нужно — формат
   TSV сохраняется.
2. **Междометия и разговорные смыслы**: en-Wiktionary содержит их как senses с
   `pos=intj` и тегами colloquial — сейчас часть отфильтровывается, потому что
   у них пустые translation-boxes. Для них брать русские соответствия из
   ru-Wiktionary статьи того же слова с `pos=intj`.
3. **Метрика покрытия в harness**: в `RankerCalibrationBenchmark` уже считается
   `labeled`; добавить в сводку явный процент покрытия и вывести его в отчёте.

**Инварианты.** №1 (канонические ключи — использовать `normalize_english`),
формат sidecar (5 колонок), лимит 128 смыслов/ключ.

**Definition of Done.** Покрытие меток на dev-наборе и holdout-v2 выросло
(цель: ≥ 24/30 на v2 против нынешних 18/30); dev-точность принятых решений не
упала (`--ranker-benchmark`, cpu и npu); smoke-набор зелёный; размер sidecar
< 12 МБ gz; числа занесены в RESEARCH.md.

## 2. Морфословарь русского (OpenCorpora)

**Мотивация.** Суффиксная морфология — самый хрупкий слой (аудит нашёл в ней
несколько багов). Ложные срабатывания вида «масло → прош. время ср.р.»
подавляются паранойей (`ValidatePastParadigms`), которая заодно отбрасывает и
верные случаи.

**Архитектура.**

- Новый build-скрипт `scripts/build-ru-morphology.py`: из дампа OpenCorpora
  (CC BY-SA) собирает компактный DAWG «словоформа → (лемма-id, POS, род/число/
  время/вид)» только для нужных категорий (глагол, сущ., прил., нареч., межд.).
  Выход: `assets/Morphology/ru-morph.dawg` (~8–15 МБ) + лицензия в
  THIRD_PARTY_NOTICES.md.
- Новый сервис `src/AsteriaScale/Services/RussianMorphologyLexicon.cs`:
  ленивая загрузка DAWG, lookup по словоформе. `RussianMorphology` становится
  фасадом: сначала лексикон, при отсутствии слова — текущие суффиксные правила
  (fallback обязателен: словарь не полон).
- Потребители не меняют сигнатур: `DetectPastForm`, `IsInfinitive`,
  `IsSemelfactiveInfinitive` внутри переключаются на лексикон. Вид глагола
  (сов./несов.) брать из грамем вместо эвристики «-нуть».

**Инварианты.** Поведение при отсутствии данных = сегодняшнее (fallback);
никакой сети в рантайме.

**Definition of Done.** Существующие smoke-блоки морфологии зелёные без правок
ожиданий; новые тесты: словарная форма, которой нет в суффиксных правилах
(«шёл» → прош. м.р. от «идти»), и слово вне словаря (fallback). Прогон
`--ranker-benchmark` (морфология влияет на `SelectSurfaceForm`) без деградации.

## 4. Интеграция text-hook (Textractor)

**Мотивация.** Для совместимых движков hook даёт идеальный текст без OCR-ошибок
и задержки распознавания. Крупнейший доступный скачок качества перевода.

**Архитектура.** Textractor — GPLv3, поэтому строго отдельный процесс (та же
модель изоляции, что и с Magpie):

- Новый интерфейс `ITextSource` (`src/AsteriaScale/Services/TextSources/`):
  `Task<HoverText?> GetTextAtAsync(Point cursor, CancellationToken)` +
  `event SentenceArrived`. Текущий OCR оборачивается в `OcrTextSource`
  (адаптер над `WindowsAiOcrService`, поведение 1:1).
- `TextractorTextSource`: запускает `TextractorCLI.exe` (x86 и x64 — старые VN
  32-битные) как дочерний процесс, командует attach к PID активного профиля
  автоматизации, читает поток предложений из stdout-пайпа. Держит кольцевой
  буфер последних N предложений с таймстампами.
- Маршрутизация в `HoverTranslationService`: если для процесса включён hook и
  свежее (< 5 c) предложение есть — использовать его как контекст; позиция
  слова под курсором всё равно берётся из лёгкого OCR-прохода (слово + индекс),
  а контекст — из hook. Полный fallback на OCR при любом сбое.
- Настройки: `AppSettings.TextHookEnabled`, путь к Textractor, per-profile
  флаг. UI: чекбокс в профиле автоматизации + статус в главном окне.
- Экранный режим: hook-предложения переводятся пакетно без OCR-геометрии не
  получится — экранный режим остаётся OCR-only, это зафиксировать в README.

**Риски.** Hook = инъекция в процесс игры: антивирусные срабатывания, окна от
администратора. Отразить в README/ограничениях. Textractor не ставится
автоматически — только указанием пути, как Magpie.

**Definition of Done.** Тестовая VN (или notepad-эмуляция через clipboard-режим
Textractor) даёт hover-перевод без OCR; выключение/сбой hook незаметно
откатывает на OCR; smoke-тест на адаптер `ITextSource` с фейковым источником;
THIRD_PARTY_NOTICES.md дополнен.

## 5. Декомпозиция HoverTranslationService

**Мотивация.** 1400 строк, четыре режима, таймер, hotkeys, жизненный цикл
моделей и вся smart-логика в одном классе. Порог входа для любой правки высок.

**Архитектура.** Только перестановка кода, ноль поведенческих изменений:

- `HoverTracking` — таймер 90 мс, якорь, стабильность, cancellation (текущий
  `OnTimer`/`ResetTracking`).
- `IHoverMode` с реализациями `SmartHoverMode`, `DictionaryHoverMode`,
  `NeuralHoverMode`, `ScreenTranslationMode`; `ResolveSmartHoverAsync` и
  цепочка эвристик переезжают в `SmartHoverMode` как есть.
- `ModelLifecycleCoordinator` — QueueUnload/WarmUp/idle-таймеры.
- `HoverTranslationService` остаётся фасадом с прежним публичным API
  (используется MainWindow/треем) и роутит в активный режим.

Порядок: выделять по одному классу на PR-шаг, после каждого — полный smoke.
Тест «Dictionary key and sentence normalization» и smart-блоки не меняются.

**Definition of Done.** Файл < 400 строк; поведение подтверждено полным
smoke-набором и ручной проверкой всех четырёх режимов; новых публичных типов в
API приложения нет (всё internal).

## 6. Память словарей

**Мотивация.** Умный режим держит ~212 МБ словарей + ~79 МБ sense-метаданных
как .NET-строки (числа из smoke-лога). Для ноутбука рядом с игрой это много.

**Архитектура.** Два независимых шага, мерить после каждого:

1. **Дешёвый**: после загрузки конвертировать словари в
   `FrozenDictionary<string, byte[]>` с UTF-8-значениями; декодировать значение
   только при показе (`Found`). Ключи остаются строками (нужны для lookup).
   Ожидание: −30–40 % на значениях (они длиннее ключей, а UTF-8 для кириллицы
   вдвое компактнее UTF-16 не будет — честно: ~равно; выигрыш в основном от
   отсутствия object-заголовков на строку → замерить и оставить только если
   ≥ 15 %).
2. **Основной**: офлайн-компиляция словарей в бинарный формат — отсортированный
   массив ключей (UTF-8, front-coding) + offset-таблица значений в одном
   memory-mapped файле `Dictionaries/eng-rus.bin`. Новый
   `scripts/build-dictionaries.py --binary` эмитит его рядом с TSV (TSV
   остаётся источником правды и форматом пользовательских словарей).
   `LocalDictionaryService` при старте: bundled-слои из .bin (mmap, бинарный
   поиск), пользовательские TSV — поверх, в обычный словарь. Sense-метаданные —
   тот же формат, ленивый.

**Инварианты.** №1 (канонизация ключей выполняется при **компиляции** .bin —
зафиксировать версию нормализации в заголовке файла и сверять с
`SmartRankingPipelineVersion`-подобным токеном); приоритет слоёв не меняется.

**Definition of Done.** Smoke-лог показывает ≤ 120 МБ на словари+senses; тест
загрузки .bin + переопределения пользовательским TSV; время загрузки не хуже
текущих ~2.5 с; VersionToken учитывает .bin-файлы.

## 7. Bi-энкодер: предвычисленные эмбеддинги глоссов

**Мотивация.** Кросс-энкодер скорит каждую пару (контекст, глосс) отдельно —
латентность растёт с числом смыслов, NPU-батчи фиксированы. Bi-энкодер с
офлайн-эмбеддингами глоссов делает стоимость ранжирования ~нулевой и открывает
дорогу №9 (мультиязычный контекст).

**Архитектура.**

- **Офлайн** (`tools/build-gloss-embeddings.py`): компактный энкодер
  (multilingual-e5-small / MiniLM-класс, зафиксированная ревизия) кодирует все
  глоссы sidecar. PCA до 128 измерений + int8-квантизация → ~52 МБ на 406 тыс.
  глоссов. Формат: заголовок (модель, ревизия, PCA-матрица, SHA-256), затем
  per-key блоки, индексированные тем же каноническим ключом; файл
  `Ranker/Models/GlossEmbeddings/eng-senses.vec` (в git не входит, как и ONNX).
- **Рантайм**: `RankerWorker` получает команду `embed-rank`: один прогон
  энкодера по размеченному контексту → PCA-проекция → скалярные произведения с
  векторами глоссов ключа → top-k (k = 8) → существующий кросс-энкодер
  GlossBERT ре-ранжирует top-k → margin-логика без изменений. Протокол v2
  расширяется до v3 (обязательное поле `pipeline: "bi+cross"` в ответе, хост
  валидирует).
- Кэш результатов: `ModelId` в `SmartDictionaryCacheRequest` включает идентичность
  обеих моделей и файла эмбеддингов — инвалидация бесплатна.
- Fallback: если .vec отсутствует — текущий чистый кросс-энкодерный путь
  (никакой деградации поставки).

**Инварианты.** №2 (GroupId-выравнивание — прореживание до top-k обязано
сохранять сквозные GroupId, а не перенумеровывать), №3, №4 (порог после
ре-ранжирования пересчитать на dev-наборе, подтверждение на holdout-v3), №8
(новые артефакты — с размером и SHA-256).

**Definition of Done.** Латентность select на CPU при 27 глоссах ниже базовой
≥ 2×; dev-точность принятых решений не ниже; отчёт `--ranker-benchmark` в обоих
режимах; RESEARCH.md дополнен; артефакты в release-ассетах.

## 8. Дистилляция и дообучение ранжировщика

**Мотивация.** GlossBERT (BERT-base 2019) обучен на SemCor — не на диалогах VN.
8 из 25 размеченных dev-случаев — воздержания; часть конвертируется в верные
решения доменным дообучением.

**Архитектура.**

- **Датасет** (`tools/distill-wsd.py`): источники — Tatoeba-предложения (CC-BY)
  и свободные англоязычные VN-скрипты (проверять лицензию каждого). Локальная
  Qwen в офлайн-батче размечает: (предложение, слово, инвентарь глоссов из
  sidecar) → выбранный глосс + уверенность; принимать только согласованные
  self-consistency прогоны (3 сэмпла, единогласие). Целевой объём: 50–100 тыс.
  пар. Датасет — артефакт с фиксированным SHA, публикуется с указанием лицензий
  источников.
- **Обучение**: дообучить контекст-глосс кросс-энкодер на базе современного
  компактного энкодера (DeBERTa-v3-small или ModernBERT-base; критерий выбора —
  качество ONNX-экспорта и совместимость с Vitis-компиляцией). Скрипт обучения
  в `tools/`, seed зафиксирован.
- **Интеграция**: путь уже проложен — новый ONNX встаёт на место
  `glossbert-fp32-dynamic.onnx` с новым `ExpectedModelVersionPrefix`, порог
  перекалибровывается на dev, финальное подтверждение — одно открытие
  holdout-v3. NPU-вариант компилируется отдельно и не обязателен в первом шаге.

**Инварианты.** №4, №5 (замороженные наборы: dev — для порога, holdout-v3 —
однократно), №8. Никаких сетевых вызовов в рантайме приложения.

**Definition of Done.** На dev: воздержаний меньше при точности принятых
решений ≥ базовой; holdout-v3 ≥ holdout-показателей GlossBERT; полный отчёт в
RESEARCH.md (данные, лицензии, seed, метрики); артефакты запинены.

- Отдельный порог воздержания: калибровать на новом JA dev-наборе (создать по

- **Редактор**: окно «Мой словарь» (WPF) над
  `%LOCALAPPDATA%\AsteriaScale\Dictionaries\eng-rus-user.tsv`: список, поиск,
  добавление из последнего hover-результата («запомнить как…» в оверлее).
  Запись — через `LocalDictionaryService`-хелпер, канонизирующий ключ (инвариант
  №1); после сохранения — `UnloadAsync`+`LoadAsync` для перечтения.
- **История**: кольцевой буфер последних 200 переводов (память + JSON в
  LOCALAPPDATA), панель с копированием.
- **Anki**: экспорт истории в TSV/apkg-совместимый CSV (слово, перевод,
  контекст) — только файл, без сетевых интеграций.

**Definition of Done.** Добавленная через UI запись немедленно влияет на hover;
тест на канонизацию ключа при записи; история переживает перезапуск; экспорт
открывается в Anki.

## 12. HDR capture path

Зависит от Magpie upstream (FP16/HDR-захват). Со стороны Asteria — отслеживать
релизы, при появлении поддержки: пробросить настройку, проверить цвета
оверлеев (они рисуются поверх в sRGB). До того — задокументированное
ограничение. Самостоятельная реализация капчера — вне скоупа (см. «чего не
делаем» в ARCHITECTURE.md).

## Чего сознательно нет в роадмапе

- **LLM-ранжирование в рантайме** — отвергнуто измерениями (латентность, VRAM);
  LLM используется только офлайн как учитель (№8).
- **Темпоральный апскейл (FSR2+/DLSS)** — требует motion vectors из игры,
  которых при захвате окна нет. Фундаментально, а не временно.
- **Собственный движок захвата/рендера** — паритет с Magpie стоит годы; вся
  ценность проекта — в слое перевода и автоматизации.
