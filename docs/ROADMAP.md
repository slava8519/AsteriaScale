## 0. Новый замороженный holdout-v3

**Мотивация.** `ranker-holdout.json` и `ranker-holdout-v2.json` уже открывались
(v2 — дважды: релиз 0.9.3 и подтверждение снятия batch-лимита). Любая работа над
моделью (№1, 7, 8, 9) требует свежего слепого набора, созданного **до** начала
экспериментов.

**Архитектура.** Новый файл `assets/Ranker/ranker-holdout-v3.json` по схеме v2
(`context`, `target`, `characterIndex`, `candidates`, `expectedTranslation`,
`partOfSpeech`, `senseClass`): 40–60 оригинальных CC0-случаев. Обязательные
классы: междометия, переносные значения, разговорные формы (самые частые
промахи покрытия v2), плюс случаи с инвентарём > 20 глоссов. Автор набора не
должен видеть текущие ошибки модели — генерировать случаи из описаний классов,
а не из логов.

**Валидация.** Схема-валидация (`context.Substring(characterIndex,
target.Length) == target`), проверка «каждый target есть в словаре» через
smoke-тест. Файл после создания не открывается до финального подтверждения
очередной модели; каждое открытие фиксируется в RESEARCH.md.

**Мотивация.** На holdout-v2 12 случаев из 30 имели метку, не покрытую
sense-инвентарём (`expected-not-covered` в `--ranker-benchmark`) — модель не
могла ответить правильно в принципе. Потолок качества сейчас в данных.

**Архитектура.** Правки только в `scripts/build-dictionaries.py` (секция

формат sidecar (5 колонок), лимит 128 смыслов/ключ.

**Definition of Done.** Покрытие меток на dev-наборе и holdout-v2 выросло
(цель: ≥ 24/30 на v2 против нынешних 18/30); dev-точность принятых решений не
упала (`--ranker-benchmark`, cpu и npu); smoke-набор зелёный; размер sidecar
< 12 МБ gz; числа занесены в RESEARCH.md.

## 2. Морфословарь русского (OpenCorpora)

**Мотивация.** Суффиксная морфология — самый хрупкий слой (аудит нашёл в ней
несколько багов). Ложные срабатывания вида «масло → прош. время ср.р.»
подавляются паранойей (`ValidatePastParadigms`), которая заодно отбрасывает и
верные случаи.

**Архитектура.**

- Новый build-скрипт `scripts/build-ru-morphology.py`: из дампа OpenCorpora
  (CC BY-SA) собирает компактный DAWG «словоформа → (лемма-id, POS, род/число/
  время/вид)» только для нужных категорий (глагол, сущ., прил., нареч., межд.).
  Выход: `assets/Morphology/ru-morph.dawg` (~8–15 МБ) + лицензия в
  THIRD_PARTY_NOTICES.md.
- Новый сервис `src/AsteriaScale/Services/RussianMorphologyLexicon.cs`:
  ленивая загрузка DAWG, lookup по словоформе. `RussianMorphology` становится
  фасадом: сначала лексикон, при отсутствии слова — текущие суффиксные правила
  (fallback обязателен: словарь не полон).
- Потребители не меняют сигнатур: `DetectPastForm`, `IsInfinitive`,
  `IsSemelfactiveInfinitive` внутри переключаются на лексикон. Вид глагола
  (сов./несов.) брать из грамем вместо эвристики «-нуть».

**Инварианты.** Поведение при отсутствии данных = сегодняшнее (fallback);
никакой сети в рантайме.

**Definition of Done.** Существующие smoke-блоки морфологии зелёные без правок
ожиданий; новые тесты: словарная форма, которой нет в суффиксных правилах
(«шёл» → прош. м.р. от «идти»), и слово вне словаря (fallback). Прогон
`--ranker-benchmark` (морфология влияет на `SelectSurfaceForm`) без деградации.

## 4. Интеграция text-hook (Textractor)

**Мотивация.** Для совместимых движков hook даёт идеальный текст без OCR-ошибок
и задержки распознавания. Крупнейший доступный скачок качества перевода.

**Архитектура.** Textractor — GPLv3, поэтому строго отдельный процесс (та же
модель изоляции, что и с Magpie):

- Новый интерфейс `ITextSource` (`src/AsteriaScale/Services/TextSources/`):
  `Task<HoverText?> GetTextAtAsync(Point cursor, CancellationToken)` +
  `event SentenceArrived`. Текущий OCR оборачивается в `OcrTextSource`
  (адаптер над `WindowsAiOcrService`, поведение 1:1).
- `TextractorTextSource`: запускает `TextractorCLI.exe` (x86 и x64 — старые VN
  32-битные) как дочерний процесс, командует attach к PID активного профиля
  автоматизации, читает поток предложений из stdout-пайпа. Держит кольцевой
  буфер последних N предложений с таймстампами.
- Маршрутизация в `HoverTranslationService`: если для процесса включён hook и
  свежее (< 5 c) предложение есть — использовать его как контекст; позиция
  слова под курсором всё равно берётся из лёгкого OCR-прохода (слово + индекс),
  а контекст — из hook. Полный fallback на OCR при любом сбое.
- Настройки: `AppSettings.TextHookEnabled`, путь к Textractor, per-profile
  флаг. UI: чекбокс в профиле автоматизации + статус в главном окне.
- Экранный режим: hook-предложения переводятся пакетно без OCR-геометрии не
  получится — экранный режим остаётся OCR-only, это зафиксировать в README.

**Риски.** Hook = инъекция в процесс игры: антивирусные срабатывания, окна от
администратора. Отразить в README/ограничениях. Textractor не ставится
автоматически — только указанием пути, как Magpie.

**Definition of Done.** Тестовая VN (или notepad-эмуляция через clipboard-режим
Textractor) даёт hover-перевод без OCR; выключение/сбой hook незаметно
откатывает на OCR; smoke-тест на адаптер `ITextSource` с фейковым источником;
THIRD_PARTY_NOTICES.md дополнен.

## 5. Декомпозиция HoverTranslationService

**Мотивация.** 1400 строк, четыре режима, таймер, hotkeys, жизненный цикл
моделей и вся smart-логика в одном классе. Порог входа для любой правки высок.

**Архитектура.** Только перестановка кода, ноль поведенческих изменений:

- `HoverTracking` — таймер 90 мс, якорь, стабильность, cancellation (текущий
  `OnTimer`/`ResetTracking`).
- `IHoverMode` с реализациями `SmartHoverMode`, `DictionaryHoverMode`,
  `NeuralHoverMode`, `ScreenTranslationMode`; `ResolveSmartHoverAsync` и
  цепочка эвристик переезжают в `SmartHoverMode` как есть.
- `ModelLifecycleCoordinator` — QueueUnload/WarmUp/idle-таймеры.
- `HoverTranslationService` остаётся фасадом с прежним публичным API
  (используется MainWindow/треем) и роутит в активный режим.

Порядок: выделять по одному классу на PR-шаг, после каждого — полный smoke.
Тест «Dictionary key and sentence normalization» и smart-блоки не меняются.

**Definition of Done.** Файл < 400 строк; поведение подтверждено полным
smoke-набором и ручной проверкой всех четырёх режимов; новых публичных типов в
API приложения нет (всё internal).

## 6. Память словарей

**Мотивация.** Умный режим держит ~212 МБ словарей + ~79 МБ sense-метаданных
как .NET-строки (числа из smoke-лога). Для ноутбука рядом с игрой это много.

**Архитектура.** Два независимых шага, мерить после каждого:

1. **Дешёвый**: после загрузки конвертировать словари в
   `FrozenDictionary<string, byte[]>` с UTF-8-значениями; декодировать значение
   только при показе (`Found`). Ключи остаются строками (нужны для lookup).
   Ожидание: −30–40 % на значениях (они длиннее ключей, а UTF-8 для кириллицы
   вдвое компактнее UTF-16 не будет — честно: ~равно; выигрыш в основном от
   отсутствия object-заголовков на строку → замерить и оставить только если
   ≥ 15 %).
2. **Основной**: офлайн-компиляция словарей в бинарный формат — отсортированный
   массив ключей (UTF-8, front-coding) + offset-таблица значений в одном
   memory-mapped файле `Dictionaries/eng-rus.bin`. Новый
   `scripts/build-dictionaries.py --binary` эмитит его рядом с TSV (TSV
   остаётся источником правды и форматом пользовательских словарей).
   `LocalDictionaryService` при старте: bundled-слои из .bin (mmap, бинарный
   поиск), пользовательские TSV — поверх, в обычный словарь. Sense-метаданные —
   тот же формат, ленивый.

**Инварианты.** №1 (канонизация ключей выполняется при **компиляции** .bin —
зафиксировать версию нормализации в заголовке файла и сверять с
`SmartRankingPipelineVersion`-подобным токеном); приоритет слоёв не меняется.

**Definition of Done.** Smoke-лог показывает ≤ 120 МБ на словари+senses; тест
загрузки .bin + переопределения пользовательским TSV; время загрузки не хуже
текущих ~2.5 с; VersionToken учитывает .bin-файлы.

### Ревизия этапа 2 (измерение 2026-07-21): бланкетный mmap отменён

Замер состава 212 МБ словарей показал, что вес распределён крайне неравномерно:

| Слой | Строк | Доля RAM |
|---|---|---|
| Tatoeba EN (`eng-rus-dialogue`) | 502 680 | ~120 МБ (57 %) |
| Японские (три файла) | 194 523 | ~45 МБ (21 %) |
| Английские лексические | 273 848 | ~47 МБ (22 %) |

Вывод: переводить **все** словари в бинарный формат нерентабельно — выигрыш
~150 МБ (1 % ОЗУ типовой машины) ценой переписывания storage в самом
инвариант-нагруженном компоненте, где аудит уже находил три бага. Рядом
работают GlossBERT-воркер (модель 438 МБ) и Qwen 2B (~2 ГБ): словари не
доминирующий потребитель, к тому же выгружаются при смене режима.

**Заменяющий план (делать только по триггеру):**

1. **Дисковый индекс для Tatoeba-слоя** (M): −120 МБ, 44 % одним слоем.
   Идеальный кандидат — 500 тыс. предложений, одно обращение на наведение,
   значения в RAM не нужны. Переиспользовать готовый паттерн
   `GlossEmbeddingIndex` (смещения в памяти, значения с диска через
   `FileStream` с `FileOptions.RandomAccess`). Осторожно: короткие
   диалоговые записи (≤3 токенов) участвуют и в фразовом поиске — индекс
   должен обслуживать оба пути.
2. **Не грузить японские словари**, когда `SmartDictionarySourceLanguage`
   жёстко = English (S): −45 МБ. Нужен ленивый догруз, если `ContainsJapanese`
   всё же сработает на кадре.

**Триггеры возврата:** (а) японский sense-sidecar №9 + NMT в процессе №16
поднимут суммарное потребление за ~500 МБ; (б) жалобы на машинах с 8 ГБ.
До наступления — не трогать.

## 7. Bi-энкодер: предвычисленные эмбеддинги глоссов

**Мотивация.** Кросс-энкодер скорит каждую пару (контекст, глосс) отдельно —
латентность растёт с числом смыслов, NPU-батчи фиксированы. Bi-энкодер с
офлайн-эмбеддингами глоссов делает стоимость ранжирования ~нулевой и открывает
дорогу №9 (мультиязычный контекст).

**Архитектура.**

- **Офлайн** (`tools/build-gloss-embeddings.py`): компактный энкодер
  (multilingual-e5-small / MiniLM-класс, зафиксированная ревизия) кодирует все
  глоссы sidecar. PCA до 128 измерений + int8-квантизация → ~52 МБ на 406 тыс.
  глоссов. Формат: заголовок (модель, ревизия, PCA-матрица, SHA-256), затем
  per-key блоки, индексированные тем же каноническим ключом; файл
  `Ranker/Models/GlossEmbeddings/eng-senses.vec` (в git не входит, как и ONNX).
- **Рантайм**: `RankerWorker` получает команду `embed-rank`: один прогон
  энкодера по размеченному контексту → PCA-проекция → скалярные произведения с
  векторами глоссов ключа → top-k (k = 8) → существующий кросс-энкодер
  GlossBERT ре-ранжирует top-k → margin-логика без изменений. Протокол v2
  расширяется до v3 (обязательное поле `pipeline: "bi+cross"` в ответе, хост
  валидирует).
- Кэш результатов: `ModelId` в `SmartDictionaryCacheRequest` включает идентичность
  обеих моделей и файла эмбеддингов — инвалидация бесплатна.
- Fallback: если .vec отсутствует — текущий чистый кросс-энкодерный путь
  (никакой деградации поставки).

**Инварианты.** №2 (GroupId-выравнивание — прореживание до top-k обязано
сохранять сквозные GroupId, а не перенумеровывать), №3, №4 (порог после
ре-ранжирования пересчитать на dev-наборе, подтверждение на holdout-v3), №8
(новые артефакты — с размером и SHA-256).

## 8. Bake-off и доменное обучение definition-aware ранжировщика

**Мотивация.** Проекту нужен не бренд GlossBERT, а локальная
definition-aware функция `(контекст, target, произвольные Wiktionary-glosses)
→ выбранный GroupId | abstain`. Текущий GlossBERT (BERT-base 2019, SemCor)
уже даёт точный консервативный baseline, поддерживает произвольные определения
и работает через ONNX на CPU/NPU, но не обучен на VN-диалогах, сокращениях и
Wiktionary-инвентаре Asteria. Заменять его можно только победителем
same-build сравнения, а не более новым названием модели.

**Архитектура.**

- **Зафиксировать baseline:** 65-case dev, register/18+ dev из №14.2C,
  latency по малым/большим инвентарям, peak working set, размер артефакта,
  accepted precision, decision и end-to-end correct coverage. Margin `0.25`
  текущего GlossBERT до выбора победителя не меняется.
- **Кандидаты bake-off:**
  1. текущий GlossBERT cross-encoder — обязательный baseline и rollback;
  2. уже реализованный MiniLM bi-encoder top-12 + GlossBERT cross rerank;
  3. `microsoft/deberta-v3-small` (MIT, 6 слоёв) как основной новый
     cross-encoder после WSD/VN fine-tune;
  4. `answerdotai/ModernBERT-base` (Apache-2.0, 149M) как кандидат качества,
     только если ONNX Runtime/Vitis поддерживают его ops без CPU fallback;
  5. enhanced sense representation: definition + проверенный synonym/example,
     поскольку обогащение представления смысла может дать прирост без смены
     runtime-архитектуры.
- **Не кандидаты поставки:** ESCHER/ConSeC используются только как
  исследовательские ориентиры: их официальные реализации сильны на стандартном
  WordNet WSD, но имеют CC BY-NC / CC BY-NC-SA лицензии, Linux/PyTorch-обвязку
  и фиксированный sense-inventory workflow. Генеративная модель не становится
  hover-ranker: она медленнее и хуже подходит для детерминированного
  margin-abstention.
- **Gold-разметка под управлением Codex** (`tools/distill-wsd.py`): сначала
  формируется очередь `(context, target span, POS, полный inventory glosses)`.
  Codex задаёт руководство разметчика, вручную выбирает/исправляет 1 500–3 000
  сложных train-примеров и разбирает все конфликты: близкие значения одного
  lemma/POS, редкие смыслы, MWE, сокращения, разговорный и register/18+
  контраст. Каждая запись хранит выбранный GroupId, допустимые альтернативы,
  краткое обоснование, источник, лицензию и статус `gold`.
- **Silver-масштабирование:** целевой объём 50–100 тыс. пар набирается сначала
  из sense-linked Wiktionary examples и иной однозначной distant supervision,
  затем — из Tatoeba (CC-BY) и свободных VN-скриптов с проверенной лицензией.
  Локальная Qwen может дать три независимых черновых ответа, но метка становится
  `silver` только при единогласии, прохождении POS/span/inventory-проверок и
  отсутствии конфликта с gold. Неуверенные, расходящиеся и низкомаржинальные
  случаи автоматически попадают в Codex-очередь, а не в обучение.
- **Опциональный внешний учитель:** frontier API разрешён только для публичных
  или явно разрешённых пользователем данных, с отдельным бюджетом и manifest;
  он также производит кандидаты, а не автоматически истинные метки. Сам Codex
  не вызывается из локального batch-скрипта без такого явно настроенного API.
- **Защита от teacher bias:** dev, register-dev и frozen holdout не входят в
  запросы учителям; splits делаются по lemma/диалогу до генерации вариантов.
  Датасет публикуется с SHA-256, версией инструкции, provenance каждой метки и
  полной статистикой `gold|silver|rejected|needs_review`.
- **Обучение**: одинаковый split/seed/negative sampling для GlossBERT,
  DeBERTa-v3-small и допустимого ModernBERT. Обязательны hard negatives одного
  lemma/POS, редкие смыслы, MWE, разговорные и register/18+ контрасты. Сначала
  выполняется controlled run только на gold, затем gold+silver с повышенным
  весом gold; прирост от silver обязан подтверждаться отдельной абляцией.
  Скрипт обучения в `tools/`, входы и teacher outputs закрепляются SHA-256.
- **Интеграция**: путь уже проложен — новый ONNX встаёт на место
  `glossbert-fp32-dynamic.onnx` с новым `ExpectedModelVersionPrefix`, порог
  перекалибровывается на dev, финальное подтверждение — одно открытие
  holdout-v3. NPU-вариант компилируется отдельно и не обязателен в первом шаге.

**Инварианты.** №4, №5 (замороженные наборы: dev — для порога, holdout-v3 —
однократно), №8. Никаких сетевых вызовов в рантайме приложения.

**Правило выбора.** Победитель обязан сохранить accepted precision не ниже
`95 %` и без значимого падения относительно baseline, поднять end-to-end
correct coverage минимум на `8` п.п., уменьшить долю воздержаний минимум на
`20 %`, пройти register/18+ gates №14.2C и не ухудшить CPU latency/peak memory
более чем на `20 %`. Никакого provider fallback. После фиксации модели и
порога — одно заранее объявленное открытие holdout-v3; до него holdout не
используется.

**Definition of Done.** Опубликованы versioned annotation guide, gold/silver
manifest и абляции `base → gold → gold+silver`, одинаковые dev-отчёты всех
кандидатов, лицензии и ONNX/NPU-совместимость; победитель проходит правило
выбора и one-shot holdout не хуже GlossBERT. Если никто не проходит — GlossBERT
остаётся production ranker, а отрицательный результат фиксируется в
RESEARCH.md.

**Архитектура.**

## 14. Глоссарное связывание и смысловая валидация

**Мотивация.** 2B-модель проваливается на редких смыслах и терминах — ровно
там, где словарный стек силён. При этом выбранная словарная поверхность не
всегда является единственной естественной русской реализацией смысла. Поэтому
GlossBERT должен не диктовать текст Qwen, а консервативно обнаруживать явный
выбор отвергнутого смысла.

**Архитектура.**
- `TranslationScaffoldBuilder` просматривает все контентные слова, MWE и exact
  dialogue. Детерминированно подтверждённые имена, термины и выражения остаются
  обязательными `ScaffoldTerm`; именно они и только они попадают в первый
  prompt Qwen.
- Для каждого оставшегося неоднозначного английского слова GlossBERT получает
  исходный план с `CandidateGroupIds`. Принятое по frozen margin `0.25` решение
  становится `ScaffoldSenseHint`: source, английское определение, выбранная и
  все отвергнутые русские поверхности. Оно **не** превращается в mandatory
  term. Abstention означает отсутствие hint, а не ошибку.
- Один и тот же production-конвейер включён во всех EN full-text маршрутах:
  `Neural`, автоматический и ручной fallback `Smart`, пакетный `Screen`;
  text-hook подменяет источник текста, но не маршрут перевода. Японская ветвь
  ждёт smart-словарь №9.
- Exact dialogue из доверенного слоя возвращается без Qwen, если совместим с
  детерминированными авторитетными terms. Neural hints не блокируют bypass.
- Явная отвергнутая русская поверхность при отсутствии выбранной поверхности
  того же source — только prefilter для semantic review, а не доказательство
  ошибки. Если mandatory-термины соблюдены, разрешён один structured review той
  же Qwen с полностью английскими служебными инструкциями: English source,
  предыдущий русский перевод и английские definitions передаются как
  non-authoritative hypotheses, а выбранные/отвергнутые neural-поверхности в
  prompt не попадают. Ответ — строго `KEEP` либо `FIX|<исправленный перевод>`;
  `KEEP` сохраняет естественный синоним/словоформу или отвергает неподходящую
  GlossBERT-гипотезу.
- При mandatory miss neural review не совмещается с исправлением: единственный
  вызов получает прежний deterministic fidelity prompt, а sense-prefilter после
  него служит диагностикой. Кандидат `FIX` или deterministic retry принимается
  только при строгом лексикографическом улучшении пары
  `(mandatory violations, unresolved sense flags)`. `KEEP`, пустой или
  невалидный ответ и prompt echo не могут заменить первый перевод. Qwen служит
  окончательным смысловым арбитром: валидный `FIX` снимает sense flag только
  при содержательно изменившемся очищенном тексте и при неухудшившихся
  mandatory-терминах. Невалидный review показывается как безопасный первый
  ответ, но не кэшируется.
- Batch-ранжирование последовательно и использует общий circuit на операцию:
  первая ошибка GlossBERT помечает остальные neural-запросы как skipped, но
  deterministic scaffold и Qwen продолжают работу. Abstention circuit не
  открывает.
- Provider задаётся явно и валидируется вместе с моделью; fallback между
  CPU/NPU запрещён. Кэшируются selected и abstained решения с идентичностью
  provider/model/dictionary/input/plan; ошибки не кэшируются.

**Инварианты.** Порог GlossBERT и критерий принятия не меняются: только margin
`0.25`. `GroupId == index` сохраняется при обратном отображении решения. После
записи JSONL-запроса всегда дренируется ровно один ответ. Ошибка neural-части не
роняет перевод; cancellation не проглатывается. Подсказка GlossBERT
неавторитетна и никогда не расширяет обязательный каркас.

**Definition of Done.** Исходное требование `qwen-scaffold ≥ qwen + 15 п.п.`
было записано до baseline и после результата `53/61` оказалось математически
недостижимым: даже `61/61` даёт только `+13,115 п.п.`. До настройки №14 gate
исправлен на `≥59/61` (не менее шести исправленных baseline-промахов) при chrF
не ниже, residual-English не хуже и медианной латентности ≤ +25 %. Для
revised-v2 дополнительно фиксируются neural requests/selected/abstained/errors,
retries, отклонённые structured-ответы (включая prompt echo) и конфликты
до/после. Smoke покрывает построение single/batch prompt, eligibility exact
bypass, abstention/error circuit, ключи кэша и строгий parser/selector retry;
реальный Qwen + GlossBERT flow проверяется gated dev-бенчмарком.

**Статус 22 июля 2026:** выполнено. Deterministic-этап ранее достиг `61/61`,
chrF `0,591323` против baseline `0,513417`, residual English `0`. После трёх
отклонённых neural ablations и отклонённого consensus-v1 с русскими
review-инструкциями финальный strict-v3 English-review прогон дал chrF
`0,591288`, anchors `60/61`, residual English `0`, latency median/max
`1230,5/6666` мс. Соблюдены `26/27` deterministic terms, exact bypass `4`,
mandatory violations `4 → 1`; sense flags `6 → 3`, reviews:
`KEEP=3`, `FIX=0`, `rejected=2`, `failed=0`. Из шести sense-prefilter случаев

GlossBERT: `requests=140`, `selected=77`, `abstained=63`,

### 14.1. VN Layer 2.0 — роли, provenance и безопасное расширение

**Мотивация.** Старый `eng-rus-vn.tsv.gz` смешивал готовые переводы карточки,
кандидаты смысла, частичные каркасные якоря и целые реплики. Любая массовая
загрузка одновременно перекрывала broad-слои, подавляла GlossBERT и могла
превратить одиночную поверхность в обязательное ограничение Qwen.

**Архитектура.** Данные разделены на четыре независимые роли:

- VN-hard — небольшой проверенный слой видимых override и residual repair;
- VN-soft + sense-sidecar — разговорные и многозначные кандидаты, которые
  объединяются с broad и ранжируются GlossBERT;
- scaffold-only — отдельные обязательные термины полного перевода, невидимые
  в карточке словаря;
- exact dialogue — только полное sentence-совпадение с самым низким
  приоритетом.

Структурированный source TSV содержит стабильные source/record ID, роль,
review-tier, перевод, английское определение, регистр и POS. Source lock
закрепляет размеры, SHA-256, версии и лицензии; генератор fail-closed проверяет
канонические конфликты, русский script, число поверхностей и воспроизводимость.

**Статус 22 июля 2026:** выполнено и дополнено полевыми выражениями Ever17.
Теперь `171` уникальный ключ разнесён по `187` назначениям ролей: `114` hard,
`52` soft (`102` sense rows) и `21` scaffold anchor; `16` проверенных
hard-ключей намеренно также
имеют отдельную scaffold-роль. Всего структурированный источник содержит
`194` записи, поскольку семь soft-ключей имеют несколько смыслов. Добавлен
официальный MASSIVE 1.1 (CC BY 4.0): из `16 521` EN–RU пар после фильтров
поставляются `9 837` exact-реплик; локализованные сущности, слабые judgments,
строки длиннее 10 слов, смешанный script и конфликтующие sentence keys
отброшены. Добавлены provenance/manifest, генераторные тесты и runtime smoke
на независимость ролей. Финальное dev-подтверждение после quality foundation:
GlossBERT `21/21` правильных принятых размеченных решений, expected-inventory
coverage `37/45`, end-to-end correct coverage `33/65`; полный перевод — chrF
`0,589491`,
anchors `60/61`, residual English `0`, median `1253` мс, ranker errors `0`.
Frozen ranker/translation holdout не открывались.

### 14.2. Smart Dictionary Quality Foundation

**Мотивация.** Полевой прогон показал, что объём sidecar уже не главный
лимит. Качество теряется в маршрутизации и реализации ответа: неоднозначная
broad-фраза обходила ranker целиком, грязная русская поверхность могла
победить хорошую из-за порядка источников, а POS-слои разных частей речи
смешивались ещё при генерации данных. Увеличивать словарь поверх этих дефектов
опасно.

**Фаза A — выполнена 22 июля 2026 до обучения №8:**

- trusted user/VN-hard и чистые однозначные фразы сохраняют быстрый exact
  bypass; неоднозначные broad-фразы идут в definition-aligned smart routing;
- выбор русской поверхности сначала оценивает её пригодность, затем
  морфологию/регистр/приоритет источника; повреждённая или смешанная с латиницей
  поверхность не может вытеснить чистую;
- генератор делит русские глоссы только по запятым верхнего уровня, отбрасывает
  meta/Latin/unbalanced мусор и обогащает sense только из того же POS;
- добавлены консервативные grammar fast-path для `while`, `that`, lexical/aux
  `do`, конструкции `[duration] ago` и самостоятельного UI-глагола `Save`;
- field cases из Ever17 стали dev-регрессиями, но frozen holdout не
  используется для настройки.

**Фаза B — следующая smart-задача:** единый target-centered context builder
для cache key и worker input. Он сохраняет целевой span, симметрично обрезает
длинную реплику под реальный token budget и исключает повторное использование
решения для другого локального контекста. Benchmark gate уже усилен минимумами
expected-inventory coverage `70 %`, decision coverage `45 %` и end-to-end
correct coverage `45 %`, чтобы `100 %` точность одного принятого случая не
считалась успехом; context builder остаётся незакрытой частью фазы B.

**Фаза C — Register/18+ Fidelity, запланирована до №8.** Данные не являются
главным пробелом: текущий sense-sidecar уже содержит `6 428` грубых строк для
`1 022` ключей, `13 301` строку с жаргонной маркировкой для `3 907` ключей и `6 460`
разговорных строк для `1 784` ключей (категории пересекаются). Проблема в
политике: `RegisterRank` предпочитает «безопасную» поверхность, а full-text
prompt не требует сохранять степень грубости и сексуальную эксплицитность.

- ввести нормализованный `SenseRegister` (`neutral`, `colloquial`, `slang`,
  `vulgar/offensive`, `sexual-domain`, `archaic`, `dialect`) отдельно от
  пригодности поверхности; грубость не считается дефектом данных;
- выбирать поверхность по соответствию выбранному sense/register: не
  смягчать и не усиливать оригинал. При неуверенности карточка показывает
  несколько вариантов с метками `РАЗГ.`, `ЖАРГ.`, `ГРУБ.`, `СЕКС.`;
- full-text prompt получает явное правило: переводить без цензуры, сохранять
  уровень грубости/эксплицитности, но не добавлять её отсутствующему оригиналу;
- распространённые masked spellings (`f*ck`, `sh!t`-класс) обрабатываются
  только как lookup-кандидаты с сохранением исходного span. Глобальная
  `NormalizeEnglish` и sentence keys не меняются;
- создать `ranker-register-benchmark.json` минимум на 120 оригинальных CC0
  случаев: 30 neutral↔vulgar ambiguity, 30 sexual↔ordinary senses, 30
  slang/contractions/просторечие, 30 masked/euphemistic forms. Отдельный
  `translation-register-benchmark.json` содержит минимум 40 полных реплик;
- gates: semantic accepted precision `≥90 %`, register fidelity `≥90 %`,
  отсутствие необоснованного усиления `≥95 %`, пустых ответов/отказов/цензурных
  заглушек — `0`; все метрики считаются отдельно по четырём корзинам.

**Definition of Done фазы C.** UI показывает register provenance, Smart и
full-text проходят оба dev-набора, настройки позволяют выбрать `Точно как в
оригинале` (default) или `Смягчать`; пользовательский словарь остаётся высшим
приоритетом. Frozen ranker/translation holdout для настройки не открывается.

**Definition of Done.** Release/smoke и generator tests зелёные; dev
`--ranker-benchmark` проходит без изменения frozen margin `0.25`; отдельно
зафиксированы inventory/decision/end-to-end coverage и регрессии реальных
слов/фраз. `ranker-holdout*` не открывается до заранее назначенного one-shot.

### 14.3. Целостность OCR-реплики и подтверждённый text-hook

**Мотивация.** На пяти из десяти полевых снимков Qwen получила фрагмент вместо
реплики. На широком экране sentence capture обрезал текст, а эвристика
предложения ломалась на многоточии и нескольких предложениях. Это сильнее
любого улучшения модели: отсутствующий текст невозможно корректно перевести.

**Архитектура.**

- строить адаптивный capture вокруг фактического текстового блока, а не
  фиксированный `2400×720`; не смешивать соседние UI-колонки;
- сохранять speaker label и всю текущую реплику, корректно обрабатывать
  `...`, кавычки и несколько предложений;
- передавать provenance `OCR|HOOK` до карточки. `HOOK` показывается только
  после свежего предложения Textractor, содержащего OCR-якорь, а не после
  одного успешного attach;
- `C:\Textractor` входит в auto-probe; для 32-битного Ever17 выбирается x86
  CLI. Если автохуки не дали полного текста, H-code ищется живым capture на
  точной сборке EXE и сохраняется в профиль; код от другой версии не
  угадывается;
- span mismatch в GlossBERT остаётся fail-open, логируется с source/target и
  покрывается регрессией нормализации.

**Промежуточный статус 22 июля 2026:** provenance доведена до карточки,
`HOOK` появляется только при фактическом свежем совпадении, `C:\Textractor`
добавлен в auto-probe и CLI выбирается по битности процесса. Адаптивный OCR
реплики, явная метка `OCR` и живая проверка/подбор H-code для точной сборки
Ever17 остаются работой этапа 14.3.

**Definition of Done.** На широком экране контрольный набор Ever17 отдаёт
полную реплику со speaker label; карточка явно показывает `HOOK` или `OCR`;
ellipsis/multi-sentence/wrapped-line tests зелёные; десять сохранённых кадров
повторно прогнаны без усечения source. Только после этого начинать №15.

## 15. Контекстная память диалога

**Мотивация.** Реплики VN переводятся изолированно: теряются род говорящего,
анафора («she» → кто?), стиль обращения (ты/вы), единообразие имён.

**Архитектура.**
- Новый `src/AsteriaScale/Services/DialogueContextMemory.cs` (internal sealed):
  - кольцевой буфер последних 8 пар `(source, translation, speaker?)` на
    процесс (ключ — имя процесса, как в `TextHookService.FindProfileFor`);
  - парсер спикера: строка вида `[Имя]` или `Имя:` в начале реплики (или
    предыдущей OCR-строки) → поле speaker;
  - персистентный словарик игры
    `%LOCALAPPDATA%\AsteriaScale\Context\<processName>.json`:
    `{ names: {"Yuki": {"ru": "Юки", "gender": "f"}}, pairs: [...] }`,
    LRU-кап 200 имён, схема versioned (`"version": 1`), атомарная запись
    через временный файл (образец — `SmartDictionaryResultCache`);
  - выведение пола: если модель выбрала «сказала/улыбнулась» при спикере X —
    зафиксировать X как жен. (морфолексикон №2 даёт грамемы);
  - `Clear()` + кнопка «Забыть контекст игры» в UI (рядом с настройками
    перевода).
- Инъекция в промпт (продолжение шаблона №14, бюджет ≤ 600 символов):
  ```
  Контекст (уже переведено, не переводить):
  [Юки] Давно не виделись!
  [Гг] Да, целый год…
  Говорит: Юки (жен.)
  ```
- Синергия с text-hook: буфер `TextHookService` уже держит исходные
  предложения — использовать их как source-контекст, даже когда переводов ещё
  нет.
- Зафиксированные имена автоматически попадают в глоссарный блок №14 —
  единообразие без повторного выбора.

**Definition of Done.** Смоук-тесты: парсер спикера, LRU-кап, персистентность
(temp-каталог), выведение пола по прошедшей форме. На dev-наборе №13 (добавить
10 связных мини-диалогов с местоимениями) — anaphora-подмножество: доля
правильного рода ≥ +20 п.п. к изолированному переводу.

## 16. Направленные модели: en→ru, ja→en, ja→ru

**Мотивация.** Универсальная Qwen — компромисс. Специализированная NMT меньше
и быстрее на «чистом» переводе; но глоссарные ограничения в NMT не
вставляются промптом. Решение — выбор движка per-направление, а не замена.

**Архитектура.**
- `ITranslationEngine` (internal): `TranslateAsync(source, scaffold, context,
  CancellationToken)`; реализации: `QwenTranslationEngine` (текущий
  FoundryTranslationService-путь, поддерживает каркас+контекст) и
  `OnnxNmtEngine` (ONNX Runtime, артефакты пинуются SHA-256 как GlossBERT,
  в git не входят; beam=4, максимум 128 токенов).
- Настройки: `TranslationEngineEnRu`, `TranslationEngineJaRu`,
  `TranslationEngineJaEn` = `auto|qwen|nmt`; `JapaneseTargetLanguage = ru|en`.
  `auto`: каркас непуст → qwen (ограничения важнее), пуст → nmt (скорость).
  Направление: `ContainsJapanese` + override из настроек.
- **Рекомендации по моделям** (проверить актуальность на дату реализации):
  - **en→ru, первый specialised bake-off**: `google/translategemma-4b-it`
    (Gemma terms, 55 языков, 2K input context) против текущего Qwen 3.5 2B.
    Модель создана именно для перевода и важнее общей Gemma 4. До production
    обязательны проверка Gemma terms для register/18+ сценария, воспроизводимый
    text-only export/quantization и отдельный worker: в каталоге Foundry Local
    0.10.2 на эталонной машине TranslateGemma отсутствует.
  - **en→ru, Foundry-кандидат без нового runtime**: доступный в текущем каталоге
    `qwen3.5-9b` CPU (`7,9 ГБ`) — только dev A/B после проверки свободной RAM и
    p95 latency. `qwen3-14b` CPU (`9,3 ГБ`) допускается как верхняя контрольная
    точка, но не как ожидаемый live default на машине с 24 ГБ общей RAM.
  - **en→ru, компактный NMT baseline**: Helsinki-NLP `opus-mt-en-ru`
    (MarianMT, ~300 МБ fp32 / ~80 МБ int8; экспорт: `optimum-cli export onnx`).
    Лицензия CC-BY-4.0 совместима. Он нужен как нижняя граница latency/памяти,
    а не предполагаемый победитель качества.
  - **GGUF research lane:** `IlyaGusev/saiga_nemo_12b` (Apache-2.0) можно
    измерить через изолированный llama.cpp harness, но один Habr-тест на трёх
    фрагментах HPMOR не заменяет VN-dev №13. `saiga_yandexgpt_8b` не брать:
    custom-лицензия базовой YandexGPT запрещает ряд оскорбительных/explicit
    outputs и конфликтует с register/18+ fidelity; Gemma-based Saiga остаётся
    ниже официальной TranslateGemma по приоритету и требует отдельной проверки
    всей цепочки производных моделей.
  - **ja→ru напрямую**: открытые NMT слабые (`opus-mt-ja-ru` низкого
    качества). Рекомендация: остаётся Qwen (2B мультиязычна и с каркасом
    из JMdict-глоссов №9 даёт лучший результат). NMT-инвестиции сюда не
    делать до появления сильной открытой пары.
  - **ja→en**: кандидаты — `opus-mt-ja-en` (посредственно), Sugoi/JParaCrawl-
    based NMT (сильна именно на VN, **но лицензия JParaCrawl — research-only:
    юридическая проверка обязательна до включения в сборку**), NLLB-600M
    (CC-BY-NC — NC-ограничение!). До прояснения лицензий ja→en тоже Qwen.
  - **Замена самой Qwen**: следить за каталогом Foundry Local; кандидаты
    Qwen/Gemma/TranslateGemma замерять ТОЛЬКО через №13 (dev), с одним
    подтверждением на holdout. Общая Gemma 4 26B-A4B — возможный офлайн-учитель,
    но не live-кандидат эталонной машины: даже Q4 требует около `14,4 ГБ`
    только на веса, поскольку все 26B параметров MoE должны быть загружены.
    TowerInstruct — CC-BY-NC, не брать.
  - **Пивот ja→en→ru** (двойной NMT): не делать — накопление ошибок, два
    прогона; Qwen напрямую лучше.
- **Исследовательский вопрос** (отдельный файл-заметка в RESEARCH.md):
  constrained decoding для Marian ONNX (вставка глоссария в NMT) — известные
  подходы (vocabulary constraints, prefix-tree decoding) дороги; практичный
  паллиатив — пост-валидация №14 с повтором через Qwen при провале якорей.
- NPU-компиляция NMT (Vitis) — не в скоупе: encoder-decoder с beam-поиском
  плохо ложится на статические формы; вернуться после №7-опыта.

**Definition of Done.** Абстракция движков + `OnnxNmtEngine` для en→ru за
флагом; сравнение qwen / qwen-scaffold / nmt на dev-наборе №13 (chrF, якоря,
латентность) в RESEARCH.md; выбор per-направление в UI (ComboBox в панели
перевода); фолбэк: сбой NMT → Qwen → словарная карточка (никогда не пусто).

## 17. Экранный конвейер 2.0

**Мотивация.** Экранный режим переводит блоки изолированно и по одному:
медленно (N вызовов LLM) и бессвязно (блоки одного диалога переводятся
без взаимного контекста).

**Архитектура.**
- Пакетный промпт: блоки нумеруются и переводятся одним вызовом
  (`1. ... 2. ...` → парсинг ответа по номерам; при расхождении числа строк —
  откат на поштучный путь). Кап: 12 блоков на вызов, длинные экраны — сериями.
- Блоки сортируются в порядке чтения (сверху вниз, уже есть геометрия
  `ScreenOcrBlock`) и получают общий контекст №15 + общий каркас №14
  (объединение терминов всех блоков, кап 20).
- Кэш экрана: нормализованное предложение → перевод (переиспользовать
  паттерн `SmartDictionaryResultCache`: SHA-ключи, LRU, debounce-персист;
  отдельный файл `screen-translation-cache.v1.json`, кап 2 МБ). Повторный
  Alt+Shift+T на неизменном экране — мгновенный (уже есть unchanged-frame
  guard в OCR — расширить до переводов).
- Прогресс в оверлее: «переведено 4/9…» (сейчас только «перевожу»).

**Definition of Done.** На эталонном скриншоте с 8 блоками: число вызовов
LLM ≤ 2, повторный прогон < 300 мс; смоук на парсер нумерованного ответа
(включая случай «модель склеила строки»); поведение при отмене — без
частичных оверлеев.

## 18. Персональная память переводов (TM)

**Мотивация.** Один и тот же текст в VN перечитывается многократно
(бэклог, повторные прохождения). Принятый перевод должен быть бесплатным при
повторе — это и скорость, и стабильность.

**Архитектура.** Новый `TranslationMemoryService`: персистентный LRU
(нормализованный `NormalizeEnglishSentenceKey`-источник → перевод, движок,
таймстамп), файл `%LOCALAPPDATA%\AsteriaScale\translation-memory.v1.json`,
кап 10 000 записей / 4 МБ (весь паттерн — копия `SmartDictionaryResultCache`,
включая атомарную запись и debounce). Проверка ДО вызова LLM в обоих
полнотекстовых путях; сохранение ПОСЛЕ валидации №14. Экспорт в TSV кнопкой
(формат пользовательского словаря — записи можно повысить до
`eng-rus-user.tsv`). Инвалидация: смена движка/модели меняет ключевое поле
`engineId` — старые записи продолжают работать (перевод не хуже), но
перезаписываются при повторном перев��де.

**Definition of Done.** Смоук: попадание/промах, LRU, персистентность,
экспорт; в `--translation-benchmark` появляется столбец «TM hit-rate» на
повторном прогоне (ожидание: 100 %).

## 19. Дистилляция направленного переводчика

**Мотивация.** Долгосрочно: своя компактная модель en→ru VN-домена, обученная
понимать реплику, контекст и регистр и уважать словарный каркас, вместо
универсальной 2B. Один перевод Qwen не является эталоном: у естественной
реплики допустимо несколько русских реализаций, а ошибки учителя иначе
дистиллируются вместе с его знаниями.

**Архитектура (исследовательский протокол).**
1. **Единица данных:** `{source, previousTurns, speaker, deterministicScaffold,
   reference[], register, requiredAnchors, forbiddenDrifts, provenance}`.
   Split выполняется по произведению/диалогу, чтобы соседние реплики не
   оказались одновременно в train и dev. Frozen `translation-holdout-v1`
   исключается до финального one-shot.
2. **Codex-gold:** 2 000–5 000 наиболее информативных реплик переводятся или
   исправляются Codex по versioned guide. В gold входят короткие эллиптические
   реплики, местоимения и род из №15, многозначность №8, MWE, имена, юмор,
   грубый/сексуальный/разговорный регистр №14.2C и намеренно похожие
   preferred/rejected пары. Допустимы несколько равноценных references.
3. **Silver-корпус:** 100–300 тыс. реплик только из источников с проверенной
   лицензией. Существующий перевод используется, когда он действительно
   выровнен и лицензионно пригоден. Иначе текущая Qwen с каркасом №14 и
   контекстом №15 генерирует 2–3 кандидата; правила проверяют anchors, имена,
   числа, residual English, длину, повторения и register drift. Единогласные
   случаи получают `silver`, остальные идут на Codex-adjudication. Qwen —
   генератор вариантов, не источник истины.
4. **Опциональная frontier-разметка:** только после отдельного разрешения на
   сеть/стоимость и только для публичных либо явно разрешённых текстов. Ответы,
   версия модели и prompt сохраняются в manifest; критичные примеры всё равно
   подтверждаются Codex. Приватные пользовательские скрипты по умолчанию не
   отправляются наружу.
5. **Обучение:** сначала SFT на gold, затем gold+silver с повышенным весом gold.
   Для decoder-студента отдельный preference/contrastive этап учит отличать
   исправленный вариант от семантического, терминологического или регистрового
   промаха. Сравниваются LoRA компактной Qwen-класса, TranslateGemma 4B и
   направленный MarianMT; входной контракт обязан принимать контекст и scaffold
   либо явно доказать, что выигрыш скорости компенсирует их отсутствие.
6. **Абляции:** `base`, `silver-only`, `gold-only`, `gold+silver`,
   `gold+silver+preferences`, а также без context и без scaffold. Так отдельно
   измеряется вклад данных, Codex-разметки, памяти и словарного каркаса.
7. **Оценка до holdout:** автоматические chrF/anchors/residual-English,
   сохранение имён и чисел, register fidelity №14.2C, связность №15, latency,
   peak memory и слепое попарное сравнение минимум 200 dev-реплик. Оценщик не
   видит источник варианта; спорные оценки сохраняются, а не принудительно
   сводятся к мнению учителя.
8. **Вход в production:** anchors не ниже текущих `60/61`, residual English и
   цензурные заглушки — `0`, register fidelity не ниже `90 %`, критических
   смысловых ошибок не больше baseline, слепая доля win+tie не ниже baseline;
   при этом median CPU latency лучше минимум на `25 %` и peak memory меньше
   минимум на `30 %`. Затем один прогон `translation-holdout-v1`. Если gate не
   пройден, Qwen остаётся production-движком; студент может жить только за
   экспериментальным флагом.
9. Всё обучение и экспорт находятся в `tools/`; релизный runtime остаётся
   полностью офлайн, артефакты модели закрепляются размером и SHA-256.

**Definition of Done.** Опубликованы annotation guide, gold/silver/rejected
manifest с лицензиями и SHA-256; воспроизводимые скрипты генерации, обучения,
абляций и ONNX-экспорта; слепой dev-отчёт в RESEARCH.md; прошедшая gate модель
под флагом с безопасным fallback на Qwen и пинами release-артефактов.

## Чего сознательно нет в роадмапе

- **LLM-ранжирование в рантайме** — отвергнуто измерениями (латентность, VRAM);
  LLM используется только офлайн как учитель (№8).
- **Пословная сборка полного перевода без генеративной модели (RBMT)** —
  словарь+смыслы+морфология не решают синтаксический перенос, падежное
  управление и согласование; это потолок PROMT-девяностых. Словарный стек —
  каркас и валидатор для генеративного слоя (Трек II), а не его замена.
- **Темпоральный апскейл (FSR2+/DLSS)** — требует motion vectors из игры,
  которых при захвате окна нет. Фундаментально, а не временно.
- **Собственный движок захвата/рендера** — паритет с Magpie стоит годы; вся
  ценность проекта — в слое перевода и автоматизации.
