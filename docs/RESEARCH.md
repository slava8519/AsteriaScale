# Исследование real-time апскейла окон

Дата фиксации исследования: 18 июля 2026 года.

## Вывод

Для произвольного low-res окна на Windows лучший практически применимый путь — `Windows Graphics Capture → Direct3D 11 texture → специализированный spatial CNN/HLSL → edge-aware resize → presentation`. Для визуальных новелл главная модель — CuNNy2 NVL, а не универсальный FSR: она обучена на скриншотах и CG visual novel и отдельно учитывает текст/line art.

Temporal upscalers уровня FSR 2/3 или DLSS нельзя честно применить к захваченному окну с тем же качеством, что внутри игры: захват отдаёт готовый цветной кадр, но не motion vectors, depth, jitter и exposure. Поэтому Asteria использует spatial pipeline и не обещает недоступные данные.

## Захват окна

Microsoft описывает `Windows.Graphics.Capture` как API получения кадров отдельного окна или дисплея с Direct3D frame pool. Для размера кадра и смены размера окна предусмотрен `Direct3D11CaptureFramePool` и его `Recreate`.

Источник: [Screen capture — Windows apps](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture).

Magpie сравнивает Graphics Capture, Desktop Duplication, GDI и DWM Shared Surface и рекомендует Graphics Capture для общей совместимости и плавности. GDI не поддерживает DirectComposition и имеет нестабильную производительность; Desktop Duplication хуже подходит для отдельного окна.

Источник: [Magpie — Comparison of capture methods](https://github.com/Blinue/Magpie/wiki/Comparison-of-capture-methods).

Практический выбор Asteria: Graphics Capture (`captureMethod = 0`), без захвата title bar, с Per-Monitor V2 DPI awareness.

## Алгоритмы

### CuNNy2 NVL

Автор CuNNy прямо указывает, что это компактный real-time CNN, обученный на скриншотах/CG визуальных новелл. Вариант `NVL` предназначен для visual novel и качественных иллюстраций. В исходном проекте качество моделей возрастает от veryfast до 8×32, а каждая модель масштабирует в 2 раза.

Источник: [funnyplanter/CuNNy](https://github.com/funnyplanter/CuNNy).

В Asteria:

- 4×24 NVL — рекомендуемый баланс;
- 8×32 NVL — максимум качества;
- 4×16 NVL — мягкий и более быстрый режим.

После фиксированного CNN ×2 нужен второй проход до физического размера экрана. Для общего случая используется FSR EASU; в soft-пресете — perceptual SSim downscale.

### Anime4K

Anime4K — модульный real-time набор для восстановления линий, denoise и апскейла anime-style изображения. Сам проект предупреждает, что он изначально оптимизирован скорее под 1080p anime → 4K, а SRGAN лучше восстанавливает сильно деградированное low-res изображение, хотя обычно тяжелее для real-time.

Источник: [bloc97/Anime4K](https://github.com/bloc97/Anime4K).

Поэтому Anime4K не выбран пресетом visual novel по умолчанию, но доступен для роликов и анимированных сцен.

### AMD FSR 1

FSR 1 — spatial upscaler текущего кадра. Его EASU-проход реконструирует границы, а RCAS возвращает локальную резкость. AMD указывает поддержку DirectX 11/12 и произвольного масштаба 1×–4×. В отличие от temporal FSR, он не требует истории кадра или motion vectors, поэтому подходит для внешнего захвата окна.

Источник: [AMD FidelityFX Super Resolution 1](https://gpuopen.com/fidelityfx-superresolution/).

В Asteria FSR выполняет две роли: быстрый универсальный режим и точная подгонка результата фиксированного CuNNy ×2 к экрану.

### Magpie как рендерер

Magpie — открытый DirectX 11 window upscaler с полноэкранным/оконным режимом, multi-monitor, FP16 и HLSL-эффектами. В его текущих эффектах присутствуют CuNNy2, Anime4K, FSR, FSRCNNX, RAVU, NNEDI3 и xBRZ. Документация отдельно отмечает CuNNy как семейство для visual novel-style изображений.

Источники: [Magpie repository](https://github.com/Blinue/Magpie), [Built-in effects](https://github.com/Blinue/Magpie/wiki/Built-in-effects).

Asteria запускает Magpie отдельным процессом, добавляет свои цепочки в JSON, скрывает служебный UI и управляет зарегистрированными hotkeys. Это сохраняет лицензионную и процессную границу: Magpie остаётся GPLv3-программой, Asteria не встраивает его бинарный код.

## NPU

Windows ML предоставляет общий ONNX Runtime и умеет динамически устанавливать execution providers для CPU, GPU и NPU. Для AMD доступен `VitisAIExecutionProvider`; vendor providers требуют Windows 11 24H2 build 26100+ и совместимый драйвер.

Источники:

- [What is Windows ML?](https://learn.microsoft.com/en-us/windows/ai/new-windows-ml/overview)
- [Supported execution providers](https://learn.microsoft.com/en-us/windows/ai/new-windows-ml/supported-execution-providers)
- [Install execution providers](https://learn.microsoft.com/en-us/windows/ai/new-windows-ml/initialize-execution-providers)
- [AMD Windows ML overview](https://ryzenai.docs.amd.com/en/latest/winml/winml_overview.html)

Обнаруженная целевая система:

- AMD Ryzen AI 7 H 450;
- Radeon 860M;
- NPU Compute Accelerator Device, driver 32.0.203.329;
- Windows 11 build 26200;
- дисплей 3200×2000 @ 60 Hz, 200% DPI.

NPU полезен для задач без непрерывного обмена кадрами с GPU. Windows AI Text Recognition извлекает текст, границы слов и уверенность локально и выполняется на NPU. Поэтому перевод под курсором захватывает только область 900×340 вокруг указателя, выбирает ближайшую OCR-строку и не отправляет изображение в сеть.

Источники: [Windows AI Text Recognition](https://learn.microsoft.com/en-us/windows/ai/apis/text-recognition), [Foundry Local](https://github.com/microsoft/Foundry-Local), [Foundry Local CLI](https://learn.microsoft.com/en-us/azure/foundry-local/reference/reference-cli).

Для полного перевода проверялись несколько локальных Qwen. Основная полнотекстовая модель — Qwen 3.5 2B; до 21 июля 2026 использовался GPU-вариант `qwen3.5-2b-text-generic-gpu:3`, а после регрессии execution-provider-ов Foundry 0.10.2 явно закреплён официальный CPU-вариант `qwen3.5-2b-text-generic-cpu:1`. Генеративные Qwen 0.5B/1.5B оказались неудачным инструментом именно для ранжирования словарных смыслов: они тяжелее специализированного классификатора, медленнее прогреваются и могут вернуть текст вне допустимого списка.

### Контекстный словарь: GlossBERT

Начиная с версии 0.9.2 выбор значения выполняет [GlossBERT](https://huggingface.co/kanishka/GlossBERT), закреплённый на ревизии `0cc3b83af5496e27ebcc95ef0cf37ea0a9281a7a` (MIT). Это BERT-классификатор задачи word-sense disambiguation: он получает предложение с отмеченным целевым словом и английское определение одного смысла, а не пытается заново перевести всю реплику.

Кандидаты берутся из полного слоя English Wiktionary: 147 583 английские словоформы и фразы, 406 179 русских переводов, выровненных с полными английскими определениями, частями речи и стилистическими метками. Одинаковые видимые русские варианты объединяются до сравнения; порог оценивает разрыв между разными результатами, а не между дублирующими определениями.

В версии 0.9.3 конвейер расширен, но сохраняет безопасное воздержание:

1. сначала независимо ищутся словарное выражение длиной до шести слов и точное полное предложение Tatoeba;
2. Tatoeba служит контекстным результатом или fallback и не может вытеснить найденное внутри строки лексическое выражение случайным длинным фрагментом; если точный русский перевод предложения однозначно содержит один словарный смысл с другой грамматической формой (`признак → признаков`), он выбирается без запуска модели;
3. формы выражений канонизируются ограниченно: `shook her head` сопоставляется с `shake one's head`, а `get separated from` распознаётся как единая результативно-пассивная конструкция;
4. модель ранжирует значения смыслового ядра, а близкие русские формулировки одного значения объединяются только при совпадении части речи и защитных семантических признаков;
5. результат принимается только при достаточном разрыве между различными группами значений; иначе ранжировщик воздерживается и оставляет пользователю до трёх компактных словарных вариантов;
6. только отсутствие словарной записи или ошибка ранжировщика могут вызвать полнотекстовый перевод, причём лишь при явно выбранном fallback `Автоматически`.

Порог `0,25` был заморожен на отдельном dev-наборе до открытия контрольного `ranker-holdout-v2.json`. На независимом CC0-наборе из 30 оригинальных однословных случаев CPU FP32 принял 18 решений, из которых 17 совпали с разметкой; NPU-путь принял 16 решений, из которых 15 совпали. Это маленький регрессионный набор, а не гарантия точности на произвольном тексте. CPU поэтому выбран как эталонный режим по умолчанию. NPU-путь на целевой машине был быстрее в прогретом микробенчмарке, но компиляция модели и конкретная версия AMD-драйвера могут слегка менять оценки.

Изначально ранжировщик дополнительно принудительно воздерживался, когда число глоссов превышало калибровочный размер пакета (32 на CPU, 4 на NPU). Позднее это правило было снято: парные оценки GlossBERT независимы и считаются фиксированными чанками, поэтому размер инвентаря не меняет отдельные оценки, а порог margin остаётся единственным критерием воздержания. Измерения через полный продакшн-конвейер (`AsteriaScale.Tests --ranker-benchmark`, словарь + группировка + изолированный worker) показали: после объединения смыслов ни один случай dev-набора и holdout-v2 не превышает 18 глоссов, а зонд из гиперполисемичных слов (`set`, `run`, `go`, `light`) достигает максимум 27 — предел CPU был практически недостижим, тогда как предел NPU принудительно гасил две трети рангируемых случаев. После снятия правила: dev-набор — CPU 17 принятых решений / 17 верных среди размеченных инвентарём случаев, NPU 17/17 с расхождением margin от CPU не более `0,01`; holdout-v2 (повторно открытый только для этого подтверждения) — CPU 8/8, NPU 8/8 при пяти воздержаниях. Строгий матчер бенчмарка не засчитывает морфологические варианты (`серьёзный` ↔ `серьёзным`), поэтому эти числа консервативны и не сравниваются напрямую с методикой 0.9.3.

Сверка порога между провайдерами (роадмап №3): на dev-наборе по дампам `--ranker-benchmark --dump` медианный сдвиг margin CPU↔NPU составил `0,005`, максимальный — `0,031` (один случай), пересечений порога `0,25` и различий в принятых решениях — ноль. Вывод: общий порог для обоих провайдеров обоснован, раздельная калибровка NPU не требуется. Для будущих сверок создан замороженный `ranker-holdout-v3.json` (46 случаев: междометия, переносные, разговорные, омонимы, большие инвентари; автор не сверялся с логами ошибок модели); набор не открыт. Обогащение sense-sidecar из ru-Wiktionary (роадмап №1: заимствование междометных поверхностей и синонимов-соседей по запятой при совпадении основы) выполнено: словари регенерированы из бит-идентичного исходного дампа (SHA-256 совпал с закреплённым), sidecar вырос с 406 179 до 455 814 выровненных поверхностей (+49 657 заимствованных). Матчер бенчмарка сделан толерантным к словоформам одиночных слов (общая основа ≥ 4–5 символов — зеркало рантайм-выравнивания): показ леммы «серьёзный» на ожидание «серьёзным» — верный ответ, а не промах покрытия. Итог: dev-набор — покрытие 26/30, решения 17/17 верных; holdout-v2 — покрытие 17/27 (было 13/27), решений 11, верных 10; новая единственная ошибка («framed» → «обрамлять» вместо переносного «подставить») — подлинный промах модели, ранее скрытый строгим матчером, целевой класс задачи №8. Остаточные пробелы покрытия — идиоматические многословные соответствия и междометия, отсутствующие в ru-Wiktionary.

Морфословарь (роадмап №2): русская глагольная морфология переведена с чисто суффиксных правил на лексикон OpenCorpora (154 527 форм — только инфинитивы и прошедшее время, через pymorphy3-dicts-ru, так как экспорт opencorpora.org недоступен; CC BY-SA). Леммы служат парадигмо-стабильными основами (супплетивные «пошёл/пошла/пошли» группируются под «пойти», что суффиксным основам недоступно), вид глагола берётся из граммем — пары «закрыть/закрывать» стали различимы для выбора вида без эвристики «-нуть». Суффиксные правила остаются обязательным fallback для слов вне лексикона. Dev-бенчмарк без деградации: покрытие 26/30, решения 17/17.

CPU использует исходный динамический FP32 ONNX. Полная dynamic-INT8-квантизация была удалена: на контрольном dev-наборе она сохранила только 34 из 37 решений FP32 и, в частности, сжала margin для `utter confusion` с `0,254` до `0,150`. Вход CPU дополняется только до самой длинной пары в текущем пакете, максимум до 128 токенов, что уменьшает стоимость пустого padding. NPU-вариант — заранее скомпилированный AMD Vitis EPContext; автоматического перехода между providers нет. Если NPU несовместим с машиной, приложение сохраняет обычный словарный результат и позволяет явно выбрать CPU. Модель работает в отдельном дочернем процессе, поэтому отключение режима и таймер простоя возвращают её память независимо от основного UI.

### Упрощённый словарный режим

Для минимальной задержки добавлен второй путь после того же NPU-OCR. Он не запускает генеративную модель:

1. OCR сообщает строку, слово и относительную позицию курсора;
2. для английского строятся выражения, содержащие выбранное слово, от самого длинного к короткому; отдельный лексический индекс допускает выражения до шести слов, не смешивая их с корпусом полных реплик Tatoeba;
3. при отсутствии выражения выполняется поиск слова и простая нормализация форм (`waiting → wait`, `was → be`);
4. для японского ищется самое длинное словарное совпадение, пересекающее символ под курсором;
5. при переходе в этот режим Qwen выгружается, а пустой сервер Foundry Local останавливается, чтобы не удерживать память модели.

Одиннадцать загружаемых словарных слоёв дают около 881 тысячи индексированных английских и японских слов/выражений. В их числе полный, а не частотный English Wiktionary с отдельным definition-aligned слоем для умного режима и точные MASSIVE-реплики, изолированные от лексического поиска. TSV-индексы сжаты gzip; подробные версии и лицензии источников перечислены в `THIRD_PARTY_NOTICES.md`. Источники: [FreeDict eng-rus](https://download.freedict.org/generated/eng-rus/), [Kaikki English Wiktionary](https://kaikki.org/dictionary/English/), [JMdict project](https://www.jmdict.org/), [EDRDG licence](https://www.edrdg.org/edrdg/licence.html), [Tatoeba downloads](https://tatoeba.org/downloads), [Amazon MASSIVE](https://github.com/alexa/massive).

Для real-time апскейла NPU по-прежнему полезен только при наличии модели, скомпилированной/квантованной под VitisAI, и zero-copy пути между capture texture и tensor. Текущие лучшие VN-модели поставляются как HLSL и уже исполняются FP16 на GPU. Перенос GPU texture → CPU/NPU tensor → GPU texture в каждом кадре способен увеличить latency и энергозатраты.

Следующий исследовательский этап:

1. экспорт CuNNy2 NVL в ONNX;
2. INT8/BF16 quantization и VitisAI compilation;
3. benchmark 1280×720 → 2560×1440 и 1920×1080 → 3200×1800;
4. сравнение end-to-end frame time, включая texture/tensor interop;
5. автоматический выбор NPU только при выигрыше по p95 latency и энергопотреблению.

## Критерии качества

Для будущего объективного сравнения нужны отдельные наборы:

- текст visual novel: OCR accuracy, edge overshoot/ringing, мелкие кандзи/кириллица;
- line art/CG: SSIM, LPIPS и слепое попарное сравнение;
- градиенты: banding count и chroma shift;
- real-time: median/p95 GPU frame time, dropped frames, input-to-photon latency;
- стабильность: resize, alt-tab, multi-monitor, DPI 100/150/200%, HDR on/off.

Без такого набора слово «самый совершенный» было бы маркетинговым утверждением. Реализованный пресет — исследовательски обоснованный сильный baseline, а не заявление о математически абсолютном качестве.

## Bi-энкодерный префильтр (роадмап №7)

MiniLM-префильтр (all-MiniLM-L6-v2, int8-индекс на 225 217 глоссов) сокращает
инвентарь до 12 лучших групп перед GlossBERT, включаясь только при >16
группах. Калибровка на dev-наборе и зонде: k=8 выбрасывал правильный смысл
гиперполисемичного «set» — margin взлетал с 0,229 до 0,335 и воздержание
превращалось в уверенную ошибку; при k=12 и пороге 16 решения и margin
побайтно совпадают с чистым cross-путём на всех измеримых случаях, CPU-выигрыш
~1,5× на инвентарях >16 групп, NPU нейтрален (прогретые раунды быстрее
стоимости энкодера). Замороженный ranker-holdout-v3 сознательно НЕ открыт:
при текущих порогах префильтр не активируется ни на одном случае замороженных

обязательными, а neural-решение используется только как консервативная

### Revised-v2: финальный контракт

GlossBERT теперь подключён ко всем EN full-text маршрутам (`Neural`, оба
полных fallback режима `Smart`, пакетный `Screen`) как **semantic validator**.
Первый prompt Qwen получает только deterministic scaffold. Accepted sense
хранит source, английское определение, выбранную и отвергнутые русские
поверхности, но не становится mandatory term. Явная отвергнутая поверхность без
выбранной — только prefilter для одного structured review, а не доказательство
ошибки. Если mandatory-термины соблюдены, review получает полностью английские
служебные инструкции, English source, предыдущий русский перевод и английские
definitions как non-authoritative hypotheses, но не получает выбранные или
отвергнутые neural-поверхности. Строгий ответ `KEEP` сохраняет естественный
синоним/словоформу или отвергает неподходящую GlossBERT-гипотезу;
`FIX|<перевод>` предлагает коррекцию.

При mandatory miss semantic review не совмещается с исправлением: единственный
дополнительный запрос использует прежний deterministic fidelity prompt, затем
sense-prefilter пересчитывается для диагностики. Кандидат `FIX` или
deterministic retry принимается только при строгом лексикографическом улучшении
`(mandatory violations, unresolved sense flags)`; `KEEP` сохраняет первый
ответ. Валидный `FIX` является окончательной semantic adjudication Qwen, но
снимает flag только для содержательно изменившегося очищенного текста и не
может ухудшить mandatory-компонент. Empty/invalid output и prompt echo никогда
не заменяют первый ответ и не кэшируются. Trusted exact dialogue bypass
сохраняется, если он совместим с deterministic terms.
Batch-ранжирование последовательно и имеет общий circuit на операцию. Provider
задаётся явно без fallback; кэшируются selected и abstained решения, но не
errors. Критерий GlossBERT остаётся исключительно margin-only с замороженным
порогом `0.25`.

После revised-v2 matcher отвергнутых поверхностей сделан консервативным:
закрытые парадигмы допускают падеж/число, но не производные существительные и
совпадения по общему префиксу. Финальный strict-v3 English-review dev-прогон
принят как dev-подтверждение:

- chrF mean/median/min — `0.591288` / `0.563388` / `0.064103`;
- anchors — `60/61` (`98.361 %`), residual English — `0`, строк с латиницей —
  `0`;
- latency median/max — `1230.5/6666` мс;
- deterministic terms — `26/27`, exact bypass — `4`, retries — `9`,
  mandatory violations — `4 → 1`;
- sense flags — `6 → 3`, sense-prefilter cases — `6`; structured review:
  `KEEP=3`, `FIX=0`, `rejected=2`, `failed=0`. Шестой sense-prefilter совпал
  с mandatory miss, поэтому получил только deterministic fidelity retry и
  остался с outcome `NotIssued`;
- GlossBERT — `requests=140`, `selected=77`, `abstained=63`, `errors=0`,
  `skipped=2`; neural `terms=0`, `hints=100`.

Gate №14 пройден: anchors не ниже `59/61`, chrF выше чистого Qwen-baseline,

## VN Layer 2.0 — безопасное расширение данных (22 июля 2026)

Исследовательский вывод: массовое добавление пар `слово → перевод` в прежний
авторитетный VN-файл ухудшило бы систему. Оно одновременно перекрыло бы broad
словари, подавило definition-aligned ранжирование GlossBERT и превратило бы
непроверенные поверхности в residual/full-text ограничения. Поэтому данные
разделены по назначению, а не только по источнику:

- `hard`: 103 вручную проверенных display/residual override;
- `soft`: 52 ключа и 102 definition-aligned sense rows для карточки и
  GlossBERT без авторитетного override;
- `scaffold`: 21 отдельно проверенный full-text anchor, невидимый в карточке;
- `exact dialogue`: 9 837 полных реплик, которые не участвуют в лексическом
  поиске и имеют самый низкий приоритет.

В структурированном curated-источнике 183 записи. Это 160 уникальных ключей и
176 назначений ролей: 16 hard-выражений также отдельно подтверждены как
scaffold, а семь soft-ключей имеют дополнительные смыслы. Runtime сохраняет
контракт `user > hard > merged broad/soft > exact dialogue`; scaffold находится
в отдельном индексе. Hard больше не становится mandatory автоматически.
Инфлектированный scaffold возвращает фактический span предложения и уступает
пересекающейся пользовательской фразе, даже когда та многозначна и ranker
воздержался. Производные формы VN-hard исключены: exact broad `lolling` и
`damning` не превращаются в `lol` и `damn`. Продвижение soft-леммы выше точного
broad-слова ограничено регулярной глагольной морфологией; регрессии
`saw → see` и реальная `lemming → lemme` закреплены отрицательными тестами.

Для массового exact-слоя выбран официальный Amazon MASSIVE 1.1 (CC BY 4.0),
потому что EN/ru-RU локали выровнены стабильным record ID и содержат judgments.
Архив (`40 251 390` байт) и оба JSONL member закреплены размером и SHA-256 в
source lock. Из 16 521 пар до конфликторазрешения прошли 9 915; 11 были
эквивалентными дублями, итог — 9 837 ключей. Отброшено 6 673 записи:
3 730 с локализованными slot values, 1 306 со слабыми judgments, 1 319 длиннее
10 слов, 181 короче двух слов, 70 с латиницей в русском результате и 67 с
конфликтующим нормализованным ключом. Числовые источники и строки без кириллицы
в этой версии не добавили отдельных отклонений после более ранних фильтров.

Transform из lock теперь проверяется как точный frozen-контракт. Curated и
MASSIVE нельзя собирать по отдельности: семь gzip-результатов сначала создаются
в staging-каталоге, затем заменяются с manifest-last и rollback. Manifest v2

## Полевой аудит Ever17 Himmel Edition — 22 июля 2026

Десять снимков ручного прогона показали, что главная текущая потеря качества
полного перевода происходит до Qwen: в пяти случаях модель получила не полную
реплику, а OCR-фрагмент (`Er.`, хвост `things to watch out for`, середину
`heme park and tell you a few`, только второе предложение). Даже при полном
источнике остались независимые semantic-ошибки Qwen: `the other day → сегодня`,
неестественное `told me a joke`, ошибка согласования в `let us inside` и
неверная интерпретация `who cares`. Метки говорящего часто терялись, поэтому
исчезали выбор `ты/вы` и род.

Первопричина повреждённых реплик — не размер карточки: усечённый source уже
попадал в историю. Sentence OCR ограничивал захват `2400×720`, тогда как
ручной прогон шёл на экране шириной около 3200 пикселей; геометрическое
объединение строк и выделение до первого `.?!` дополнительно ломали многоточия
и составные реплики. Это отдельный обязательный этап **OCR utterance
integrity** перед контекстной памятью №15: адаптивный захват текстового блока,
сохранение speaker label и всей реплики, тесты на ellipsis/multi-sentence и
явная provenance `OCR|HOOK` в карточке.

Text-hook в этом прогоне фактически не участвовал. В сохранённых настройках
`TextHookEnabled=false`, `TextractorDirectory` пуст, хотя у профиля
`ever17PC_us` per-profile Hook был включён. После установки Textractor в
`C:\Textractor` найдены оба CLI; Ever17 — 32-битный процесс и должен получать
`x86\TextractorCLI.exe`. Исполняемый файл импортирует `TextOutA`, поэтому
штатные GDI-hooks Textractor являются разумным первым путём; наличие полного
текста подтверждается только фактическим свежим совпадением hook-предложения,
а не успешным attach. Для этого карточке нужен видимый маркер `HOOK`; при
отсутствии совпадения остаётся OCR. Специальный H-code для точной Himmel-сборки
в проверенной базе не найден и должен добавляться только после живой проверки,
а не угадываться по другой версии EXE.

В `hover-translation.log` пользовательского прогона обнаружена одна настоящая
ошибка в `16:01:00`: `GlossBertRankerException: The selected target does not
occur in the source context`. Full-text pipeline корректно продолжил работу,
но факт означает рассинхронизацию target/span после повреждения или
нормализации OCR-контекста. Записи `synthetic neural scaffold failure` в том
же файле созданы smoke-тестами намеренно и не относятся к ручному запуску.

Регрессия масштабирования оказалась отдельной гонкой старта Magpie: Asteria
считала скрытое pre-render окно `Magpie Scaling Window` уже активной сессией,
увидела ещё не опубликованный `Magpie.SrcHWND == 0` и останавливала масштаб
через примерно `145–170` мс. Ошибок GPU, capture или shader в циклах не было.
Исправление должно считать сессию готовой только после видимости окна и
совпадения `SrcHWND` с ожидаемым источником, а остановку посылать через hotkey
активного fullscreen/windowed режима.

Frozen ranker/translation holdout во время полевого аудита не открывались.

### DPI-виртуализация источника — 23 июля 2026

Живое сравнение Ever17 выявило критический фактор вне shader-пресетов: при
глобальном масштабе Windows выше 100% DPI-unaware игра сначала bitmap-scaled
самой Windows, и Magpie захватывает уже увеличенный и интерполированный кадр.
При 200% это до четырёх раз больше входных пикселей; наблюдаемая нагрузка резко
возрастает, а различия CuNNy/FSR становятся менее заметны. Стандартный
compatibility override `Application` (`~ HIGHDPIAWARE`) при сохранении удобных
200% рабочего стола воспроизвёл качество и нагрузку режима 100%.

В Asteria добавлен `DpiCompatibilityService` и блок «DPI игры» для выбранного
EXE. Изменение записывается только в HKCU, не требует администратора и вступает
в силу после перезапуска игры. Полное предыдущее значение AppCompat Layers
сохраняется для точного возврата. Если значение затем меняется извне, Asteria
отказывается от destructive restore; ручной уже существующий override только
показывается как активный. Release build завершился без предупреждений и
ошибок, полный smoke — `37/37`, включая registry-контракт на fake store и
реальный жизненный цикл Magpie. Frozen holdout не открывались.

## Smart Dictionary Quality Foundation, Magpie и Textractor — 22 июля 2026

Фаза A выполнена по полевым дефектам Ever17. Trusted user/VN-hard и чистые
однозначные фразы сохраняют быстрый bypass, а неоднозначные broad-фразы теперь
попадают в definition-aligned разрешение смыслов. Выбор русской поверхности
сначала отбрасывает Latin/meta/unbalanced мусор и только затем учитывает
контекст, морфологию, регистр и источник. Добавлены консервативные fast-path

Генератор теперь делит глоссы только по запятым верхнего уровня, отбрасывает

записей из 11 источников и lazy sense-index на `147 840` ключей / `446 855`

открывался. CPU-прогон: 45 ранжируемых случаев, 16 phrase bypass, три
auto-resolved и один no-inventory; expected-label coverage `37/45` (`82,2 %`).
Приняты все 21 размеченное решение и все `21/21` верны; 16 размеченных случаев
воздержались. С учётом строгой проверки детерминированных ответов end-to-end
correct coverage — `33/65` (`50,8 %`), median select latency `180` мс,

минимум 20 случаев, accepted precision `90 %`, expected-inventory coverage
`70 %`, decision coverage `45 %`, end-to-end correct coverage `45 %`.

## Нужен ли GlossBERT и Register/18+ audit — 23 июля 2026

Проверка текущего `eng-rus-enwiktionary-senses.tsv.gz` показала, что adult и
разговорные данные генератором не цензурируются. В sidecar находятся `6 428`
строк с грубой маркировкой для `1 022` ключей, `13 301` строка с жаргонной маркировкой для
`3 907` ключей, `6 460` разговорных строк для `1 784` ключей и `1 400`
диалектных строк для `402` ключей; категории пересекаются. Эвристический поиск
сексуальной семантики по key/definition нашёл `6 419` sense rows для `2 513`
ключей — это оценка покрытия, не готовая классификация. Слова с обычным и
adult-смыслом (`cock`, `pussy`, `horny` и подобные) имеют раздельные английские
definitions, то есть definition-aware ranker принципиально может их различать.

Обнаруженный архитектурный дефект — не отсутствие словаря, а смешение
пригодности и регистра: `SmartDictionarySenseResolver.RegisterRank` ставит
neutral выше colloquial/slang/vulgar даже внутри уже выбранного смысла.
Full-text prompt также не требует сохранять эксплицитность. Поэтому данные
покрывают класс, но production пока не гарантирует перевод без смягчения.
Этому выделена фаза 14.2C с отдельными Smart/full-text dev-наборами и метриками
semantic correctness, register fidelity, over-strengthening и censorship.

[GlossBERT](https://aclanthology.org/D19-1355/) признан не незаменимой моделью,
а корректным production baseline.
Его полезная роль — независимо и детерминированно сравнить контекст с
произвольными английскими Wiktionary definitions, вернуть стабильный GroupId и
воздержаться по margin без генерации русского текста. Это хорошо совпадает с
архитектурой Asteria и не заменяется обычным словарём или Qwen без потери
контроля. Недостатки: BERT-base 2019, обучение на SemCor/WordNet, линейная
стоимость cross-encoding и отсутствие VN/register-доменного обучения.

Исследованные направления:

- [gloss-informed bi-encoder BEM](https://aclanthology.org/2020.acl-main.95/)
  улучшает редкие/невиданные смыслы и позволяет
  предвычислить gloss vectors; в Asteria эта идея уже реализована как MiniLM
  top-12 prefilter, но bi-encoder не должен единолично принимать тонкие решения;
- [ESCHER](https://github.com/SapienzaNLP/esc) (ALL `80,7`) и
  [ConSeC](https://github.com/SapienzaNLP/consec) (`82,0` SemCor, `83,2` с
  WNGT) сильнее старого GlossBERT на стандартном WordNet WSD и показывают
  пользу совместного чтения кандидатов/соседних смыслов. Их официальные
  реализации имеют соответственно CC BY-NC 4.0 и CC BY-NC-SA 4.0, требуют
  собственную PyTorch/WordNet обвязку и не являются допустимой прямой
  зависимостью поставки;
- [enhanced sense representations](https://aclanthology.org/2021.findings-emnlp.365/)
  (definition + synonyms/examples/hypernyms) достигали `82,0 F1`, поэтому
  качество sidecar-входа — самостоятельный рычаг;
- [исследование ACL 2025](https://aclanthology.org/2025.acl-long.113/)
  показывает преимущество DeBERTa-v3 среди проверенных encoder-only PLM для
  разделения смыслов; официальный
  [DeBERTa-v3-small](https://huggingface.co/microsoft/deberta-v3-small) имеет
  MIT-лицензию и 6 слоёв.
  [ModernBERT-base](https://huggingface.co/answerdotai/ModernBERT-base)
  доступен под Apache-2.0, но его
  архитектурные ops и реальная NPU-производительность требуют прототипа.

Историческое решение 22 июля (заменено готовыми-model bake-off 29 июля): не
удалять GlossBERT и не переносить академическую SOTA-модель напрямую. №8 был
превращён в same-build bake-off текущего hybrid baseline,
DeBERTa-v3-small cross-encoder и, при совместимости, ModernBERT-base с
одинаковым domain fine-tune. Qwen используется только как необязательный
офлайн-генератор черновых кандидатов.
Замена происходит лишь при сохранении высокой precision, приросте end-to-end
coverage, меньшем abstention и приемлемых CPU/NPU ресурсах; иначе production
остаётся на GlossBERT. Frozen holdout при исследовании не открывался.

### Gold/silver протокол для WSD и полного перевода — 23 июля 2026

После уточнения роли учителя №8 и №19 переведены с Qwen-centric distillation на
контролируемый gold/silver процесс. Codex отвечает за versioned annotation
guide, ручную разметку сложного gold, исправление кандидатов и арбитраж всех
расхождений. Это не означает прямой перенос возможностей Codex в веса:
сохранённые решения становятся обычными обучающими примерами, после чего
DeBERTa или переводчик обучается воспроизводимым локальным скриптом.

Для WSD планируются 1 500–3 000 gold и 50–100 тыс. silver-пар. Приоритет silver
отдан sense-linked примерам и distant supervision; локальная Qwen может только
массово предложить три варианта. В train допускаются лишь единогласные ответы,
прошедшие span/POS/inventory-проверки; остальные возвращаются Codex. Отдельные
абляции `base → gold → gold+silver` не позволят скрыть ухудшение за объёмом
псевдоразметки.

Для полнотекстового en→ru перевода планируются 2 000–5 000 Codex-gold реплик и
100–300 тыс. лицензированных silver-реплик. Единица данных сохраняет предыдущие
ходы, говорящего, каркас, регистр, обязательные якоря, запрещённые смысловые
сдвиги и несколько допустимых references. Qwen производит кандидатов, а не
истину; неоднозначность, имена, местоимения, юмор и register/18+ входят в
обязательную очередь ручного арбитража. Для decoder-студента предусмотрены SFT
и preference-пары «исправленный вариант против конкретной ошибки».

Внешний frontier API — отдельный опциональный источник кандидатов только после
явного разрешения на сеть и стоимость. Пользовательские приватные скрипты по
умолчанию наружу не отправляются. Dev и frozen holdout не показываются ни
одному учителю и не входят в train. Полнотекстовый студент допускается в
production лишь при сохранённой смысловой точности, anchors не хуже `60/61`,
register fidelity не ниже `90 %`, нулевом residual English/цензурных заглушках
и измеримом выигрыше CPU latency/памяти. Если gate не пройден, текущие
GlossBERT и Qwen остаются production baseline. Frozen holdout при составлении
этого плана не открывался.

### Проверка новых моделей и коммерческих словарей — 23 июля 2026

Проверена предложенная подборка на актуальном состоянии эталонной машины:
`23,7 ГБ` общей RAM, Radeon 860M с `4 ГБ` заявленной adapter memory и Foundry
Local 0.10.2. [Gemma 4 26B-A4B](https://ai.google.dev/gemma/docs/core)
существует и действительно активирует около 4B параметров на токен, но Google
оценивает Q4_0 footprint примерно в `14,4 ГБ`
без KV cache и runtime и отдельно подчёркивает, что все 26B параметров должны
быть загружены. Поэтому это не лёгкая live-модель для Asteria: она конкурирует
за общую память с Windows, Magpie, OCR, словарями и ranker. Использовать её
имеет смысл только как необязательного офлайн-учителя.

В фактическом каталоге Foundry доступны `qwen3.5-9b` CPU (`7,9 ГБ`),
`qwen3-14b` CPU (`9,3 ГБ`), а для `qwen3.5-2b-text` каталог показывает GPU
вариант (`1,3 ГБ`), хотя production из-за provider-регрессии по-прежнему явно
закреплён за CPU-вариантом;
Gemma 4, TranslateGemma и Saiga отсутствуют. Наиболее интересный новый кандидат
обнаружен вне исходного списка: официальный
[`google/translategemma-4b-it`](https://huggingface.co/google/translategemma-4b-it) —
специализированная модель Google Translate для 55 языков. Её нужно ставить в
первый en→ru bake-off перед общей Gemma 4, но для интеграции потребуется свой
worker/export и принятие Gemma terms. Модели при этом не скачивались.

[Habr-результат `89,57`](https://habr.com/ru/articles/951416/) для
`saiga_yandexgpt_8b` — настоящий опубликованный
COMET-замер, но он получен на трёх независимых фрагментах одной главы HPMOR,
без диалогового контекста, на RTX 4090/3090; автор сам отмечает возможное
попадание текста в train. Это полезный кандидат-сигнал, но не переносимый
benchmark Asteria. Кроме того,
[custom-лицензия YandexGPT](https://huggingface.co/yandex/YandexGPT-5-Lite-8B-pretrain/blob/main/LICENSE)
запрещает создание
ряда оскорбительных и порнографических материалов, что несовместимо с нашим
обязательным переводом исходного register/18+ без смягчения. Apache-2.0
[`saiga_nemo_12b`](https://huggingface.co/IlyaGusev/saiga_nemo_12b) можно
оставить только в GGUF research lane.

Коммерческие онлайн-словари не превращаются в bundled layer от того, что ими
можно бесплатно пользоваться в браузере. У
[Multitran](https://www.multitran.com/m.exe?a=421) нет открытой лицензии на
массовое копирование базы; [Reverso Context](https://context.reverso.net/translation/about)
показывает данные из уже
переведённых текстов без пригодной для нашей поставки открытой лицензии;
[`WordReference`](https://www.wordreference.com/english/TermsOfService.aspx)
прямо запрещает automated collection, derivative dictionaries, ML и
использование как основы машинного перевода. Их допустимо применять для
ручной проверки отдельных gold-примеров без копирования корпуса. English
[`Wiktionary`](https://en.wiktionary.org/wiki/Wiktionary:Copyrights) остаётся
правильным массовым источником при соблюдении CC BY-SA/GFDL; для дополнительных
фраз нужны исходные открытые корпуса, а не выдача
Reverso. Frozen holdout при этом исследовании не открывался.

## Зафиксированный baseline ранжировщика для №8 — 25 июля 2026

Первый пункт карточки №8 («зафиксировать baseline») выполнен как
воспроизводимый артефакт, а не как строчка в логе. `--ranker-benchmark`
получил аргумент `--ranker-report <path>`, который пишет единую JSON-схему;
её обязан выдавать каждый кандидат bake-off. Смысл — сделать требование
«same-build сравнение» и «одинаковые dev-отчёты всех кандидатов» механическим:
и набор-бенчмарк, и каждый модельный артефакт закреплены SHA-256, поэтому
отчёт не может незаметно описывать не тот вход, что заявляет.

Эталон GlossBERT/CPU: `assets/Ranker/baselines/glossbert-cpu.json`.

Три метрики из требуемых №8 раньше не измерялись вообще; теперь они есть:

- **Peak working set воркера — `677 МБ`** (`709 918 720` байт). Читается с
  процесса воркера до его выгрузки, потому что модель живёт там, а не в
  harness. Из правила выбора №8 («не ухудшить CPU latency/peak memory более
  чем на 20 %») бюджет кандидата — **`813 МБ`**.
- **Размер артефактов — `799 МБ`** суммарно по пяти файлам: GlossBERT FP32
  `418 МБ`, NPU-контекст `89 МБ` + `118 МБ`, MiniLM `86 МБ`, индекс глоссов
  `87 МБ`.
- **Максимальная задержка select — `3 488 мс`** (медиана `228 мс`,
  large-inventory медиана `662 мс`, 45 замеров).

Решения совпали с ранее записанным прогоном: 45 ранжируемых, 16 phrase
bypass, 3 auto-resolved, 1 no-inventory; coverage `37/45` (`82,2 %`);
`decided=21`, `correct=21` (accepted precision `100 %`); воздержаний 16;
decision coverage `56,8 %`; end-to-end `33/65` (`50,8 %`); медианный margin
`0,305`; pipeline `cross` во всех 45 случаях. Frozen holdout не открывался.

**Оговорка по полю `DictionaryVersion`.** Оно информационное и не
content-addressable: `ComputeVersionToken` строится из имён, размеров и
**времён модификации** файлов, поскольку его задача — инвалидация кэшей, а не
идентичность содержимого. На другой машине или после перевыкачки словарей оно
отличается при том же содержимом. Сравнивать кандидатов по нему нельзя;
для этого служат SHA-256 набора и артефактов.

**Блокер, обнаруженный при фиксации.** Baseline №8 требует ещё
«register/18+ dev из №14.2C», а `ranker-register-benchmark.json` (минимум 120
CC0-случаев) не создан: §14.2 фаза C помечена «запланирована до №8», и
рекомендуемый порядок роадмапа — `14.2B → 14.2C → 14.3 → 8`. Поэтому
зафиксированный baseline полон по семантической части и **неполон по
register-части**; объявить победителя bake-off до закрытия 14.2C нельзя, так
как правило выбора требует прохождения register/18+ gates.

## Register fidelity: ядро №14.2C — 25 июля 2026

Реализованы три из шести пунктов фазы C. Главное, что выяснилось при
реализации и меняет трактовку задачи: **метка регистра описывает английский
смысл, а не русскую поверхность**. Генератор берёт её из тегов/категорий
sense-а en-Wiktionary (`_kaikki_style_prefix`) и приписывает всем переводам,
собранным из этого смысла. Значит прежний `RegisterRank`, штрафовавший `груб.`
на 8 и `жарг.` на 7, не «выбирал безопасную формулировку» — он выбирал
формулировку, не соответствующую источнику.

Словарь маркеров оказался закрытым и маленьким: во всём английском sidecar
семь токенов — `устар.` 18 865, `перен.` 16 468, `жарг.` 14 407, `груб.` 7 032,
`разг.` 6 578, `диал.` 1 773, `лит.` 1 427 — в 204 сочетаниях. Поэтому парсер
перечисляет их явно, а не угадывает. `перен.` сознательно не регистр: это
описание значения, а не резкости, и трактовка его как маркера сделала бы
обычные метафоры «помеченными».

`RegisterMatchRank(expected, candidate)` — симметричное расстояние по шкале
`Neutral < Literary < Archaic < Dialect < Colloquial < Slang < SexualDomain <
Vulgar`. Симметрия отражает требование карточки: запрещено и смягчение, и
усиление. Группировка senses переносит сильнейший маркер слитых строк, иначе
грубое чтение, объединённое с нейтральным по near-equivalent определению,
теряло бы разметку.

**Прогон `--ranker-benchmark` дал решения, тождественные baseline** (45
ранжируемых, `37/45`, `21/21`, 16 воздержаний, медианный margin `0,305`,
end-to-end `33/65`, peak WS `677 МБ`). Это не подтверждение качества, а
подтверждение отсутствия регрессии: в dev-наборе нет ни одного случая с
register-неоднозначностью, поэтому он к этому изменению **слеп**. Ровно
поэтому фаза C требует собственных наборов `ranker-register-benchmark.json`
(≥120 случаев) и `translation-register-benchmark.json` (≥40 реплик) — без них
измерить register fidelity нечем, а gates `≥90 %` посчитать не на чем.
Оба набора ещё не созданы.

Изменены два ранее закреплённых ожидания: строка причины выбора поверхности
(`safer dictionary register` → `matching sense register`) и точный текст
full-text промта, который теперь содержит правило регистра. Оба изменения —
следствие смены контракта, а не подгонка под падение; регрессионный тест
`VerifyRegisterFidelity` падает на старой политике с выбором «рассердиться»
вместо «взбеситься».

## Баг генератора: метки регистра статьи протекали в отдельные смыслы — 25 июля 2026

Обнаружен при подготовке набора `ranker-register-benchmark.json` для фазы
№14.2C. Прежде чем писать 120 случаев, я проверил, на какие данные они будут
опираться, — и они оказались непригодны как эталон.

**Механизм.** Kaikki вешает большинство translation-box английских статей на
уровень **статьи**, а не смысла. `build-dictionaries.py` для таких переводов
склеивал метки **всех** смыслов статьи (`" ".join(dict.fromkeys(style_prefixes))`)
и приписывал склейку каждому переводу.

**Доказательство на источнике.** Смысл `come` «to move nearer to the point of
perspective» в kaikki несёт `tags: ['intransitive']`, `raw_tags: None`,
`categories: []`. Смысл «to achieve orgasm» несёт `tags: ['intransitive',
'often', 'slang', 'vulgar']`, `categories: ['Sex']`. Источник чистый и строго
посенсовый. В поставленном sidecar та же строка выглядела как
`[жарг. груб. перен. устар. жарг.] verb = приходить | to move nearer`.

**Масштаб на 45 063 помеченных строках:**

| Признак | Значение |
|---|---|
| Ключей, где все помеченные строки несут одну и ту же метку | 12 736 из 13 897 (**91,6 %**) |
| Меток с повторяющимися токенами (`жарг. жарг.`) | 2 903 (6,4 %) |
| Строк с `груб.` при заведомо нейтральном определении | ≥128 |

91,6 % — решающий признак: посенсовые метки давали бы разные значения у разных
смыслов одного слова, а одна метка на всю статью получается именно склейкой.

**Исправление.** `_entry_level_register` применяет метку к entry-level
переводам только если **все** смыслы статьи на ней сходятся. Статья с
равномерно грубыми значениями маркер сохраняет; статья, где грубое значение
соседствует с обычным, не получает ничего — непомеченный смысл является
положительным свидетельством неоднородности. Порядок вывода канонизирован по
`KAIKKI_STYLE_TAGS`, поэтому повторов токенов больше не возникает.

**Связь с уже сделанным.** Прежняя политика выбора поверхности «предпочитай
нейтральное» была случайно **устойчива** к этим меткам: она их игнорировала.
`RegisterMatchRank` из фазы C меткам доверяет, поэтому на испорченных данных
могла усилить нейтральный смысл — тот самый дрейф, который ТЗ запрещает. На
поставленном словаре это оставалось почти no-op (внутри группы все строки
несли одну и ту же склейку, расстояние нулевое), что и подтвердили три
прогона бенчмарка с тождественными решениями. Регенерация делает метки
осмысленными, и только после неё имеет смысл писать register-набор.

Регрессия закрыта тестами `RegisterLabelTests` в
`scripts/test-build-dictionaries.py`; на старом генераторе end-to-end тест
падает со строкой `('приходить', 'to move nearer', 'жарг. груб.', 'verb')`.

затронутого парсера, остальные слои не тронуты.

|---|---|---|
| Строк в sidecar | 447 097 | 447 097 |
| Потеряно / добавлено смыслов | — | **0 / 0** |

| Метки с повторяющимися токенами | 2 903 | **0** |

Изменился только столбец регистра: сверка по тройкам

## Первое измерение register fidelity — 25 июля 2026

Собран отдельный harness `--register-benchmark <set> <workerBase> [cpu|npu]`
(+ `--register-report`). Он намеренно отделён от калибровочного: тот отвечает на
вопрос «выбран ли верный смысл», этот — «сохранена ли резкость выбранного».

Регистр выбранной поверхности читается **не** из её текста, а по `SourceIndex`
выбранного outcome — обратно в тот ряд инвентаря, который конвейер реально
выбрал. Иначе измерялся бы разбор меток, а не работа конвейера.

**Baseline на `ranker-register-benchmark.json` (135 случаев, CPU):**

```
cases=135  decided=66  abstained=69  unresolved=0
masked-euphemistic  n=41 decided=15 semantic=14/15 (93,3 %) register=15/15 (100 %)  strengthened=0
neutral-vulgar      n=30 decided=18 semantic=15/18 (83,3 %) register=15/18 (83,3 %) strengthened=1
sexual-ordinary     n=34 decided=16 semantic=13/16 (81,2 %) register=13/16 (81,2 %) strengthened=1
slang-colloquial    n=30 decided=17 semantic=15/17 (88,2 %) register=16/17 (94,1 %) strengthened=0

semantic accepted precision : 57/66 (86,4 %)   гейт 90 % — НЕ пройден
register fidelity           : 59/66 (89,4 %)   гейт 90 % — НЕ пройден (не хватает одного случая)
no unjustified strengthening: 64/66 (97,0 %)   гейт 95 % — пройден
```

**Два гейта из трёх не пройдены. Это и есть измеренная точка старта фазы C**, а
не регрессия: до появления набора register fidelity никем не измерялась, и
все предыдущие изменения в этой области возвращали решения, тождественные
dev-baseline, именно потому, что dev к ним слеп. Гейты взяты из карточки и
**не понижались** под фактический результат — иначе набор терял бы смысл.

**Что первый прогон измерил на самом деле — дефекты harness.** Полезно
зафиксировать, потому что оба искажали цифры в разные стороны:

1. `unresolved=4`, все — случаи с `damn`. Причина не в конвейере: `damn` есть в
   VN-hard слое, а sidecar намеренно исключает пользовательские и VN-hard ключи,
   поэтому слово резолвится кураторским значением и до ранжирования смыслов не
   доходит. Случаи были невалидны: авторская валидация проверяла файл sidecar, а
   не рантайм-lookup. Удалены; в `tools/build-register-benchmark.py` добавлен
   раздел о достижимости.
2. `semantic 81,8 %` было занижено строгостью метрики. У смысла обычно несколько
   равноценных синонимов (`говнюк`/`мудак` передают одно определение), а
   ожидаемый перевод называет один. Сравнение строк штрафовало верно выбранный
   смысл за «не тот» синоним. После перехода на сравнение по английскому
   определению — `86,4 %`.

Единственное число, достоверное с первого прогона, — register fidelity: оно и
осталось `89,4 %`.

**Опровергнутое предсказание.** Я ожидал, что вся masked-корзина окажется
недостижимой: `*` не входит в `EnglishLookupTokenRegex`. Неверно — 15 из 41
случая разрешились, register fidelity на них `100 %`. `ExtractEnglishLexeme`
расширяет токен до границ пробелов, поэтому `f*ck` попадает в lookup целиком, а
`NormalizeEnglish` внутреннюю пунктуацию сохраняет. Следствие для роадмапа:
пункт «masked spellings как lookup-кандидаты» **частично уже работает** и перед
реализацией требует перепроверки объёма.

**Открытый вопрос.** Воздержаний `69/135` (51 %) против `16/37` на dev-наборе;
в masked-корзине `26/41`. Гипотеза: у таких слов десятки поверхностей внутри
немногих смыслов, margin между группами низкий. Проверять до изменения порога
`0,25` нельзя — это отдельная работа с собственным прогоном.

### Где именно происходят промахи register fidelity (диагностика маршрутов)

В отчёт добавлены `Route` (`single-outcome` / `model` / `abstained`),
`OutcomeCount` и `Margin`, чтобы отличить дефект маршрутизации от качества
модели. Результат на том же наборе:

```
маршруты:  abstained 69   model 53   single-outcome 13

single-outcome  n=13  semantic=13/13  register=13/13   (100 %)
model           n=53  semantic=44/53  register=46/53   (83 % / 87 %)
```

**Все 7 промахов register fidelity прошли через модель.** Детерминированный
путь с единственным исходом не ошибся ни разу. Рабочая гипотеза «модель просто
не спросили, дефект в маршрутизации и чинится дёшево» **опровергнута**.

Существеннее: модель ошибается **уверенно**, а не на грани.

| Случай | margin | выбрано | ожидалось |
|---|---|---|---|
| `bread-money` | `0,892` | хлеб | бабки |
| `crack-vagina` | `0,647` | щель | (регистр) |
| `ice-drug` | `0,592` | лёд | айс |
| `crib-home` | `0,546` | детская кроватка | хата |
| `ass-animal` | `0,538` | осёл | (регистр) |
| `sucker-fool` | `0,405` | лох | дурить |
| `bush-hair` | `0,272` | куст | волосня |

При пороге `0,25` механизм воздержания эти случаи поймать не может: они лежат
кратно выше порога. Поднятие порога тоже не решение — `0,892` близок к
максимуму, и такой порог погасил бы почти все верные решения.

**Разделение промахов по природе:**

- **5 — подлинные ошибки WSD модели** (`bread`, `crib`, `bush`, `sucker`,
  `ice`): `semanticOk=false`, выбран буквальный смысл вместо сленгового.
  Лечится только качеством ранжировщика, то есть карточкой №8.
- **2 — атрибуция регистра слитого outcome** (`ass-animal`, `crack-vagina`):
  `semanticOk=true`, пользователь видит правильное слово, но регистр взят из
  произвольного слитого смысла (см. выше).

**Практический вывод, меняющий порядок работ.** Гейт register fidelity `90 %`
**достижим без №8**: починка слияния даёт `61/66 = 92,4 %`. Гейт semantic
accepted precision `90 %` — **не достижим** без №8: оставшиеся 5 промахов
модельные, и `57/66 = 86,4 %` упирается в текущий GlossBERT. Это первое
количественное подтверждение мотивации карточки №8 на register-данных.

Отдельно: 69 воздержаний из 135 (51 %) при 53 решениях модели. Сочетание
высокой доли воздержаний с уверенными ошибками — сигнал о калибровке на этом
классе данных, но менять порог `0,25` без отдельного прогона нельзя.

### Регистр как часть идентичности outcome — гейт register fidelity взят

Реализован вариант (а): `CreateRankerPlan` объединяет смыслы по паре
`(нормализованная поверхность, регистр)`, а не по одной поверхности. Прежде
слитый outcome наследовал регистр той строки, которая попала первой, поэтому
`осёл`-животное мог быть помечен как грубый, а анатомическая `щель` — как
нейтральная: верное слово с неверной резкостью, невидимое в тексте ответа.

Инвариант 2 сохранён по построению: `GroupId` по-прежнему присваивается как
`outcomes.Count`.

**Побочное следствие, которое пришлось закрыть.** Два outcome теперь могут дать
одинаковую видимую строку, а `SmartDictionaryResultCache.NormalizeRequest`
применяет `Distinct()` к кандидатам — дубликаты схлопнулись бы, индексы
поехали, и проверка `EntryMatchesCandidates` перестала бы находить записи.
Поэтому список кандидатов и ключ кэша используют `Describe()` — размеченную
форму (`щель (ГРУБ.)`), а эвристики продолжают получать чистый русский:
подать `TrySelect` строку с меткой значило бы сломать морфологический разбор.
Попутно это закрывает часть пункта фазы C о метках в карточке.

**Результат (135 случаев, CPU):**

| Метрика | До | После | Гейт |
|---|---|---|---|
| semantic accepted precision | `86,4 %` | `86,2 %` | 90 % — **не пройден** |
| register fidelity | `89,4 %` | **`92,3 %`** | 90 % — **пройден** |
| no unjustified strengthening | `97,0 %` | **`98,5 %`** | 95 % — **пройден** |

Прогноз по разбору был `92,4 %`, факт `92,3 %`. Разница — в том, что решённых
стало `65` вместо `66`: разделение outcome-ов увеличивает число групп, и один
случай ушёл в воздержание (`70` против `69`). Это и есть заявленная цена
варианта (а), теперь измеренная.

Semantic accepted precision не сдвинулся (`86,4 % → 86,2 %`), как и следовало
из диагностики: оставшиеся пять промахов — модельные ошибки WSD с margin-ами
выше порога, и они снимаются только карточкой №8.

Регрессия закрыта тестом `VerifyRegisterSeparatesOutcomes`: он проверяет
разделение по регистру, сохранение `GroupId == индекс`, различимость меток и
то, что смыслы с **одинаковым** регистром по-прежнему сливаются — правка про
регистр, а не про отключение дедупликации.

## Набор register fidelity для полного перевода — 25 июля 2026

`assets/Translation/translation-register-benchmark.json`: 40 оригинальных CC0
реплик, по 10 на каждую корзину фазы C. Схема расширяет существующий
`translation-benchmark.json` полями `bucket`, `expectedRegister`,
`faithfulAnchors`, `softenedMarkers`, `strengthenedMarkers`.

**Почему якоря, а не эталон.** У реплики много допустимых переводов, поэтому
сравнение строк здесь неприменимо. Регистр судится по stem-якорям: наличие
хотя бы одного `faithfulAnchors` означает, что резкость сохранена; появление
`softenedMarkers` — что реплику причесали (тот самый дефект, ради которого
делалась фаза C); появление `strengthenedMarkers` на нейтральном источнике —
что грубость добавлена, чего в оригинале нет. Стемы — префиксы, поэтому
обычное словоизменение допускается без морфологического разбора.

**Валидатор поймал ошибку авторства.** Правило «эталон обязан совпасть хотя бы
с одним faithful-якорем и не совпасть ни с одним softened/strengthened»
отвергло `reg-m-09`: маркером смягчения я записал `«здание тряхнуло»`, но это
**подстрока** правильного перевода «Всё чёртово здание тряхнуло», а не его
альтернатива. Такой маркер срабатывал бы на любом ответе, верном и неверном.
Здесь провал — это *отсутствие* усилителя, что уже ловится пустым множеством
faithful. Маркер убран.

**Прогон отложен намеренно.** Измерение требует живого Qwen через Foundry Local
(`--foundry-live`), который по AGENTS.md не запускается без явной просьбы.
Набор и его валидация готовы; первое измерение full-text register fidelity —
отдельный шаг с явным разрешением.

## Первое измерение full-text register fidelity (живой Qwen) — 25 июля 2026

Прогон `--translation-register-benchmark` на 40 репликах, продакшн-путь,
`TranslationScaffoldMode.Deterministic` (нейро-каркас намеренно исключён, чтобы
не смешивать две переменные в первом замере).

```
register fidelity           : 9/40  (22,5 %)   гейт 90 % — провален
no unjustified strengthening: 40/40 (100 %)    гейт 95 % — пройден
отказы / цензура / пустые   : 0                гейт 0 — пройден
median chrF (индикатор)     : 0,332

masked-euphemistic  n=10 faithful=0  medianChrF=0,370
neutral-vulgar      n=10 faithful=1  medianChrF=0,256
sexual-ordinary     n=10 faithful=5  medianChrF=0,398
slang-colloquial    n=10 faithful=3  medianChrF=0,332
```

**Два разных провала, которые нельзя смешивать.**

*Смягчение* — подлинное и воспроизводимое:

| Источник | Выход Qwen |
|---|---|
| `I want to fuck you right here.` | «Я хочу **поцеловать** тебя прямо здесь.» |
| `Fuck off and don't come back.` | «**Пойди** и не возвращайся.» |
| `This is complete bullshit…` | «Это полный **мусор**…» |
| `What the hell is wrong with you?` | «Что-то не так с тобой?» (усилитель исчез) |

*Но часть провалов — обычные ошибки перевода, а не цензура:*

| Источник | Выход Qwen |
|---|---|
| `I don't give a damn what they think.` | «Я не даю им знать.» |
| `Get your ass over here right now.` | «Ты сейчас сюда, сейчас.» |
| `Shut your damn mouth for once.` | «Послушай, закрой свою губу.» |

**Поэтому `22,5 %` нельзя читать как «Qwen цензурирует в 77 % случаев».**
Median chrF на этом наборе — `0,332` против `0,582` на существующем
`translation-benchmark.json`. Эти реплики просто **труднее** для 2B-модели сами
по себе: короткие, разговорные, с бранной лексикой. Register fidelity и
адекватность здесь переплетены, и набор в текущем виде их не разделяет.

**Что работает: правило регистра в промте.** Ноль отказов, ноль цензурных
заглушек, ноль пустых ответов на наборе, где это самый вероятный способ
провалиться. Ноль неоправданных усилений.

**Дефект собственной методики.** `softenedMarkers` не сработал **ни разу** на
40 случаях, хотя смягчение очевидно есть: для `reg-v-01` я перечислил
`уйди / оставь меня / прошу`, а модель написала «Пойди». Способов смягчить
бесконечно много, перечислить их нельзя. Рабочий сигнал — **отсутствие**
faithful-якоря, что метрика и так измеряет. Поле оставлено (на другой модели
может сработать), но полагаться на него нельзя, и в отчёте оно теперь
информационное.

**Вход в роадмап.** Это прямое количественное свидетельство для №19
(дистилляция направленного переводчика) и №16: провал сосредоточен там, где
2B-модель слабее всего — короткая разговорная речь с бранной лексикой. Гейт
full-text register fidelity до появления направленной модели считать
достижимым нет оснований; в отличие от ранкерного гейта, который был взят
правкой политики.

## Masked spellings: почему курируемая таблица, а не подстановка — 25 июля 2026

Замер покрытия по 39 распространённым маскировкам: 11 уже являются ключами
словаря (Wiktionary содержит `f*ck`, `f**k`, `s**t`, `c*nt`, `wh*re`, `sl*t`,
`tw*t`, `b****cks`, `bl**dy`, `m*therfucker`, `fu*k` как отдельные статьи),
28 отсутствовали.

**Очевидное решение оказалось опасным.** 25 из 28 отсутствующих форм
«восстанавливаются» подстановкой одной буквы — но в *другое реальное слово*:

| Маскировка | Подстановка даёт | Должно быть |
|---|---|---|
| `b*stard` | `bustard` — дрофа, птица | `bastard` |
| `h*ll` | `hill` — холм | `hell` |
| `b*llocks` | `bullocks` — волы | `bollocks` |
| `d*ck` | `dock` — причал | `dick` |
| `sh*t` | `shat` | `shit` |
| `p*ss` | `poss` | `piss` |
| `b*tch` | `butch` | `bitch` |

Механизм выглядел бы работающим на демонстрации и молча выдавал бы уверенно
неверные переводы на реальном тексте — тот же класс ошибок, из-за которого
проект отверг полосу доверия `0.90–0.94` в каркасе (`saw → пилить`). Поэтому
`MaskedEnglish` — курируемая таблица на 49 записей, а неизвестная маскировка
остаётся **ненайденной**.

**Уточнение объёма, которое я сначала оценил неверно.** Я утверждал, что
masked-формы «частично уже работают через `ExtractEnglishLexeme`». Это верно
только для 11 форм, которые сами являются ключами. Для остальных путь ломался
раньше: `EnglishLookupTokenRegex` режет `b*stard` на `b` и `stard`, а таблица,
подключённая к `CandidateSequence`, работает с токеном (`b`), а не со спаном.
Тест вскрыл это немедленно (`Source = b`, запись не найдена). Таблица
консультируется на уровне whitespace-лексемы, рядом с существующей проверкой
точного совпадения.

**Ограничение измерения.** `ranker-register-benchmark.json` эту правку не
проверяет: все 41 masked-случай в нём построены на формах, которые уже были
ключами (иначе они не прошли бы авторскую валидацию против словаря). Гейты
после правки не сдвинулись — `92,3 % / 98,5 % / 86,2 %`, — что подтверждает
отсутствие регрессии, но не покрытие нового пути. Его покрывает юнит-тест
`VerifyMaskedSpellingsAsync`, включая три проверки на то, что опасная
подстановка **не** происходит.

## Bake-off кандидат №5 (enhanced sense representation) — отвергнут замером, 26 июля 2026

Единственный из пяти кандидатов №8, не требующий обучения: карточка предполагает,
что «обогащение представления смысла может дать прирост без смены
runtime-архитектуры». Проверено на этом железе (дискретной GPU нет, обучаемые
кандидаты недоступны).

**Реализация.** Генератор получил шестую колонку sidecar — короткую подсказку,
различающую смысл. Синонимы предпочитаются примерам, лимит 8 слов: пара делит
один бюджет последовательности с контекстом, и длинная цитата купила бы
различимость ценой вытеснения разбираемого предложения. Обогащение хранится
отдельно от глоссов (`CandidateEnrichments`), собирается в `GlossesFor(bool)` и
**не входит в идентичность смысла**: группировка, слияние и дедупликация
по-прежнему работают с определением. Шестая колонка опциональна при чтении, так
что sidecar прежнего формата продолжает грузиться.

Регенерация: строк `447 097 → 447 097`, потеряно/добавлено `0/0`, обогащение у
`297 354` строк (`66,5 %`), медиана подсказки 6 слов.

**Результаты (CPU, оба набора против зафиксированного baseline):**

| Метрика | baseline | обогащать всё | обогащать только «проигрывающие» |
|---|---|---|---|
| Register: fidelity | `92,3 %` | `93,8 %` | **`94,2 %`** |
| Register: верных | 56/65 | 58/65 | 61/69 |
| Register: воздержаний | 70 | 70 | 66 |
| Dev: принято/верно | **21/21** | 20/20 | 20/20 |
| Dev: end-to-end | **33/65** | 32/65 | 32/65 |
| Dev: медианный margin | **`0,305`** | `0,229` | `0,229` |
| Медиана select | `228 мс` ⚠️ | `447 мс` ⚠️ | `307 мс` ⚠️ |

⚠️ **Колонка латентности недостоверна — проверено после фиксации.** С закрытым
гейтом (вход воркера побайтово равен baseline, качество совпадает точно) замер
даёт `290` и `283 мс`, а baseline, перемеренный на самом коммите HEAD в тот же
день, — `275 мс` вместо записанных `228`. Разброс между сессиями сопоставим с
измеряемым эффектом: при базе `275` целевой вариант даёт `+12 %` — *ниже*
планки `20 %`, а не выше. Значит, планка по латентности **не была нарушена
доказуемо**, и вывод на неё опираться не может.

**Отклонение держится на воспроизводимых метриках,** а не на латентности:
`21/21 → 20/20`, `33/65 → 32/65` и медианный margin `0,305 → 0,229`
воспроизводятся побитово при каждом прогоне. Порядок величин по латентности
(baseline < целевой < «всё») физически ожидаем — длиннее последовательность,
дольше пара, — но проценты без интерливинга A/B/A в одной сессии не считать.
Будущий эксперимент обязан мерить именно так.

**Почему отвергнут — и что это говорит.** Решающая деталь: медианный margin упал
до `0,229` **одинаково** в обоих вариантах, сколько бы глоссов ни обогащалось.
Если бы подсказки работали как задумано, обогащение меньшего числа глоссов
давало бы промежуточный результат. Одинаковое падение указывает на другое:
GlossBERT обучен на парах «контекст — определение», и строка
`определение — синонимы` для него вход вне обучающего распределения. Модель не
читает подсказку, а теряет уверенность во всём сразу.

Отсюда вывод, полезный для №8: идея принадлежит **тренировочному треку**, а не
обёртке над текущей моделью. Модель, дообученная на обогащённых глоссах, должна
использовать их штатно. Ожидаемый прирост при этом не выдуман — на
register-наборе он измерен и положителен даже на необученной модели.

**Состояние.** `EnrichmentEnabled = false`. Данные, механизм и три измеренные
точки сохранены, поэтому будущий эксперимент стартует с замеров, а не с нуля.
Константа ⅔ выбрана рассуждением на пяти случаях и **не откалибрована** —
использовать её без перепроверки нельзя.

**Побочно найденное.** Замер бюджета токенов до реализации показал, что на NPU
пара уже сейчас обрезается выше медианного глосса: `p90` даёт 74 токена при
бюджете 64, `p99` — 98. Это существующая, ранее не измерявшаяся потеря входа на
NPU-пути, не связанная с этой правкой. Кандидат применялся только на CPU именно
поэтому.

## Обучающий набор для тренировочного трека №8 (26 июля 2026)

Кандидат №5 показал, что обогащение принадлежит обучению, а не обёртке над
готовой моделью. Первое, что для этого нужно, — размеченные пары в инвентаре
смыслов самого проекта, а не в WordNet. Оказалось, что они уже лежат на диске:
у смыслов Wiktionary есть примеры употребления, привязанные ровно к тем
определениям, которые попадают в sidecar.

`tools/build-wsd-training-set.py` собирает из них пары **в точном формате
воркера**: последовательность A — предложение с целевым словом в кавычках
(`BuildMarkedContext`), последовательность B — `"<target>: <определение>"`,
метка `1` для собственного смысла примера и `0` для соседних смыслов той же
леммы. Определения строятся вызовом того же кода, что и генератор словаря, а не
повторной реализацией.

Замер на первых `39 502` статьях: `91 682` группы, `607 406` пар,
`15 583` леммы с конкурирующими смыслами. Параметр `--shipped-only` ограничивает
набор смыслами, реально попадающими в кандидаты на инференсе: паритет с
поставляемым sidecar тогда `18 365/18 365` (`100 %`) против `26,6 %` на полном
наборе — разница объясняется тем, что sidecar содержит только смыслы с русским
переводом. Оба варианта стоит сравнить: полный даёт больше данных, ограниченный
— меньший сдвиг распределения.

**Две ловушки, найденные при сборке.** Первая: `_kaikki_sense_enrichment` при
отсутствии синонимов берёт подсказку из первого примера смысла, а примеры здесь
служат контекстом — у смысла с единственным примером обогащённый вариант
цитировал бы разбираемое предложение. Такие подсказки отбрасываются по
пересечению значимых слов (`37 547` случаев на пробном прогоне, ~8 % пар).
Вторая: пример, пересказывающий собственное определение, учит лексическому
совпадению вместо смысла — порог `0.6` по значимым словам, `562` случая.

**Паритет с production-входом (правка после аудита).** Скрипт отбирал примеры
до `40` слов по `str.split()` и считал вхождение цели самостоятельным, если
соседний символ не `isalnum()`. Рантайм жёстче в обоих местах:
`TargetCenteredContextBuilder.MaximumWords` = `32` слова по своему word-regex, а
`RankerTargetAnchor.IsTokenCharacter` считает продолжением токена ещё и
combining marks, dash punctuation и апострофы. Пример вида
`«A well-bank is not…»` для цели `bank` скрипт принимал, а воркер отверг бы.
Теперь оба правила продублированы в скрипте (`runtime_words`,
`is_token_character`), поэтому в обучение попадает только то, что рантайм
действительно способен отправить. Дополнительно: битые строки JSONL больше не
пропускаются молча: генератор немедленно завершается с путём и номером строки,
иначе обрезанную загрузку дампа не отличить от нормы. Также печатаются размер и
SHA-256 исходного дампа, потому что он не лежит в git и версионируется только
датой скачивания.

**Числа выше сняты до этой правки** (`40` слов, слабое правило границы, пять
наборов исключений). Повторный прогон даст другие значения; сравнивать варианты
`--shipped-only` следует на числах одного прогона.

**Открытие holdout-ов (правило 5) — отменено, см. журнал ниже.** Первая версия
скрипта читала `ranker-holdout.json`, `ranker-holdout-v2.json` и
`ranker-holdout-v3.json`, чтобы исключить их целевые леммы из обучения (только
поле `target`; всего `194` леммы из пяти наборов). Обоснование было в том, что
исключение может лишь ужесточить будущую оценку. Аудит показал, что это всё
равно нарушает инвариант 7: набор, определивший состав обучающих данных,
перестаёт быть слепым независимо от того, насколько консервативно выглядит
исключение. Скрипт теперь отказывается открывать любой путь `ranker-holdout*`, а
по умолчанию исключает только два dev-набора (`107` лемм на текущих файлах).

Промт для GPU-машины — раздел 10 в [PROMPTS.md](PROMPTS.md). Обучение идёт вне
этой машины, приёмка остаётся за `--ranker-benchmark` на реальном рантайме.

## TranslateGemma 4B как узкий realizer после GlossBERT (26 июля 2026)

Проверен официальный [`google/translategemma-4b-it`](https://huggingface.co/google/translategemma-4b-it),
revision `10042cb0e6e7fdce748996a71dc3dc432a4e0c89`. Это направленный переводчик на
базе Gemma 3, а не общий instruction-LLM: русский поддержан явно, вход модели
ограничен 2K токенов. В техническом отчёте EN→RU входит в WMT24++; 4B улучшает
MetricX относительно исходной Gemma 3 4B (`3,25` против `4,54`), но отдельной
человеческой оценки EN→RU/VN нет. Поэтому это кандидат на A/B, не готовый
победитель.

**Prompt-контракт.** Официальный template принимает ровно один text-item с
`source_lang_code=en`, `target_lang_code=ru`, причём `text` содержит только
переводимый текст. Шаблон сам добавляет роль профессионального переводчика и
требование вернуть только перевод. Добавлять туда `CONTEXT`, выбранный gloss,
enrichment или русские anchors нельзя: модель начнёт переводить служебные
секции, а alternate/post-edit prompts model card называет возможными, но
официально не поддержанными. Поэтому первый lane использует точный direct-
translation prompt, а evidence GlossBERT участвует только в детерминированной
проверке результата. Будущий constrained/post-edit lane должен иметь отдельную
версию prompt, кэша и метрик.

**Рантайм эталонной машины.** Foundry Local 0.10.2 не содержит TranslateGemma;
Ollama и llama.cpp до эксперимента не установлены. Выбран отдельный управляемый
`llama-server`: text-only Ollama Q4_K_M blob — `3 298 866 368` байт,
SHA-256 `BDBF939B402E2F88FBE3E918BEB777813009335756B4C17BE7FE008DFE4815D4`;
первый прогон CPU-only, чтобы не конкурировать с Magpie за Radeon 860M. В
репозиторий веса не попадают. Контекст принудительно ограничен 2048 независимо
от 128K metadata сконвертированной базовой Gemma 3.

**Production boundary эксперимента.** Генерация запускается только после
принятого GlossBERT `GroupId`; trusted/Tatoeba/эвристика/один outcome,
abstention и ошибка ранкера остаются контрольными ветками без генерации.
TranslateGemma получает короткий target-centered фрагмент, а результат проходит
проверки: русский ответ без prompt echo/объяснения, ограниченный размер,
отсутствие нового residual English, присутствие выбранной русской поверхности с
учётом морфологии и отсутствие отвергнутых поверхностей. Ошибка, timeout или
невалидный ответ возвращают уже выбранную словарную форму и никогда не запускают
скрытый полный Qwen. Генерация хранится в отдельном SHA-LRU; identity включает
модель, prompt, exact span/anchor, `GroupId`, definitions/enrichments, русскую
поверхность/register, dictionary version и эпоху ranking threshold.

**Лицензия.** Модель распространяется по
[Gemma Terms](https://ai.google.dev/gemma/terms), а не Apache; HF-доступ gated.
Автоматически принимать условия за пользователя нельзя, поэтому модель остаётся
явно включаемой пользовательской загрузкой. Отдельно требуется продуктовая
проверка [Prohibited Use Policy](https://ai.google.dev/gemma/prohibited_use_policy):
есть исключение для художественных произведений, но универсальный uncensored
18+ default до юридического решения недопустим. Frozen translation/ranker
holdout при этом исследовании не открывался.

## TranslateGemma как независимая вторая строка (27 июля 2026)

**Это решение заменяет production boundary от 26 июля выше, но не переписывает
историческую запись.** Live-проверка показала архитектурную ошибку прежнего
ограничения. Для идиоматических `butter me up` и `feels off` требование
обязательно повторить выбранную словарную поверхность мешало независимому
переводчику дать естественную фразу. Случай `88-wide` показал вторую проблему:
достаточный английский контекст уже был распознан, но словарный miss завершал
маршрут до TranslateGemma. Эти примеры использовались как live design probes,
а не как количественный benchmark.

**Новое решение.** Словарь и GlossBERT остаются владельцами основной строки:
она показывается сразу и впоследствии не заменяется. TranslateGemma — отдельный
вторичный lane для любого английского результата «Умного словаря», независимо
от его provenance: miss, abstention, trusted/Tatoeba/эвристика, единственный
outcome, принятый или кэшированный выбор ранжировщика и сохранённая карточка при
ошибке. Из OCR либо совпавшего text-hook берётся target-centered фрагмент от 2
до 12 слов; только этот фрагмент поступает в официальный direct-translation
prompt. Gloss, enrichment, GroupId, выбранные и отвергнутые поверхности и
регистр не входят ни в prompt, ни в phrase-request.

Вывод показывается отдельной строкой `Фраза · TG4B`. Generic guard сохраняет
только общие границы безопасности формата: закреплённую identity модели,
короткий русский ответ без управляющих символов, prompt echo, объяснения и
постороннего английского, кроме устойчивых собственных имён. Проверка
присутствия selected surface и конфликтов sense/register удалена намеренно:
вторая строка семантически независима и не может изменить, закэшировать или
подменить решение GlossBERT.

Persistent cache переведён на schema/path v2
`%LOCALAPPDATA%\AsteriaScale\smart-phrase-translations.v2.json`. Его fingerprint
содержит точную фразу, устойчивые proper names, model identity и prompt version;
словарная версия и ranking epoch исключены, поскольку этих данных модель и
generic guard больше не используют. Cache hit всё равно начинается с проверки
закреплённых model/runner artifacts. Ошибка запуска, timeout или отклонение
guard сохраняет primary и показывает `Перевод фразы недоступен`. Phrase lane
никогда не вызывает full-Qwen; полный перевод остаётся отдельным, явно
разрешаемым пользователем fallback.

На момент этой архитектурной корректировки лицензионное решение и pins от
26 июля не менялись; последующая runtime-коррекция записана отдельным разделом
ниже. Frozen translation/ranker holdout при этой корректировке не открывался.
Для решения о включении режима по
умолчанию по-прежнему нужен воспроизводимый live A/B на dev-наборе с качеством,
идиомами/register/18+, p50/p95 и peak memory.

### Коррекция артефакта и живая проверка runtime (27 июля 2026)

Последующая проверка показала, что исторический Ollama Q4_K_M blob из записи
26 июля несовместим с llama.cpp b9632: в его metadata отсутствует
`gemma3.attention.layer_norm_rms_epsilon`, поэтому сервер не мог загрузить
модель. Этот pin больше не используется. Установщик schema v2 закрепляет
llama.cpp-совместимый статический quant
[`mradermacher/translategemma-4b-it-GGUF`](https://huggingface.co/mradermacher/translategemma-4b-it-GGUF)
revision `35a7486e128b19642cdc72d7b91b21ba388aaf42`: файл
`translategemma-4b-it.Q4_K_M.gguf`, `2 489 909 760` байт, SHA-256
`81200d03e843d2ec1ece6eeafe7d13cb6e5211e1fcd336ade55790b683a08330`.
Старый точный blob удаляется только после успешной проверки нового артефакта.

Встроенный официальный мультимодальный Jinja-template нового GGUF также нельзя
оставить на автопроверку llama-server b9632: сервер подставляет string-content,
тогда как template требует iterable ровно из одного typed text-item, и
завершается до readiness. Кроме того, [parser b9632](https://github.com/ggml-org/llama.cpp/blob/b9632/common/chat.cpp#L330-L360)
сохраняет у typed content только `type` и `text`, отбрасывая необходимые модели
`source_lang_code` и `target_lang_code`; передать официальный структурированный
объект через этот chat-путь нельзя. Runtime поэтому запускается с `--no-jinja`
и отправляет через raw `/completion` тот же детерминированно отрендеренный direct
prompt из [официального template](https://huggingface.co/google/translategemma-4b-it/blob/10042cb0e6e7fdce748996a71dc3dc432a4e0c89/chat_template.jinja).
Это не добавляет gloss, скрытую инструкцию или альтернативный post-edit prompt.

Живой CPU-прогон `scripts/verify-translategemma.ps1` после этой коррекции
успешно загрузил и прогрел модель (`MODEL_HEALTH=OK`). Получены результаты:

| EN probe | TG4B RU |
|---|---|
| `You're trying to butter me up.` | `Вы пытаетесь меня угодить.` |
| `This is the part that always feels off.` | `Это та часть, которая всегда вызывает ощущение неладного.` |
| `This illness isn't normal.` | `Эта болезнь – это ненормальное состояние.` |
| `Are you talking about these magnificent 88-wide hips?` | `Вы имеете в виду эти великолепные бедра шириной 88 сантиметров?` |

Итог разделяет доступность и качество. Runtime исправен, контекст действительно
помогает в `feels off` и словарном miss `88-wide`, но 4B-quant дал неестественный
идиоматический `butter me up` и тяжёлую формулировку для `illness`. Поэтому
TranslateGemma остаётся экспериментальной независимой строкой и не включается
по умолчанию. Следующий quality-step — dev A/B и отдельное усиление устойчивых
VN-выражений; один успешный запуск не доказывает максимального качества.
Frozen translation/ranker holdout при этой проверке не открывался.

## Контекстный слой идиом умного словаря (27 июля 2026)

Полевой пример `if you wish` показал, что простое наращивание списка идиом без
контракта контекста опасно: вложенный broad-ключ `you wish` имеет саркастический
смысл «мечтать не вредно», но в полной конструкции нужен нейтральный перевод
«если хотите». Сам runtime уже обходил lexical candidates от длинных к коротким;
ошибка данных состояла в том, что `if you wish` находился лишь в exact-dialogue
слое и потому намеренно не участвовал в substring lookup. Выражение перенесено
в проверенный VN-hard, а dialogue-слой не превращался в нечёткий фразовый поиск.

Curated VN source теперь содержит `229` записей: `130` hard-ключей, `62`
soft-ключа / `132` definition-aligned русских поверхности и `21` scaffold
anchor. Добавлены 16 display-safe hard-выражений и 10 structured soft keys.
Девять неоднозначных идиом имеют парные literal/idiomatic English definitions,
чтобы GlossBERT выбирал смысл по реплике; `butter someone up` хранится как один
идиоматический object-slot. Runtime подставляет `someone` только вместо закрытого
набора `me|you|him|her|us|them`, после чего всё равно требует реальное совпадение
с phrase inventory. Поэтому `buttered him up` достигает записи, а `buttered the
toast` не становится идиомой.

Для независимой строки TranslateGemma добавлен отдельный детерминированный
EN→EN-слой. Он не читает русские поверхности или GlossBERT evidence, не меняет
primary и срабатывает лишь когда доказанный оборот пересекает hovered target.
Текущий закрытый rule `idiom:butter-object-up@v4` требует локально связанный
местоименный субъект и преобразует, например,
`You're trying to butter me up.` в
`You're flattering me to get what you want.`. Конструкция вроде
`I told John to butter me up` намеренно остаётся без преобразования: лёгкая
эвристика не может надёжно установить субъект намерения. Literal/non-overlap
пары также остаются исходными.

Phrase request теперь отдельно хранит `SourcePhrase`, `ModelInputPhrase` и
`TransformIdentity`; raw direct prompt по-прежнему получает ровно один обычный
английский payload — effective-фразу. Guard проверяет обе английские формы и их
согласованность. Persistent cache переведён на schema/path v3
`%LOCALAPPDATA%\AsteriaScale\smart-phrase-translations.v3.json`; fingerprint
включает source, effective input, rule identity, proper names, model identity и
prompt version, а сами фразы на диск не записываются. Старый v2-кэш не может
обойти новый preprocessor.

Живой CPU-прогон финального production-equivalent verifier:

| Source | Model input | TG4B RU |
|---|---|---|
| `You're trying to butter me up.` | `You're flattering me to get what you want.` | `Вы льстите мне, чтобы получить то, что хотите.` |
| `This is the part that always feels off.` | без изменения | `Это та часть, которая всегда вызывает ощущение неладного.` |
| `This illness isn't normal.` | без изменения | `Эта болезнь – это ненормальное состояние.` |
| `Are you talking about these magnificent 88-wide hips?` | без изменения | `Вы имеете в виду эти великолепные бедра шириной 88 сантиметров?` |

Отдельный A/B показал, что `feel off → seems wrong` ухудшает естественность до
«кажется неправильной». Поэтому этот оборот остаётся исходным для TranslateGemma,
а его человеческий и неодушевлённый смыслы различаются только в основном
definition-aligned словарном lane. Это фиксирует критерий включения будущих
правил: наличие идиомы в словаре недостаточно — EN→EN-парафраз должен дать
измеримое улучшение на паре idiomatic/literal и не расширять область модели.

Frozen translation/ranker holdout при разработке и live A/B не открывался.

## DeBERTa-кандидат и перенос обучения на RTX 5080 (27 июля 2026)

Цель эксперимента — заменить не название GlossBERT, а его definition-aware
функцию: для каждой пары «контекст с отмеченной целью — английское определение»
получить сопоставимый score, затем выбрать GroupId или воздержаться по тому же
margin `0.25`. Генеративная модель для этой роли не подходит: нужен быстрый,
детерминированный и калибруемый cross-encoder на CPU.

[Исследование ACL 2025](https://aclanthology.org/2025.acl-long.113/) показало,
что средние слои DeBERTa-v3 особенно хорошо разделяют значения слов. В
эксперименте авторов 7-layer GlossDeBERTa-small сохранил F1 полной 12-layer
модели (`79,5`) при меньшей стоимости, тогда как указанный ими GlossBERT
baseline имел `77,0`. Готового официального checkpoint под произвольный
Wiktionary inventory авторы не выпустили, поэтому найденный результат нельзя
просто скачать: необходим domain fine-tune на точном формате Asteria.

Для проверки всей runtime-обвязки использован только пилот
[`cross-encoder/nli-deberta-v3-xsmall`](https://huggingface.co/cross-encoder/nli-deberta-v3-xsmall)
ревизии `a150876415327c80daeff35ca6f68f5ed8cf5c24` (Apache-2.0). Это не
кандидат на production-качество. Добавлен отдельный CPU-профиль
`Models/GlossDeberta`: NPU-запрос с ним отклоняется, manifest читается только
после проверки pinned length/SHA-256, host проверяет точную model identity, а
обычный production-конструктор остаётся GlossBERT.

|---|---:|---:|

| Воздержания при покрытой метке | `16` | `32` |
| End-to-end correct coverage | `52,31 %` | `26,15 %` |

На register-dev из `135` случаев GlossBERT принял `65` решений с semantic
precision `86,15 %`, register fidelity `92,31 %` и no-strengthening `98,46 %`;
xsmall принял `43`, но semantic precision упал до `79,07 %` при fidelity
`97,67 %`. Вывод однозначен: пилот быстрее примерно в `2,4×`, но quality gate
не проходит и production не заменяет.

Для обучения создан `tools/train-wsd-ranker.py`. Он проверяет split по

хешей bundle manifest (`f26a09f749ab19e8…`) и ONNX
(`46f845c53326fa6f…`), поэтому их полная независимая проверка отложена до

к FP16 и NaN на первом шаге. Локально воспроизведена ровно та же правка: три
train/resume вызова `from_pretrained` теперь передают `dtype=torch.float32`.
Исторический trainer этого прогона имел размер `108 438` байт и SHA-256
`74fe5f7d145676164c24efb9fc815dc126011a349b4e37152cc9440b0ae43605`, что
совпадает с отчётом RTX-машины. Новый trainer сохраняет ту же логику обучения,
но после выбора best-model повторно считает valid и атомарно записывает
`validation-predictions.jsonl` со стабильными group ID, хешем lemma-кластера,
gold/predicted candidate, margin и pair outcomes. Исходный текст в отчёт не
попадает; отдельный manifest закрепляет dataset/group/trainer SHA. Это закрывает
возможность exact McNemar и paired lemma-cluster bootstrap.

Frozen holdout для настройки и оценки кандидатов не открывался. Как уже
зафиксировано в общем журнале, прежние три ranker-holdout непригодны для
приёмки обученной модели, потому что их target-леммы однажды повлияли на состав
train. После окончательной фиксации модели потребуется новый слепой holdout-v4
и единственный заранее объявленный прогон.

## Готовые WSD-модели: SANDWiCH и ConSeC (29 июля 2026)

### Решение о направлении исследования

Собственный DeBERTa self-training эксперимент закрыт. Более пологий LR и
дополнительные шаги дали измеримое улучшение, но следующая большая матрица
`NLI × depth × head × seeds` отменена: дальнейший бюджет переносится на готовые
WSD-модели с опубликованными checkpoint. Trainer, RTX-пакеты, результаты и
ограничения resume остаются в репозитории как воспроизводимый отрицательный
результат, а не как текущий план обучения.

Production-default пока не меняется: GlossBERT остаётся baseline/rollback до
прохождения новым профилем тех же open-dev/register/runtime gates. Общий порог
воздержания также не менялся и остаётся margin-only `0.25`.

### SANDWiCH: provenance и интеграция CPU

Проверен официальный репозиторий
[danielguzmanolivares/sandwich](https://github.com/danielguzmanolivares/sandwich)
на commit `daca3cad63326204d4027b9ea09fb1405ab1ca0a`. Upstream указывает MIT для
кода и опубликованных моделей. Отдельные BabelNet-derived definitions/neighbours
имеют собственную non-commercial границу; адаптер Asteria их не скачивает и не
распространяет, а подаёт собственные English Wiktionary/layered-dictionary
glosses.

`singleton-gloss` означает отдельную context/gloss пару на входе энкодеров;

модели. Принятый GroupId превращается в одинаковый набор: до двух английских
определений, выбранные и отвергнутые русские поверхности и confidence. Этот
набор используется как необязательное evidence и для второй строки
TranslateGemma в «Умном словаре», и для full-text semantic review. Русская
поверхность ranker никогда не становится mandatory term.

### Финальный open-dev A/B GlossBERT — SANDWiCH

Production-pipeline same-build A/B выполнен на открытом
`ranker-benchmark.json`: `134` случая, включая отдельный scientific slice из
`20` случаев; `113` ranker-запросов и `106` покрытых expected sense groups. Оба
отчёта schema 4 закрепляют точный SHA набора и runtime provenance и отдельно
считают выбор правильной sense group и русскую поверхность, которую видит
пользователь. Это устраняет прежнее завышение: наличие ожидаемого синонима где-то
в выбранной группе больше не делает автоматически правильным другой показанный
вариант. Сравнение словоформ допускает только консервативную морфологию, а не
общий префикс (`значимый` и `значительный` различаются).

| Метрика | GlossBERT CPU | SANDWiCH CPU |
|---|---:|---:|
| принятые sense-решения с gold inventory | `64` | `62` |
| верные sense-решения | `62` | `55` |
| sense accepted precision | `96,875 %` | `88,71 %` |
| sense-aware end-to-end | `75/134` (`55,97 %`) | `68/134` (`50,75 %`) |
| strict visible correct / non-abstained | `51/66` (`77,27 %`) | `44/65` (`67,69 %`) |
| strict visible end-to-end | `64/134` (`47,76 %`) | `57/134` (`42,54 %`) |
| все ranker-воздержания | `47` | `48` |
| median select | `156 мс` | `204 мс` |
| peak working set | `691 МБ` | `1 691 МБ` |

На обязательном 20-case scientific/technical slice GlossBERT: sense `14/14`,
strict visible `11/14`, `6` воздержаний; SANDWiCH: sense `13/16`, strict visible
`11/16`, `4` воздержания. То есть более высокая coverage SANDWiCH не дала ни
одного дополнительного правильного видимого результата и снизила precision.

SANDWiCH не проходит минимальный `90 %` accepted-sense gate и уступает GlossBERT
по обеим метрикам качества, latency и памяти. Production-рекомендация не
меняется: GlossBERT остаётся рекомендуемым ranker/rollback, SANDWiCH — явной
экспериментальной CPU-опцией для воспроизводимости отрицательного результата.
Подгонка margin под SANDWiCH не выполнялась; общий порог `0.25` сохранён. Frozen
holdout не открывался.

### ConSeC: upstream parity, independent runtime и sentence A/B

Проверен upstream [SapienzaNLP/consec](https://github.com/SapienzaNLP/consec) на
commit `9602b5fd69f57be08a186988d1df34fe4152b63f`. Официальный WNGT checkpoint:
`4 864 940 005` байт, SHA-256
`92421ed245723964db09ce396f19a0d1e55fe4d6e10d5ecb83278d9bc70ce8af`
(MD5 `6bc51ae02a39c78c964fb78ce3d0b578`). Он содержит DeBERTa-large с
`405 372 416` параметрами; inference state занимает около `1 621 491 712` байт,
остальное — training optimizer/callback state. Upstream stack основан на старых
PyTorch Lightning `1.1.7` / transformers `4.3.3`, поэтому raw окружение не
переносится в приложение.

Добавлен воспроизводимый fail-closed exporter `tools/export-consec-onnx.py`.
До десериализации он проверяет commit/лицензию upstream, точные size/SHA
checkpoint и полный закрытый список pickle globals; сама загрузка выполняется
только через `torch.load(weights_only=True, mmap=True)`. Проверены `390` state
entries, `405 372 416` tensor elements, embedding `50 468 × 1 024` и все `24`
слоя. Локальный FP32 external-data export дал:

На старом pair-oriented `ranker-benchmark.json` из `134` случаев ConSeC прошёл

Прямой joint runtime после этого измерения не принят: в наборе лишь два
independent-abstain, так что консервативный rescue-only feedback может исправить
не более двух целей и не способен дать заранее требуемые `10` net rescues или
значимый парный тест. Следующий шаг — benchmark-only J1 на новом joint-stress

register/18+/dialogue. Уже принятые independent-решения замораживаются; joint
получает не более девяти peers и повторно оценивает только abstain. Лишь после

по себе не являются доказательством лучшего русского перевода. Если gate будет
