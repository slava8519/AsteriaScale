# Исследование real-time апскейла окон

Дата фиксации исследования: 18 июля 2026 года.

## Вывод

Для произвольного low-res окна на Windows лучший практически применимый путь — `Windows Graphics Capture → Direct3D 11 texture → специализированный spatial CNN/HLSL → edge-aware resize → presentation`. Для визуальных новелл главная модель — CuNNy2 NVL, а не универсальный FSR: она обучена на скриншотах и CG visual novel и отдельно учитывает текст/line art.

Temporal upscalers уровня FSR 2/3 или DLSS нельзя честно применить к захваченному окну с тем же качеством, что внутри игры: захват отдаёт готовый цветной кадр, но не motion vectors, depth, jitter и exposure. Поэтому Asteria использует spatial pipeline и не обещает недоступные данные.

## Захват окна

Microsoft описывает `Windows.Graphics.Capture` как API получения кадров отдельного окна или дисплея с Direct3D frame pool. Для размера кадра и смены размера окна предусмотрен `Direct3D11CaptureFramePool` и его `Recreate`.

Источник: [Screen capture — Windows apps](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture).

Magpie сравнивает Graphics Capture, Desktop Duplication, GDI и DWM Shared Surface и рекомендует Graphics Capture для общей совместимости и плавности. GDI не поддерживает DirectComposition и имеет нестабильную производительность; Desktop Duplication хуже подходит для отдельного окна.

Источник: [Magpie — Comparison of capture methods](https://github.com/Blinue/Magpie/wiki/Comparison-of-capture-methods).

Практический выбор Asteria: Graphics Capture (`captureMethod = 0`), без захвата title bar, с Per-Monitor V2 DPI awareness.

## Алгоритмы

### CuNNy2 NVL

Автор CuNNy прямо указывает, что это компактный real-time CNN, обученный на скриншотах/CG визуальных новелл. Вариант `NVL` предназначен для visual novel и качественных иллюстраций. В исходном проекте качество моделей возрастает от veryfast до 8×32, а каждая модель масштабирует в 2 раза.

Источник: [funnyplanter/CuNNy](https://github.com/funnyplanter/CuNNy).

В Asteria:

- 4×24 NVL — рекомендуемый баланс;
- 8×32 NVL — максимум качества;
- 4×16 NVL — мягкий и более быстрый режим.

После фиксированного CNN ×2 нужен второй проход до физического размера экрана. Для общего случая используется FSR EASU; в soft-пресете — perceptual SSim downscale.

### Anime4K

Anime4K — модульный real-time набор для восстановления линий, denoise и апскейла anime-style изображения. Сам проект предупреждает, что он изначально оптимизирован скорее под 1080p anime → 4K, а SRGAN лучше восстанавливает сильно деградированное low-res изображение, хотя обычно тяжелее для real-time.

Источник: [bloc97/Anime4K](https://github.com/bloc97/Anime4K).

Поэтому Anime4K не выбран пресетом visual novel по умолчанию, но доступен для роликов и анимированных сцен.

### AMD FSR 1

FSR 1 — spatial upscaler текущего кадра. Его EASU-проход реконструирует границы, а RCAS возвращает локальную резкость. AMD указывает поддержку DirectX 11/12 и произвольного масштаба 1×–4×. В отличие от temporal FSR, он не требует истории кадра или motion vectors, поэтому подходит для внешнего захвата окна.

Источник: [AMD FidelityFX Super Resolution 1](https://gpuopen.com/fidelityfx-superresolution/).

В Asteria FSR выполняет две роли: быстрый универсальный режим и точная подгонка результата фиксированного CuNNy ×2 к экрану.

### Magpie как рендерер

Magpie — открытый DirectX 11 window upscaler с полноэкранным/оконным режимом, multi-monitor, FP16 и HLSL-эффектами. В его текущих эффектах присутствуют CuNNy2, Anime4K, FSR, FSRCNNX, RAVU, NNEDI3 и xBRZ. Документация отдельно отмечает CuNNy как семейство для visual novel-style изображений.

Источники: [Magpie repository](https://github.com/Blinue/Magpie), [Built-in effects](https://github.com/Blinue/Magpie/wiki/Built-in-effects).

Asteria запускает Magpie отдельным процессом, добавляет свои цепочки в JSON, скрывает служебный UI и управляет зарегистрированными hotkeys. Это сохраняет лицензионную и процессную границу: Magpie остаётся GPLv3-программой, Asteria не встраивает его бинарный код.

## NPU

Windows ML предоставляет общий ONNX Runtime и умеет динамически устанавливать execution providers для CPU, GPU и NPU. Для AMD доступен `VitisAIExecutionProvider`; vendor providers требуют Windows 11 24H2 build 26100+ и совместимый драйвер.

Источники:

- [What is Windows ML?](https://learn.microsoft.com/en-us/windows/ai/new-windows-ml/overview)
- [Supported execution providers](https://learn.microsoft.com/en-us/windows/ai/new-windows-ml/supported-execution-providers)
- [Install execution providers](https://learn.microsoft.com/en-us/windows/ai/new-windows-ml/initialize-execution-providers)
- [AMD Windows ML overview](https://ryzenai.docs.amd.com/en/latest/winml/winml_overview.html)

Обнаруженная целевая система:

- AMD Ryzen AI 7 H 450;
- Radeon 860M;
- NPU Compute Accelerator Device, driver 32.0.203.329;
- Windows 11 build 26200;
- дисплей 3200×2000 @ 60 Hz, 200% DPI.

NPU полезен для задач без непрерывного обмена кадрами с GPU. Windows AI Text Recognition извлекает текст, границы слов и уверенность локально и выполняется на NPU. Поэтому перевод под курсором захватывает только область 900×340 вокруг указателя, выбирает ближайшую OCR-строку и не отправляет изображение в сеть.

Источники: [Windows AI Text Recognition](https://learn.microsoft.com/en-us/windows/ai/apis/text-recognition), [Foundry Local](https://github.com/microsoft/Foundry-Local), [Foundry Local CLI](https://learn.microsoft.com/en-us/azure/foundry-local/reference/reference-cli).

Для полного перевода проверялись несколько локальных Qwen. `qwen3.5-2b-text-generic-gpu:3` остаётся полнотекстовой моделью для английских и японских реплик. Генеративные Qwen 0.5B/1.5B оказались неудачным инструментом именно для ранжирования словарных смыслов: они тяжелее специализированного классификатора, медленнее прогреваются и могут вернуть текст вне допустимого списка.

### Контекстный словарь: GlossBERT

Начиная с версии 0.9.2 выбор значения выполняет [GlossBERT](https://huggingface.co/kanishka/GlossBERT), закреплённый на ревизии `0cc3b83af5496e27ebcc95ef0cf37ea0a9281a7a` (MIT). Это BERT-классификатор задачи word-sense disambiguation: он получает предложение с отмеченным целевым словом и английское определение одного смысла, а не пытается заново перевести всю реплику.

Кандидаты берутся из полного слоя English Wiktionary: 147 583 английские словоформы и фразы, 406 179 русских переводов, выровненных с полными английскими определениями, частями речи и стилистическими метками. Одинаковые видимые русские варианты объединяются до сравнения; порог оценивает разрыв между разными результатами, а не между дублирующими определениями.

В версии 0.9.3 конвейер расширен, но сохраняет безопасное воздержание:

1. сначала независимо ищутся словарное выражение длиной до шести слов и точное полное предложение Tatoeba;
2. Tatoeba служит контекстным результатом или fallback и не может вытеснить найденное внутри строки лексическое выражение случайным длинным фрагментом; если точный русский перевод предложения однозначно содержит один словарный смысл с другой грамматической формой (`признак → признаков`), он выбирается без запуска модели;
3. формы выражений канонизируются ограниченно: `shook her head` сопоставляется с `shake one's head`, а `get separated from` распознаётся как единая результативно-пассивная конструкция;
4. модель ранжирует значения смыслового ядра, а близкие русские формулировки одного значения объединяются только при совпадении части речи и защитных семантических признаков;
5. результат принимается только при достаточном разрыве между различными группами значений; иначе ранжировщик воздерживается и оставляет пользователю до трёх компактных словарных вариантов;
6. только отсутствие словарной записи или ошибка ранжировщика могут вызвать полнотекстовый перевод, причём лишь при явно выбранном fallback `Автоматически`.

Порог `0,25` был заморожен на отдельном dev-наборе до открытия контрольного `ranker-holdout-v2.json`. На независимом CC0-наборе из 30 оригинальных однословных случаев CPU FP32 принял 18 решений, из которых 17 совпали с разметкой; NPU-путь принял 16 решений, из которых 15 совпали. Это маленький регрессионный набор, а не гарантия точности на произвольном тексте. CPU поэтому выбран как эталонный режим по умолчанию. NPU-путь на целевой машине был быстрее в прогретом микробенчмарке, но компиляция модели и конкретная версия AMD-драйвера могут слегка менять оценки.

Изначально ранжировщик дополнительно принудительно воздерживался, когда число глоссов превышало калибровочный размер пакета (32 на CPU, 4 на NPU). Позднее это правило было снято: парные оценки GlossBERT независимы и считаются фиксированными чанками, поэтому размер инвентаря не меняет отдельные оценки, а порог margin остаётся единственным критерием воздержания. Измерения через полный продакшн-конвейер (`AsteriaScale.Tests --ranker-benchmark`, словарь + группировка + изолированный worker) показали: после объединения смыслов ни один случай dev-набора и holdout-v2 не превышает 18 глоссов, а зонд из гиперполисемичных слов (`set`, `run`, `go`, `light`) достигает максимум 27 — предел CPU был практически недостижим, тогда как предел NPU принудительно гасил две трети рангируемых случаев. После снятия правила: dev-набор — CPU 17 принятых решений / 17 верных среди размеченных инвентарём случаев, NPU 17/17 с расхождением margin от CPU не более `0,01`; holdout-v2 (повторно открытый только для этого подтверждения) — CPU 8/8, NPU 8/8 при пяти воздержаниях. Строгий матчер бенчмарка не засчитывает морфологические варианты (`серьёзный` ↔ `серьёзным`), поэтому эти числа консервативны и не сравниваются напрямую с методикой 0.9.3.

Сверка порога между провайдерами (роадмап №3): на dev-наборе по дампам `--ranker-benchmark --dump` медианный сдвиг margin CPU↔NPU составил `0,005`, максимальный — `0,031` (один случай), пересечений порога `0,25` и различий в принятых решениях — ноль. Вывод: общий порог для обоих провайдеров обоснован, раздельная калибровка NPU не требуется. Для будущих сверок создан замороженный `ranker-holdout-v3.json` (46 случаев: междометия, переносные, разговорные, омонимы, большие инвентари; автор не сверялся с логами ошибок модели); набор не открыт. Обогащение sense-sidecar из ru-Wiktionary (роадмап №1: заимствование междометных поверхностей и синонимов-соседей по запятой при совпадении основы) выполнено: словари регенерированы из бит-идентичного исходного дампа (SHA-256 совпал с закреплённым), sidecar вырос с 406 179 до 455 814 выровненных поверхностей (+49 657 заимствованных). Матчер бенчмарка сделан толерантным к словоформам одиночных слов (общая основа ≥ 4–5 символов — зеркало рантайм-выравнивания): показ леммы «серьёзный» на ожидание «серьёзным» — верный ответ, а не промах покрытия. Итог: dev-набор — покрытие 26/30, решения 17/17 верных; holdout-v2 — покрытие 17/27 (было 13/27), решений 11, верных 10; новая единственная ошибка («framed» → «обрамлять» вместо переносного «подставить») — подлинный промах модели, ранее скрытый строгим матчером, целевой класс задачи №8. Остаточные пробелы покрытия — идиоматические многословные соответствия и междометия, отсутствующие в ru-Wiktionary.

Морфословарь (роадмап №2): русская глагольная морфология переведена с чисто суффиксных правил на лексикон OpenCorpora (154 527 форм — только инфинитивы и прошедшее время, через pymorphy3-dicts-ru, так как экспорт opencorpora.org недоступен; CC BY-SA). Леммы служат парадигмо-стабильными основами (супплетивные «пошёл/пошла/пошли» группируются под «пойти», что суффиксным основам недоступно), вид глагола берётся из граммем — пары «закрыть/закрывать» стали различимы для выбора вида без эвристики «-нуть». Суффиксные правила остаются обязательным fallback для слов вне лексикона. Dev-бенчмарк без деградации: покрытие 26/30, решения 17/17.

CPU использует исходный динамический FP32 ONNX. Полная dynamic-INT8-квантизация была удалена: на контрольном dev-наборе она сохранила только 34 из 37 решений FP32 и, в частности, сжала margin для `utter confusion` с `0,254` до `0,150`. Вход CPU дополняется только до самой длинной пары в текущем пакете, максимум до 128 токенов, что уменьшает стоимость пустого padding. NPU-вариант — заранее скомпилированный AMD Vitis EPContext; автоматического перехода между providers нет. Если NPU несовместим с машиной, приложение сохраняет обычный словарный результат и позволяет явно выбрать CPU. Модель работает в отдельном дочернем процессе, поэтому отключение режима и таймер простоя возвращают её память независимо от основного UI.

### Упрощённый словарный режим

Для минимальной задержки добавлен второй путь после того же NPU-OCR. Он не запускает генеративную модель:

1. OCR сообщает строку, слово и относительную позицию курсора;
2. для английского строятся выражения, содержащие выбранное слово, от самого длинного к короткому; отдельный лексический индекс допускает выражения до шести слов, не смешивая их с корпусом полных реплик Tatoeba;
3. при отсутствии выражения выполняется поиск слова и простая нормализация форм (`waiting → wait`, `was → be`);
4. для японского ищется самое длинное словарное совпадение, пересекающее символ под курсором;
5. при переходе в этот режим Qwen выгружается, а пустой сервер Foundry Local останавливается, чтобы WebGPU не удерживал зарезервированную память.

Восемь словарных слоёв дают около 871 тысячи индексированных английских и японских слов/выражений. В их числе полный, а не частотный English Wiktionary с отдельным definition-aligned слоем для умного режима. TSV-индексы сжаты gzip; подробные версии и лицензии источников перечислены в `THIRD_PARTY_NOTICES.md`. Источники: [FreeDict eng-rus](https://download.freedict.org/generated/eng-rus/), [Kaikki English Wiktionary](https://kaikki.org/dictionary/English/), [JMdict project](https://www.jmdict.org/), [EDRDG licence](https://www.edrdg.org/edrdg/licence.html), [Tatoeba downloads](https://tatoeba.org/downloads).

Для real-time апскейла NPU по-прежнему полезен только при наличии модели, скомпилированной/квантованной под VitisAI, и zero-copy пути между capture texture и tensor. Текущие лучшие VN-модели поставляются как HLSL и уже исполняются FP16 на GPU. Перенос GPU texture → CPU/NPU tensor → GPU texture в каждом кадре способен увеличить latency и энергозатраты.

Следующий исследовательский этап:

1. экспорт CuNNy2 NVL в ONNX;
2. INT8/BF16 quantization и VitisAI compilation;
3. benchmark 1280×720 → 2560×1440 и 1920×1080 → 3200×1800;
4. сравнение end-to-end frame time, включая texture/tensor interop;
5. автоматический выбор NPU только при выигрыше по p95 latency и энергопотреблению.

## Критерии качества

Для будущего объективного сравнения нужны отдельные наборы:

- текст visual novel: OCR accuracy, edge overshoot/ringing, мелкие кандзи/кириллица;
- line art/CG: SSIM, LPIPS и слепое попарное сравнение;
- градиенты: banding count и chroma shift;
- real-time: median/p95 GPU frame time, dropped frames, input-to-photon latency;
- стабильность: resize, alt-tab, multi-monitor, DPI 100/150/200%, HDR on/off.

Без такого набора слово «самый совершенный» было бы маркетинговым утверждением. Реализованный пресет — исследовательски обоснованный сильный baseline, а не заявление о математически абсолютном качестве.
